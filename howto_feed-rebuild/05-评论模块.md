# 05 - 评论模块（Comment）【全量版】

前置：阶段 4。结构与点赞同构，练"照着成熟模式举一反三"，重点在**属主权限校验**和**写时冗余**。

> **对齐原则（全程适用）**：最终产出 = 原项目全部功能。若某能力依赖后续阶段（Redis 缓存、限流、MQ 异步落库、通知推送），本文档明确标注"阶段 N 回填"，绝无遗漏——每个能力都有归属阶段。

## 目标

- 发表评论（**@提及**会写通知）、删除评论（**仅作者本人**）、列出视频全部评论（时间升序、上限 200 条）
- 评论数参与热度：发评论 popularity +1（MQ 化与缓存失效部分阶段 7/9 回填）
- 与 account 模块配合：**发布时**由 handler 查账号填入 username（写时冗余），列表接口零补齐
- 评论没有唯一约束（一人可发多条）——没有 1062 分支，幂等性弱于点赞，这是与点赞模块的关键差异

## 接口设计

| 路由 | 鉴权 | 限流(阶段7回填) | 请求 → 响应 |
|---|---|---|---|
| POST /comment/listAll | 无 | - | `{video_id}` → `[comment...]`（created_at 升序，最多 200 条） |
| POST /comment/publish | JWT | 10次/分/账号 | `{video_id, content}` → `{message}` |
| POST /comment/delete | JWT | 10次/分/账号 | `{comment_id}` → `{message}` |

三个接口都是 POST（含 listAll，项目惯例：JSON body 走 POST）。错误响应统一 `{"error": "..."}`。

comment 对象（listAll 返回的数组元素）：

```json
{
  "id": 12,
  "username": "alice",
  "video_id": 3,
  "author_id": 2,
  "content": "拍得真好 @bob",
  "created_at": "2026-09-10T12:00:00+08:00"
}
```

各失败分支的真实状态码（以原项目 `apierror.ClassifyHTTPStatus` 为准，验收时别意外）：

| 场景 | 状态码 | error 消息 | 来源 |
|---|---|---|---|
| publish：content 为空 / video_id<=0 | 400 | `content is required` / `video_id is required` | handler |
| publish：视频不存在 | 500 | `video not found` | service（裸 errors.New → 500） |
| delete：评论不存在 | 500 | `comment not found` | service |
| delete：删别人的评论 | **401** | `unauthorized`（apierror.ErrUnauthorized） | service |
| listAll：视频不存在 | 500 | `video not found` | service |
| listAll：无评论 | 200 | `[]`（nil 切片兜底成空数组，不是 null） | handler |

## 关键设计决策（动手前先回答自己）

**Q1：谁能删评论？判断代码在哪一行？** 在 **Service 层 `CommentService.Delete`** 里，且在一切落库/入队动作之前：

```
repo.GetByID(commentID) → nil → errors.New("comment not found")
comment.AuthorID != accountID → apierror.ErrUnauthorized   ← 权限判断就这一行
```

Handler 从 `jwt.GetAccountID(c)`（JWT 中间件 `c.Set("accountID")` 的产物）取身份，请求体里**只有 comment_id，没有任何可伪造的身份字段**——不信任客户端是这条安全线的根基。注意原项目用的是 401（unauthorized）而不是 403（forbidden），语义上 403 更贴切，复刻时先照抄，进阶改进里再讨论。

**Q2：为什么 handler 会依赖 account 模块的 service？** `NewCommentHandler(service, accountService)`——因为 `Comment.Username` 是**写时冗余**：发布时需要把 accountID 翻译成 username 存进评论行。这一步放在 handler 而不是 service，原项目的分层逻辑是：service 只收"完整的业务对象"，**身份 → 展示信息的装配属于请求组装**，由 handler 完成（`accountService.FindByID(ctx, authorID)` 查出账号，填 `Comment.Username` 后整体交给 service）。这也是本项目 handler 跨模块依赖 service 的唯一样板：依赖的是**读查询**，不引入写路径耦合。为什么不用 JWT claims 里现成的 username（`c.Set("username")`）省一次查库？`FindByID` 拿的是**当前**用户名（改过名也正确），claims 里是签发时刻的快照，且查一次顺带确认账号仍然存在。

**Q3：评论列表怎么"补用户信息"？** 答案是**不补**——这正是原项目的设计：username 在发布时就冗余进了 Comment 行（Q2），`listAll` 一条单表查询直接带出 username，**零 JOIN、零额外查询、零 N+1**。和 account 模块的配合全部发生在写路径。代价两条：用户改名后历史评论仍显示旧名（读时补齐则永远最新）；列表拿不到头像（进阶改进可改读时批量补 `avatar_url`——注意要批量化防 N+1）。

**Q4：和点赞模块的架构差异？** 模式同构，差异三点：
- 无唯一约束 → 无 1062 分支、无幂等防线（重复发布就是两条评论，产品语义如此）
- 删除必须**先查后校验再删**（点赞 unlike 只需 RowsAffected）；属主判断必须同步做，**不能把"能否删"交给异步 Worker**——delete 事件里只有 commentID，Worker 无从校验身份
- publish 事件带全量上下文（username/videoID/authorID/content），Worker 不用回调 API；delete 事件只带 commentID，Worker 得先 `GetByID` 查回评论（这也是删评论没减热度的诱因，见 Q5）

**Q5：热度与缓存怎么更新？** 最终形态是"**MQ 优先、失败直写**"的双开关降级（阶段 9 实现，阶段 5 先写事务直写版）：

```
mysqlEnqueued  := commentMQ.Publish(username, videoID, authorID, content) 成功
redisEnqueued  := popularityMQ.Update(videoID, +1) 成功
两者都成功      → 直接返回（MySQL 落库交 CommentWorker，Redis 交 PopularityWorker）
commentMQ 失败  → 事务直写：确认视频存在 → INSERT comment → UPDATE popularity +1
popularityMQ 失败 → UpdatePopularityCache(ctx, cache, videoID, 1)（Redis 兜底，阶段 7 回填）
最后 notifyMentions(ctx, comment)（两条路径都调）
```

画个 2×2 矩阵推演四种组合：**MySQL 和 Redis 各自恰好 +1，不重不漏**——直写事务代码不是废代码，它就是降级路径。删评论原项目**没有 popularity -1**（已知瑕疵，榜单虚高）：`comment.delete` 事件只传 commentID，Worker 得先查回评论才知道 videoID，而它没查热度这一步——教训是"**事件里要带够上下文**"。复刻时建议你补上（Delete 里记录 videoID 一并 -1）。

**Q6：@提及通知怎么做的？** `notifyMentions`（就在 comment_service.go 里）：正则 `@(\w+)` 抽取提及 → seen map 去重、跳过自己 → 按 username 查 accounts 表拿 id（查不到就跳过）→ **直接写 notifications 表**（Type="mention"、TargetID=videoID、Content="<user> 在评论中提到了你"），失败只 log 不影响评论成功。两个细节：它绕过 repo 层直接用 `s.repo.db` 写表（同包内可行，分层妥协，心里有数）；MQ 路径下评论落库是异步的，但提及通知是**同步**写的——极端情况下评论最终没落库、通知却已发出（原项目接受的不一致）。另外 comment.publish 事件还有第二个消费者（通知视频作者"评论了你的视频" + SSE 推送），阶段 9 回填。

## 难点清单（本阶段真正难的地方）

1. **属主校验的位置与时机**：必须同步在 `service.Delete`、任何删除/入队动作之前完成（GetByID → 比对 AuthorID）。不能挪进 Worker：delete 事件只有 commentID，异步方既没有身份上下文也没有义务做安全判断。删别人的评论是 401 不是 200 也不是 403——每个码都要能解释来源。
2. **双 MQ + 缓存的降级矩阵**：commentMQ/popularityMQ 成败共 4 种组合，每种组合下 MySQL、Redis 各自恰好 +1、不重不漏（Q5 的 2×2 表）。阶段 5 虽然只写直写版，但接口签名和 nil 判空要一次到位，阶段 9 才不用返工。
3. **错误分类的精确使用**：原项目只有 `ErrUnauthorized`→401、`ErrValidation`→400、`gorm.ErrRecordNotFound`→404 有专属状态码；service 里的 `errors.New("video not found")`、`"comment not found"` 是裸错误 → 全部落 500。要能逐分支说出每个失败返回什么码、为什么，而不是笼统"报错了"。

## 亮点（原项目在评论模块的工程亮点）

- **写时冗余 username**：发布时查一次账号，列表读取永远单表、零 JOIN、零 N+1，配合 `LIMIT 200` 硬上限，读性能恒定可预期——"写时多一次、读时省 N 次"的典型取舍
- **MQ 优先 + 事务直写降级**：阶段 5 写的直写事务到阶段 9 原封不动变成 fallback 分支，零废弃代码；`cache/MQ` 参数可 nil 的构造函数让"同步版"和"异步版"共用同一套代码
- **事件自描述**：`CommentEvent` 带 EventID/Action/OccurredAt，publish 事件携带全量上下文（Worker 不回调 API 就能落库），为跨进程消费和幂等预留了字段
- **nil 切片兜底**：listAll 把 nil 转成 `[]Comment{}`，前端永远拿到数组而不是 null——一行代码省掉一类前端判空 bug

## 常见的坑

- content 全是空格：handler 只查 `req.Content == ""`，全空格会**穿透**到 service 被 TrimSpace 拦截——但报错是裸 errors.New，HTTP 状态是 500 不是 400（原项目瑕疵，进阶改用 `apierror.ErrValidation`）
- service 里 `errors.New("video not found")` / `"comment not found"` → **500 而非 404**（ClassifyHTTPStatus 只认 gorm.ErrRecordNotFound）；验收用 Postman 时别以为自己写错了
- 列表顺序和上限：`ORDER BY created_at ASC` + `LIMIT 200`——别凭直觉写成 DESC 或不加上限（旧版文档说"不分页"已过时，原项目现已有硬上限）
- `DeleteComment(ctx, comment)` 按主键删，传 `&Comment{}` 不带 ID 会删不动/全表条件异常；删除本身不做幂等成功（先查后删，不存在报 "comment not found"）
- listAll 忘了 nil → `[]Comment{}` 兜底 → 无评论时 JSON 返回 null
- notifyMentions 直接用 `s.repo.db` 写 notifications 表（绕过 repo 层）+ `CommentService.VideoRepository` 字段是导出的（大写）而 `repo` 是私有的——原项目命名不一致，照抄即可，但要能指出这不优雅
- `@(\w+)` 不匹配中文用户名：若你的系统支持中文昵称当用户名，正则要换（`@([\p{Han}\w]+)` + FindAllStringSubmatch 的 UTF-8 注意事项）
- CommentWorker 收到 publish 事件会再查一次视频存在性、再 TrimSpace 一次——MQ 路径下"生产者校验 ≠ 消费者免校验"，别省

## 验收清单

- [ ] A 发布评论 → 200 `{"message":"comment published successfully"}`；listAll 可见（username 正确、created_at 升序）
- [ ] B 删 A 的评论 → **401** `{"error":"unauthorized"}`；A 自己删 → 200；删除后 listAll 不再出现
- [ ] 对已删除/不存在的评论再调 delete → `{"error":"comment not found"}`（状态码 500，原项目如此）
- [ ] 对不存在的视频发评论 / listAll → `{"error":"video not found"}`
- [ ] content 全空格 → 被拦截（注意状态码 500，进阶改进后才变 400）
- [ ] video_id=0 / content 为空 / comment_id=0 → 400 `"xxx is required"`
- [ ] 无评论的视频 listAll → `[]` 而不是 `null`
- [ ] 评论带 `@已存在用户` → notifications 表出现 type=mention 记录；@自己 / @不存在的用户 → 无记录；第 201 条评论不出现在列表里（可选，造数据验证 LIMIT 200）
- [ ] （你的改进版）删评论后 popularity 相应 -1

## 后续阶段回填清单（到时回来改，现在不做）

**阶段 7（Redis）**
- router 给 `NewCommentService` 传入 `cache`（构造参数第 3 位）
- publish/delete 路由挂 `commentLimiter := ratelimit.Limit(cache, "comment_write", 10, time.Minute, ratelimit.KeyByAccount)`
- JWTAuth 换成 `jwt.JWTAuth(accountRepository, cache)`
- `UpdatePopularityCache`（`internal/video/popularity_cache.go`）：popularityMQ 失败时的 Redis 兜底分支接进来——内部含 `video:detail:*` / `video:entity:*` 缓存失效（本阶段语义就齐了）

**阶段 8（热榜）**
- `UpdatePopularityCache` 里的热度分钟桶部分（`hot:video:1m:<分钟>` 的 ZIncrBy + 2h 过期）随热榜文档回填，函数不用改

**阶段 9（RabbitMQ + Worker）**
- router 构造 `commentMQ`（NewCommentMQ 失败 log + 置 nil）、传入 `NewCommentService` 第 4/5 参
- `Publish` 改成 Q5 的双开关降级矩阵（阶段 5 的事务整体缩进为 fallback 分支）；`Delete` 改成 commentMQ.Delete 优先、失败回落 `repo.DeleteComment`
- 独立 Worker 进程（`cmd/worker/main.go`）：声明 comment 拓扑（exchange `comment.events` + 队列 `comment.events` + 绑定 `comment.*` + DLX，QoS 50），`CommentWorker`：`applyPublish`（再校验 → 插入 → `ChangePopularity(+1)`）/ `applyDelete`（GetByID → 删，**未减热度**——已知瑕疵对照点）；指数退避重试 3 次后 Ack 丢弃
- publish 路径的 Redis 侧由 `PopularityWorker` 消费 `video.popularity.events` 完成（调同一个 `UpdatePopularityCache`）
- 第二消费者：router 给 `comment.events` 交换机挂 `notification.comment` 队列（绑定 `comment.publish`），`NotificationWorker` 给视频作者写 Notification（"评论了你的视频"，跳过自己）+ SSE 实时推送

**更远的改进（无固定阶段）**：删评论 popularity -1；用 EventID + 去重表做 MQ 幂等消费；listAll 游标分页（练阶段 3 的模式）；读时批量补 avatar_url（练阶段 3 的 BatchGet 模式）。
