# 08 - 热榜（分钟桶 ZSET + 快照分页 + 双游标降级）★★★★★ 全项目难度最高

前置：阶段 7。难度 ★★★★★，抽象度也最高。建议先在 redis-cli 里手工把数据结构玩一遍再写代码，动笔前把"难点清单"四条逐个想透。

## 目标

点赞/评论实时累加热度 → 分钟桶 ZSET；`/feed/listByPopularity` 读"最近 60 分钟"聚合榜，**翻页期间榜单冻结不抖动**；Redis 不可用时降级 MySQL 三游标分页。做完后：连续翻页榜单不抖；`docker stop redis` 接口照常 200。

## 热度模型

| 行为 | popularity 增量（MySQL，累计值） | 热榜 ZSET 增量（Redis，窗口值） |
|---|---|---|
| 点赞 | +1 | +1 |
| 取消点赞 | -1 | -1 |
| 评论 | +1 | +1 |

（权重可自行设计，比如评论 +3；原项目就是 +1/-1。）

两条必须对照原项目说清楚的口径：

- **MySQL 的 `videos.popularity` 是累计值**，由点赞/评论的落库链路维护（阶段 8 在 service 事务里同步写，阶段 9 改到 LikeWorker/CommentWorker）；**Redis 分钟桶是"近 60 分钟净增量"**，由 PopularityWorker 维护（阶段 9）。两份数据、两条链路、两个失败域——这正是阶段 9 "双队列"设计的伏笔。
- **关注（follow）不触发热度**——原项目 social 模块与 popularity 零关联；评论删除也不回扣 -1。想做"关注作者 +5、删评论 -1"是进阶改进，先别做。

## 数据结构（先在 redis-cli 里玩）

```
# 写路径：点赞 +1（视频 42），key = "hot:video:1m:<yyyyMMddHHmm>"，member = videoID
ZINCRBY v1:hot:video:1m:202609091405  1  "42"
TTL     v1:hot:video:1m:202609091405        # ≈ 7200（每次写都续期 → 滚动过期）

# 读路径：as_of=14:05，把最近 60 个桶（含 14:05 本分钟）聚合成快照
ZUNIONSTORE v1:hot:video:merge:1m:202609091405  60
        v1:hot:video:1m:202609091405  v1:hot:video:1m:202609091404  ...（共 60 个）
        AGGREGATE SUM
EXPIRE  v1:hot:video:merge:1m:202609091405  120   # 快照只活 2 分钟
ZREVRANGE v1:hot:video:merge:1m:202609091405  0 9 # 第 1 页（rank 区间分页）
```

三要素背下来：

- **key 怎么拼**：`hot:video:1m:<yyyyMMddHHmm>`，时间取 `time.Now().UTC().Truncate(time.Minute)`；`cache.Key()` 会自动加 `v1:` 前缀（阶段 7 的约定）。
- **score 怎么算**：ZINCRBY 的增量就是 change（+1/-1），桶 score = 该分钟净互动量；快照 score = 60 桶 SUM = 近 60 分钟净增量。**不是累计 popularity**，且可以为负（先赞后取消）。
- **过期策略**：分钟桶 2h（60 分钟窗口 + 2 倍冗余，覆盖 Worker 重启与 as_of 回看）；快照 2min（给一次翻页会话留时间）。

## 接口协议（快照分页是核心思想）

路由：`POST /feed/listByPopularity`，挂在 `SoftJWTAuth` 分组（匿名可看榜，登录用户带 is_liked）。

```json
请求(第1页):  {"limit": 10, "as_of": 0, "offset": 0}
响应:         {"video_list": [...], "as_of": 1757393100, "next_offset": 10, "has_more": true,
               "next_latest_popularity": 7, "next_latest_before": "2026-09-09T14:03:21+08:00",
               "next_latest_id_before": 107}
请求(第2页):  {"limit": 10, "as_of": 1757393100, "offset": 10}   // as_of 原样带回来！
请求(Redis挂了之后的续翻): {"limit": 10, "latest_popularity": 7,
               "latest_before": "2026-09-09T14:03:21+08:00", "latest_id_before": 107}
```

要点：

- `as_of` 是**分钟对齐后的 Unix 秒**（服务端 Truncate 到分钟再回传）。
- 响应**同时携带两套游标**：`as_of/offset`（Redis 版）+ `next_latest_popularity/before/id`（DB 降级版，取本页最后一条）。前端约定：**as_of > 0 用 offset 翻页；收到 as_of == 0 的响应说明已降级，此后改用三游标翻页**。
- `latest_before` 在原项目里是 `time.Time` 直接 JSON 绑定，前端要传 RFC3339 格式。

## 关键设计决策（每一条都是面试题）

**Q1：为什么不直接一个大 ZSET 累加？** 单 key 写竞争激烈；且历史热度永远累计，无法表达"近期热门"。分钟桶 = 写分散（冲突概率降到 1/60）+ 天然时间衰减（老桶滚出 60 分钟窗口即消失，不需要任何定时器）。

**Q2：为什么翻页要冻结榜单（as_of）？** 实时榜每秒都在变，第 1 页和第 2 页之间名次互换 → 重复/漏看。**快照 + offset** 让一次浏览会话看到同一版本的榜单。

**Q3：快照什么时候重建？** `as_of` 落到分钟，快照 key `hot:video:merge:1m:<yyyyMMddHHmm>` 带 2min TTL 且**先 EXISTS 判断**——同一分钟的后续请求复用，只有跨分钟/过期才重算。翻页通常 2 分钟内完成，够用。`exists, _ := Exists(...)` 是**有意吞错**：查询失败按"不存在"处理 → 多算一次，ZUNIONSTORE 幂等，无害。

**Q4：ZSET 里只有 videoID，详情哪来？** `repo.GetByIDs` 一次 `IN` 查 MySQL 拿视频行，**再按 ZSET 返回的顺序重排**（IN 查询不保序！用 `map[uint]*Video` + 按 ids 序遍历）。注意原项目这里用的是 feed 自己的 `repo.GetByIDs` 直查 MySQL，没走 GetVideoByIDs 的三级缓存——榜单页每次就 10 条，直接查更简单。

**Q5：怎么判断翻到底？** 请求的 offset 已超榜 → `ZRevRange` 返回空且 `offset > 0` → 直接返回空列表 `has_more=false`（注意此时 next_offset **原样返回**，不要再 +limit）。而 `offset == 0` 时返回空则**不在此返回**——落到下面的 MySQL 降级（冷启动还没有任何桶数据的情况）。

**Q6：MySQL 降级版怎么分页？** 三字段复合游标（阶段 3 模式的三代目）：

```sql
ORDER BY popularity DESC, create_time DESC, id DESC
WHERE (popularity < ?) OR (popularity = ? AND create_time < ?)
   OR (popularity = ? AND create_time = ? AND id < ?)
```

只有 `time_before 非零 && id_before > 0` 才加 WHERE（**popularity=0 是合法游标值**，不能当"无游标"判断）；三字段必须成对出现，缺一 handler 直接 400。表上要有组合索引 `idx_videos_popularity_time_id (popularity DESC, create_time DESC)` 降级查询才走得快。

## 难点清单（★★★★★ 的难度全在这四条里，动手前逐条想透）

**难点 1：时间桶边界。**
- 对齐函数唯一：写路径 `time.Now().UTC().Truncate(time.Minute)`，读路径 `time.Unix(reqAsOf, 0).UTC().Truncate(time.Minute)`——两处必须**先 UTC 再 Truncate**，否则读写两侧算出不同 key，且和 as_of（Unix 秒）对不上。
- 窗口含"进行中的当前分钟"：`asOf.Add(-i*Minute)`，i 从 0 到 59 共 60 桶，i=0 就是 asOf 本分钟——首屏有准实时性；翻页时 as_of 已成过去分钟，60 桶全部冻结。
- `Format("200601021504")` 参考时间错一个字符 → key 全乱且极难发现。验收第一件事：redis-cli 确认 key 长相。
- 秒级粒度丢失：同分钟 N 次互动合并为 score=N（ZINCRBY 原子累加，并发安全）；跨分钟瞬间的一次互动只进新桶，旧快照看不到——实时性下界就是 1 分钟，固有取舍。
- ZINCRBY 会隐式建 key 但**不带 TTL**：ZINCRBY 与 EXPIRE 两步间进程被杀 → 桶永生。原项目用"每次写都续 2h"兜底（滚动过期），彻底方案是 Lua 原子化（进阶）。
- 客户端送来超过 2h 的旧 as_of → 桶已过期。ZUNIONSTORE 把缺失 key 当空集合，**不报错但窗口实际变短**、分数整体缩水——知道这个行为存在即可，正常翻页 as_of 只旧 2 分钟。

**难点 2：快照一致性。**
- 三层防抖，各掐一种抖动：as_of 定版（客户端带回，掐"版本漂移"）→ 快照 key 按分钟命名 + 2min TTL（同一分钟所有请求共享一份 ZSET）→ ZREVRANGE 按 rank 取区间（不变集合上 offset 才稳定）。
- EXISTS → ZUNIONSTORE **不是原子**：并发首翻会重算两三次。结果幂等（同样的 60 桶输入），只是白烧一次 O(N*K)——原项目接受这个浪费换代码简单；要抠就上锁/singleflight（进阶）。
- 重算的确定性：翻页请求的 as_of 是过去的分钟 → 60 桶全部冻结 → 快照过期重算结果完全一致；只有"as_of=当前分钟"的首屏重算会因本分钟新互动略有差异。所以 2min TTL > 典型翻页时长就够。
- 同分排序的确定性：score 相同时 ZSET 按 member 字典序定序（ZREVRANGE 里同分按 member 逆字典序）——榜单顺序确定，翻页不因同分抖动。member 用十进制 ID 字符串才保证这一点。
- 已删视频的洞：快照 member 对应的视频可能已从 MySQL 删除 → GetByIDs 查不到 → 剔除 → `NextOffset = offset + len(items)` 比 `offset+limit` 少 1 → 下一页起点回退一格，**可能重复返回上页末尾一条**。原项目已知取舍（量小无感）；严谨做法按 rank 推进或定时 ZREM 死视频。

**难点 3：ZSET 内存控制。**
- 三类 key 各有 TTL，一个都不能少：分钟桶 2h、快照 2min（另有阶段 7 的 detail/entity 缓存 5m）。忘设 TTL = 每分钟泄漏一个桶。
- 内存大头是快照：member 集合 = 60 分钟内所有被互动过的视频；2min TTL 限定了同时存活的快照数量。桶本身 member 数 = 当分钟活跃视频数，天然有界。
- 窗口别贪大：60 桶是 ZUNIONSTORE 的 K。开 24h 窗口 = 1440 个 key 一次聚合，阻塞 Redis 主线程几十上百 ms，还可能撞 proto-max-bulk-len。要"24h 热榜"应该做小时桶（24 个）或预聚合。
- member 编码即协议：写路径 `strconv.FormatUint`，读路径 `strconv.ParseUint` 还原 ID（非数字/0 的 member 直接丢弃），别加前缀别用 JSON。
- 原项目没做桶内裁剪：被疯狂刷的单桶会膨胀。改进：写路径顺带 `ZREMRANGEBYRANK` 只留 TopN（zset.go 已封装 ZRemRangeByRank，原项目用在 timeline 裁剪，思路可搬）。

**难点 4：降级切换的数据口径。**
- **两个榜单不是同一份数据**：Redis 版 = 近 60 分钟净增量（滑动窗口，有负分、老视频掉榜）；MySQL 版 = 累计 popularity 全期排序（单调、无时间语义）。停 Redis 的瞬间用户看到的"第一名"会变——原项目把它当已知取舍，你也必须在注释/文档里写明。
- 降级的两种形态收敛到同一个查询：**启动时挂**（cmd/main.go Ping 失败 → cache=nil → 整个 Redis 分支跳过）；**运行中挂/超时**（opCtx 80ms 超时 → Exists/ZUnionStore/ZRevRange 任一报错 → 不 return，继续走到 repo.ListByPopularity）。nil-safe 封装让 `cache==nil` 时读方法返回"空+无错"，流程同样自然滑入降级——业务代码只有一个 `if f.rediscache != nil`。
- 空榜与翻到底的分岔：`offset > 0` 的空 = 翻到底（返回空列表，as_of 照回）；`offset == 0` 的空 = 没有桶数据 → 降级查 DB（响应 as_of=0）。前端靠 `as_of` 是否 > 0 识别降级态。
- 降级瞬间的续翻靠"双游标并存"：Redis 版每一页都顺带下发 DB 三游标，所以无论在哪一页断掉，前端手里都有能继续的 DB 游标——前提是前端从第 1 页起就把它存下来，别只存 as_of/offset。

## 亮点：分钟桶 + 快照的组合设计

单看每层都平常（时间分桶、缓存快照、rank 分页），**组合起来**才解决"实时榜"的本质矛盾：榜单实时变 vs 分页要求稳定。

- **写路径 O(1)**：ZINCRBY 单 key 单 member，写竞争被分钟切散；"近期热门"的语义靠 TTL 滚出窗口自然达成，零定时器。
- **读路径摊平**：从"每请求一次 O(N*K) 聚合"降为"每分钟一次 ZUNIONSTORE + N 次纯读"。快照把聚合成本按分钟摊平，TTL 控制新鲜度，as_of 把"用哪一版榜单"的决策权交给客户端。
- **降级是接口契约的一部分**，不是事后补救：一套接口、一个响应结构同时承载两套游标，Redis 生死对前端基本透明。
- **与全项目的降级哲学一脉相承**：阶段 7 的 nil-safe 封装、阶段 9 的"双队列按目标独立降级"，都是"每个依赖可有可无、每个请求都有活路"。热榜是这套哲学里最精巧的落地。

## 常见的坑

- 桶 key 忘了 `v1:` 前缀：`cache.Key()` 统一加前缀，redis-cli 验收要敲 `ZREVRANGE v1:hot:video:1m:<分钟> 0 -1 WITHSCORES`
- 时区：必须 `time.Now().UTC().Truncate(time.Minute)`；用本地时间 → 读写两侧 key 错位、和 as_of 对不上
- `Format("200601021504")` 参考时间写错一个字符，key 就乱
- `ZRevRange` 只回 member 不回 score（本接口只用排名所以 member 够；要分数用 `ZRevRangeWithScores`）
- ZUnionStore 是 O(N*K)：60 桶 × 每桶成员数——别把窗口开成 24h（1440 桶）
- 降级版和 Redis 版的**排序语义不同**（累计 popularity vs 近 60 分钟增量），属已知取舍，接口注释里写明
- `NextOffset = offset + len(items)` 而不是 `offset + limit`：有视频被剔除时长度会短——理解这个选择及它带来的"可能重复 1 条"副作用（难点 2）
- `latest_before` 是 `time.Time` 直接 JSON 绑定 → 前端传 RFC3339（`"2026-09-09T14:03:21+08:00"`），和阶段 3 用 Unix 秒的风格不一致，别混淆
- 读路径 80ms / 写路径 50ms 超时都不能省：Redis 半死不活（连得上不回包）时全靠它保接口
- 点赞后只 DEL `video:detail` 忘了 `video:entity` → 最新流的 L2 缓存还是旧热度值（两个 key 的失效归属不同：entity 是给 ListLatest 的 GetVideoByIDs 用的）
