## 数据模型（关注关系怎么存：自引用设计）

```go
type Social struct {
    ID         uint `gorm:"primaryKey"`
    FollowerID uint `gorm:"not null;index:idx_social_follower;uniqueIndex:idx_social_follower_vlogger"`
    VloggerID  uint `gorm:"not null;index:idx_social_vlogger;uniqueIndex:idx_social_follower_vlogger"`
}
```

这张表是**自引用设计**：一行 = "follower_id 关注了 vlogger_id" 这一条有向边，两个 ID 都逻辑指向 `accounts.id`（不加 GORM foreign key 标签，**数据库层无外键约束**，完整性靠 service 校验两端账号存在）。

三个索引用途要分清：

- `uniqueIndex:idx_social_follower_vlogger (follower_id, vlogger_id)`——**防重复关注的唯一防线**（与点赞模块同款双层防御的兜底层）；按最左前缀它同时覆盖"查我关注了谁"的查询
- `idx_social_vlogger`——反向查询"谁关注了我"和 CountFollowers
- `idx_social_follower`——被复合唯一索引的最左前缀覆盖，**严格说是冗余的**（原项目显式建了，无害）；写的时候你能讲出"最左前缀原则"就赚到

两个值得注意的"原样保留项"：

- **没有 `created_at`**——无法知道何时关注，粉丝列表因此只能按主键序（≈关注先后）返回
- 请求/响应结构体照 entity.go 敲全：`FollowRequest/UnfollowRequest`（都是 `{vlogger_id}`）、`GetAllFollowersRequest`（`{vlogger_id}`）、`GetAllVloggersRequest`（`{follower_id}`）、`GetAllFollowersResponse/GetAllVloggersResponse`、`SocialCounts`

## 关键设计决策（动手前先回答自己）

**Q1：怎么防关注自己/重复关注/关注不存在的人？** 三层，顺序不能乱：

1. `FindByID` 校验 follower、vlogger **两端都存在**（无外键约束，完整性自己兜）
2. 业务校验：`FollowerID == VloggerID` → `can not follow self`；`IsFollowed` 预检 → `already followed`（给用户友好报错）
3. 复合唯一索引兜底：并发双击时第二次 Insert 必报 1062（预检和插入之间有时间窗，单靠预检挡不住，与阶段 4 点赞同一课）

**Q2：粉丝/关注计数怎么维护——冗余列还是实时 COUNT？** 原项目选**实时 COUNT**（`CountFollowers/CountVloggers` 每次对 socials 做 `SELECT COUNT(*)`），和点赞的 `videos.likes_count` 冗余列形成鲜明对比。为什么可以这么做：关注计数的读场景只有个人主页/列表页尾部，读频远低于"每条视频都要展示的点赞数"，实时 COUNT 换来了**零维护成本、零不一致风险**。体会这个取舍：冗余列是为读热点付的写复杂度税，没有热点就不付。

**Q3：粉丝列表两段查询还是 JOIN？** 原项目用两段：先查 relations 拿 ID 列表，再 `WHERE id IN ?` 查账号。注意三个细节：**`Limit(200)` 硬上限**（第 201 个粉丝拿不到）；ID 列表为空要**提前 return 空 slice**（不能拿空 IN 去查）；两段都**没有 ORDER BY**（顺序 = 主键序）。你两种都写一遍，比较后选一种（推荐练 JOIN）。

**Q4：取关不存在的关注关系，报错还是幂等成功？** 原项目是**报错**：service 里 `IsFollowed` 预检，未关注 → `not followed`（注意不是老版本文档说的"幂等成功"）。而 Worker 消费 unfollow 事件时的 `Delete` 才是 RowsAffected==0 静默通过。两种语义各有场景：接口层报错让用户知道操作没生效，异步层幂等保证重复消费无害——你复刻时保持这套区分。

**Q5：没关注任何人时关注流返回什么？** 空列表，不是全部视频。关键在 `viewerAccountID > 0` 这个判断：>0 才加 `author_id IN (子查询)` 过滤（子查询空 → IN 空 → 0 行）；==0 则**完全不过滤**（等于全表最新流）——所以 listByFollowing 必须挂强鉴权，见下文。

**Service 层骨架**（注意：构造参数 4 个，后两个本阶段传 nil，nil 防御从第一天就写对）：

```go
func NewSocialService(repo *SocialRepository, accountrepo *account.AccountRepository,
    socialMQ *rabbitmq.SocialMQ /*阶段9回填*/, cache *rediscache.Client /*阶段7回填*/) *SocialService

func (s *SocialService) Follow(ctx context.Context, social *Social) error:
  1. accountrepo.FindByID(follower) + FindByID(vlogger)   // 两端存在性
  2. follower == vlogger → errors.New("can not follow self")
  3. repo.IsFollowed → true → errors.New("already followed")
  4. repo.Follow                                          // 唯一索引兜底 1062
  5. [阶段7回填] invalidateFollowingFeedCache(followerID)  // s.cache 为 nil 直接 return
  6. [阶段9回填] s.socialMQ != nil → Follow(followerID, vloggerID)，失败仅记日志
```

`Unfollow` 同构：两端存在性 → `IsFollowed` 预检（false → `not followed`）→ 删 → 失效缓存 → 发 MQ。`GetAllFollowers/GetAllVloggers` 先 `FindByID` 验目标账号存在再查列表；`CountFollowers/CountVloggers` 直通 repo（不验存在性，查不存在的 ID 自然得 0）。

**Handler 层**：follow/unfollow 先 `req.VloggerID <= 0 → 400 "vlogger_id is required"`，再 `jwt.GetAccountID(c)`（失败 → 401）确定 follower；**列表接口的参数可空处理**（`getAllFollowers/getAllVloggers` 同款）：

```go
vloggerID := req.VloggerID
if vloggerID == 0 {
    accountID, err := jwt.GetAccountID(c)   // 注意 err 要检查 → 401，不能丢弃
    if err != nil { c.JSON(401, gin.H{"error": err.Error()}); return }
    vloggerID = accountID
}
```

列表 handler 查完还要补一次计数并塞进响应；`followers == nil` 时替换成 `[]*account.Account{}`（否则 JSON 出 `null`）。计数错误原项目用 `_` 吞掉（失败显示 0），你可以改进成记日志。`getCounts` 不绑定请求体，直接取 JWT ID → 两次 Count → 返回 `SocialCounts`。

## getProfile 聚合接口（跨模块聚合的难点亮点，阶段 6 完成时回填）

阶段 1 文档里挂了"getProfile 路由阶段 6 回填"——**本阶段 socialRepository 一就位，四个依赖就齐了**，现在回去把它补上。原项目 `backend/internal/http/router.go:143-168`：

- **路由挂在 accountGroup 上（公开、无鉴权）**，handler 是 router 里的一段**内联匿名函数**，不进任何模块的 handler.go——因为它不属于任何单一模块，是"胶水层"
- **混用 service 和 repo**：account 走 `accountService.FindByID`（带缓存逻辑），三个统计数**直接调各模块 repo**，绕过 service——这是有意的取舍：统计要实时新鲜，不值得缓存

```go
accountGroup.POST("/getProfile", func(c *gin.Context) {
    var req account.GetProfileRequest                 // {account_id}
    // 绑定失败 → 400；req.AccountID == 0 → 400 "account_id is required"
    acc, err := accountService.FindByID(ctx, req.AccountID)     // 阶段1：查不到 → 500
    // ↓ 阶段2 repo 方法                ↓ 阶段6 repo 方法
    videoCount,    _ := videoRepository.CountByAuthor(ctx, req.AccountID)        // COUNT videos WHERE author_id
    totalLikes,    _ := videoRepository.TotalLikesByAuthor(ctx, req.AccountID)   // SUM(likes_count) + COALESCE
    followerCount, _ := socialRepository.CountFollowers(ctx, req.AccountID)      // COUNT socials WHERE vlogger_id
    vloggerCount,  _ := socialRepository.CountVloggers(ctx, req.AccountID)       // COUNT socials WHERE follower_id
    c.JSON(200, account.GetProfileResponse{Account: account.FindByIDResponse{ID, Username, AvatarURL, Bio},
        VideoCount: videoCount, TotalLikes: totalLikes, FollowerCount: followerCount, VloggerCount: vloggerCount})
})
```

三个必须想清楚的点：

1. **依赖清单**：`videoRepository.CountByAuthor` / `TotalLikesByAuthor`（阶段 2，`video_repo.go:106-120`，后者 `COALESCE(SUM(likes_count),0)` 防 NULL）+ `socialRepository.CountFollowers` / `CountVloggers`（阶段 6）。任何一个不存在都编译不过——这就是为什么它必须等到本阶段
2. **错误策略不对称**：账号不存在 → 500 拒绝；四个统计数错误 → 全部 `_` 吞掉按 0 返回（部分降级也要给页面出数据）。原项目连日志都不打，你至少补 `log.Printf`
3. **归属之争**：内联在 router 里 vs 建 `profile` 聚合 service vs 挪进 accountHandler 注入两个 repo。原项目选了最省事的内联——能用，但 router 越长越难测。**建议**：你复刻时把它抽成一个 `GetProfile` 方法放进 accountHandler（构造参数加 `videoRepo`、`socialRepo`），体会"聚合逻辑放哪"的架构题；想省事就跟原项目内联，验收不受影响

`GetProfileRequest/GetProfileResponse` 在阶段 1 已敲进 account/entity.go，本阶段只是把路由接上。

## listByFollowing 关注流（feed 模块）与本模块的关系

路由在 feed 模块（阶段 3 文档预留的口子）：`/feed/listByFollowing` 挂在 `protectedFeedGroup`——feed 组整体 `SoftJWTAuth`，这个子组**再叠一层 `JWTAuth`**（强鉴权：关注流必须知道"我是谁"，匿名无意义）。

- **请求/响应**：`{limit, latest_time}` → `{video_list:[FeedVideoItem], next_time, has_more}`，limit 归一化（<=0 或 >50 → 10）、`latest_time` Unix 秒还原成 `time.Time`——阶段 3 的全套游标协议原样复用
- **一条 SQL 完成**（`feed/repo.go:52-70`）：feed 包 import `social.Social` 模型做子查询——**跨模块依赖发生在模型层**：

```go
if viewerAccountID > 0 {
    followingSubQuery := db.Model(&social.Social{}).Select("vlogger_id").Where("follower_id = ?", viewerAccountID)
    query = query.Where("author_id IN (?)", followingSubQuery)   // 一条 SQL，不在 Go 里拼 ID 列表
}
if !latestBefore.IsZero() { query = query.Where("create_time < ?", latestBefore) }
query.Order("create_time DESC").Limit(limit)
```

原项目选择"子查询下推给 MySQL"而不是"先查关注 ID 列表再 IN"——少一次往返，代价是 feed 包直接认识 social 的表结构（依赖方向 feed→social）。更解耦的做法是 social repo 暴露 `FollowingIDs(ctx, followerID) ([]uint, error)` 供 feed 拼接，两种都试一遍。

- **service 组装**：查完视频走阶段 3/4 的 `buildFeedVideos`（is_liked 从真实点赞表来），`next_time` = 本页最后一条的 `create_time.Unix()`，`has_more = len == limit`
- **与 social 模块的双向联动**（本阶段最容易被忽略的一条线）：
  - 读方向：关注流读的就是 socials 表（子查询）
  - 写方向：A 关注/取关 B 后，A 的关注流立刻要变——**阶段 7 回填**时 Feed 的 listByFollowing 会加缓存（key `feed:listByFollowing:limit=%d:accountID=%d:before=%d`），而 social service 的 `Follow/Unfollow` 里负责按 pattern `feed:listByFollowing:*:accountID=<followerID>:*` **失效 A 的所有游标页缓存**（`social/service.go:94-102`）。本阶段先把 `invalidateFollowingFeedCache` 的 nil 防御版本写好（cache 为 nil 直接 return），阶段 7 接上就通

## 原项目的写路径范式（复刻时要做取舍）

原项目 Follow 的实际流程：**先同步直写 MySQL → 失效缓存 → 最后发 MQ**，Worker 又消费一遍同一条消息重复 Insert → 重复插入靠唯一索引 + 1062 忽略兜底（`worker/socialworker.go:95-108`）；Unfollow 同理（Worker 的 Delete 天然幂等）。而 like/comment 是"MQ 成功就**不**直写"。两种范式混用是历史遗留：

- 范式 A（like/comment）：MQ 是唯一写路径，直写只是降级 → 削峰彻底，但读己之写有延迟
- 范式 B（social）：双写，MQ 冗余 → 强一致、无"关注了却看不到"的窗口，但 MQ 没减负（只承担通知/统计）

**建议**：你复刻时选一种范式并贯彻。关注关系的写入频次天然低，范式 B（原项目现状）其实合理——本阶段就按"校验 → 直写 → [缓存失效] → [发 MQ]"实现，MQ 那步阶段 9 再接上。

## 难点清单（本阶段真正难的地方）

1. **校验顺序与幂等语义**：两端存在性 → 自关注 → IsFollowed 预检 → 唯一索引兜底，四层各挡一种非法输入；接口层"未关注就取关"要报 `not followed`，异步层删除要幂等——同一条业务在两个入口语义不同，要能讲清楚为什么
2. **getProfile 跨模块聚合**：一个 handler 摸四个数据源，混用 service 与 repo、错误策略不对称（主数据拒绝、统计降级）、聚合代码放哪（router 内联 vs 独立聚合层）——这是后面做任何"个人主页/详情页聚合"的原型
3. **关注流的鉴权分叉**：`viewerAccountID == 0` 意味着"不过滤"（全表），`> 0` 才是"只看关注的人"——一个判断写反，匿名请求就变成全站最新流；所以 listByFollowing 必须强鉴权，且 handler 取 JWT 失败时要降级处理而不是放行

## 亮点（原项目在关注模块的工程亮点）

- **自引用关系表 + 双向索引**：3 列存下整个关注图，两个方向各一个索引服务各自方向的列表/计数，复合唯一索引把"防重复关注"下沉到数据库层——应用重启、并发、MQ 重复消费都冲不垮这条防线
- **计数零维护**：粉丝/关注数不落冗余列，实时 COUNT——用读频次低的特点换来"永不出错"，和点赞计数（冗余列 + `GREATEST` 防负数）构成一组对照实验，值得在复盘时对比写下来
- **写路径顺序讲究**：DB 成功 → 失效关注流缓存（SCAN 按 pattern 删，覆盖该用户所有游标页）→ 最后发 MQ 且失败只记日志——把"必须成功的"放前面、"锦上添花的"放后面，主流程永不因旁路组件挂掉而失败

## 常见的坑

- 列表两段查询忘判空：ID 列表为空还拿去 `IN ?`（查回全表风险）/ 忘 `Limit(200)` / 返回 nil slice → JSON `null` 炸前端
- `jwt.GetAccountID` 的 err 不检查就 `vloggerID, _ =` → 参数为 0 且未登录时静默用 0 当 ID
- 并发重复关注：预检挡不住，1062 会裸着变成 500——可改进为 `errors.As` 翻译成"already followed"（409/200 自选）
- 关注流忘写 `viewerAccountID > 0` 分支或把判断写成 `!= 0` 时漏了空关注列表测试 → 匿名/新用户看到全表
- 关注自己校验放在 IsFollowed 之后：自关注会先被"already followed"误拦（你自己不会出现在自己粉丝列表，但预检还是先跑一次）——先判自关注更省一次查询
- getProfile 的统计数错误连日志都没有 → 排查线上"计数显示 0"时两眼一抹黑
- 别把 Social 表当无主之表删字段：feed 的子查询、getProfile 的计数、本模块列表全指着 `follower_id/vlogger_id` 两列

## 验收清单

- [ ] A 关注 B → `{"message":"followed"}`；重复关注 → already followed；关注自己 → can not follow self；`vlogger_id` 缺省/0 → 400；关注不存在的用户 → 报错
