# 06 - 关注模块（Social）+ 关注流 + 软鉴权落地

前置：阶段 5。

## 目标

关注/取关、粉丝列表、关注列表；Feed 新增"关注流"（只看关注的人的视频，按时间游标）。`SoftJWTAuth` 在本模块正式派上用场。

## 接口设计

| 路由 | 鉴权 | 请求 → 响应 |
|---|---|---|
| POST /social/follow | JWT | `{vlogger_id}` → `{message}` |
| POST /social/unfollow | JWT | `{vlogger_id}` → `{message}` |
| POST /social/getAllFollowers | JWT | `{vlogger_id?}` → `{followers:[account]}` |
| POST /social/getAllVloggers | JWT | `{follower_id?}` → `{vloggers:[account]}` |
| POST /feed/listByFollowing | JWT | `{limit, latest_time}` → `{video_list, next_time, has_more}` |

> getAllFollowers/getAllVloggers 的参数**可空**：为 0 时默认"查我自己"（从 JWT 取）。

## 数据模型

```go
type Social struct {
    ID         uint `gorm:"primaryKey"`
    FollowerID uint `gorm:"not null;index:idx_social_follower;uniqueIndex:idx_social_follower_vlogger"`
    VloggerID  uint `gorm:"not null;index:idx_social_vlogger;uniqueIndex:idx_social_follower_vlogger"`
}
```

两个方向各一个普通索引（列表查询用）+ 组合唯一索引（防重复关注）。

## 关键设计决策

**Q1：怎么防关注自己/重复关注？** 业务校验（`FollowerID == VloggerID` 拒绝；`IsFollowed` 预检）+ 复合唯一索引兜底（1062）。和点赞模块同一套双层防御。

**Q2：粉丝列表两段查询还是 JOIN？** 原项目用两段：先查 relations 拿 ID 列表，再 `WHERE id IN ?` 查账号。优点是逻辑直白，缺点是两次往返；JOIN 一次搞定但取出的字段要小心。你两种都写一遍，比较后选一种（推荐练 JOIN）。

**Q3：关注流的 SQL？** 子查询版（原项目）：

```sql
SELECT * FROM videos
WHERE author_id IN (SELECT vlogger_id FROM socials WHERE follower_id = ?)
  AND create_time < ?          -- 时间游标，同阶段 3
ORDER BY create_time DESC LIMIT ?
```

GORM 写法：`query.Where("author_id IN (?)", db.Model(&Social{}).Select("vlogger_id").Where("follower_id = ?", uid))`。

**Q4：没关注任何人时？** 返回空列表，不是报错（`len(relations)==0` 提前 return 空 slice）。

## 实现提示

Follow 事务语义（原项目这里有个不一致，见下）：建议你实现为**先校验后直写**，MQ 留到阶段 9 再决定加不加。

handler 参数可空的处理：

```go
vloggerID := req.VloggerID
if vloggerID == 0 { vloggerID, _ = jwt.GetAccountID(c) }
```

## 原项目的一个架构不一致（复刻时要做取舍）

原项目 Follow 的实际流程：**发 MQ + 同步直写 MySQL**，Worker 又消费一遍同一条消息 → 重复插入靠唯一索引 + 1062 忽略兜底。而 like/comment 是"MQ 成功就**不**直写"。两种范式混用是历史遗留：
- 范式 A（like/comment）：MQ 是唯一写路径，直写只是降级 → 削峰彻底，但读己之写有延迟
- 范式 B（social）：双写，MQ 冗余 → 强一致但 MQ 没减负

**建议**：你复刻时选一种范式并贯彻。跟 like/comment 保持一致（范式 A）更好；SocialWorker 阶段 9 可以只做日志/统计消费者，练"同一队列多个消费者视角"。

## 常见的坑

- 取关不存在的关注关系 → 原项目 Unfollow 的 Delete RowsAffected==0 不报错（幂等成功），你也统一一下语义
- 关注流忘记 `viewerAccountID>0` 判断 → 匿名请求查全表
- `follow` 和 `unfollow` 都要校验目标用户存在（FindByID 两端都查）

## 验收清单

- [ ] A 关注 B；重复关注 → 报错；关注自己 → 报错
- [ ] B 的 getAllFollowers 出现 A；A 的 getAllVloggers 出现 B
- [ ] 不传参数调 getAllFollowers → 等价于传自己的 ID
- [ ] A 关注 B 后，A 的 listByFollowing 出现 B 的视频，时间倒序、游标翻页正常
- [ ] 取关后视频从关注流消失
