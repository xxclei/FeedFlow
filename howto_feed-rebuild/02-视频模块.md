# 02 - 视频模块（Video）+ 分片上传【全量版】

前置：阶段 1（JWT 鉴权 + 账号）。Feed 系统的素材来源，也是全项目第一个"文件处理 + 状态机"的重头戏。

本阶段做到与原项目**功能完全对齐**：视频/封面单文件直传、**分片上传四接口**（init / upload / status / complete，含断点续传与逐片校验）、发布（事务内写视频 + **本地消息表** + **Tag 自动提取**）、详情、作者列表、删除（service 有、路由未注册），外加 Gin 静态托管与绝对 URL 拼接。

> **对齐原则（全程适用）**：最终产出 = 原项目全部功能。若某能力依赖后续阶段（分片会话的 Redis 存储、详情缓存、热度 MQ、Outbox 消费），本文档明确标注"阶段 N 回填"，绝无遗漏——每个能力都有归属阶段。

## 目标

- **单文件直传**：`uploadVideo`（≤200MB、仅 .mp4）/ `uploadCover`（≤10MB、.jpg/.jpeg/.png/.webp），随机文件名落盘，返回可播放/可预览的绝对 URL
- **分片上传**：大文件切片上传，支持**断点续传**（同用户同文件 hash 重新 init 恢复会话）、**逐片 MD5 校验**、**重复分片幂等**、按序合并、失败清理临时目录
- **发布**：`publish` 把（直传或分片得到的）play_url/cover_url 落库；**一个事务**里同时写 video、OutboxMsg（阶段 9 消费）、Tag/VideoTag（从标题+描述里 `#xxx` 自动提取）
- **查询**：视频详情、作者主页视频列表（时间倒序，≤200 条）
- **文件服务**：`r.Static("/static", "./.run/uploads")`，URL 拼成绝对地址（识别 TLS / `X-Forwarded-Proto`）

## 接口设计

路由全表（原项目 `router.go:60-85`，chunk 四接口全部在 JWT 保护组里）：

|---|---|---|
| POST /video/uploadVideo | JWT | multipart `file` → `{url, play_url}`（两值相同） |
| POST /video/uploadCover | JWT | multipart `file` → `{url, cover_url}`（两值相同） |
| POST /video/publish | JWT | `{title, description, play_url, cover_url}` → video 对象（含自增 id） |

### 分片上传四接口的精确行为（照着做，别自己发明）

**1. `chunk/init` —— 建会话 / 判续传**
- `cache == nil` → 503；绑定失败 / 取 accountID 失败 → 400
- `file_size > 200<<20` → 400 `"file size exceeds 200MB limit"`
- **断点续传判断**：读 hash 索引 `chunk_upload_hash:<accountID>:<fileHash>` → 命中且旧会话还能反序列化 → **刷新两把 key 的 TTL** → 返回 `{upload_id: 旧ID, uploaded_chunks: [已传下标...]}`（前端拿着这个列表跳过已传分片）
- 未命中（或旧会话已过期丢失）→ 新建：`uploadID = randHex(16) + strconv.FormatInt(time.Now().UnixNano(), 10)`，会话 `{filename, file_size, chunk_size, total_chunks, file_hash, UploadedBits: make([]bool, total_chunks)}` 存入 session key + hash 索引 key（**都带 24h TTL**）→ 返回 `{upload_id, uploaded_chunks: []}`

**2. `chunk/upload` —— 传一片（multipart！）**
- `c.ShouldBind(&req)` 绑定 `form` 字段（**不是** ShouldBindJSON）；会话读不到 → 404 `"upload session not found"`；`session.AccountID != 本人` → 403
- `chunk_index` 越界 `[0, total_chunks)` → 400 `"invalid chunk_index"`
- **幂等**：`UploadedBits[i]` 已为 true → 直接 200 `{chunk_index}`，不重复落盘
- `c.FormFile("file")` → 打开 → **整片 MD5** 与 `chunk_hash` 比对，不符 → 400 `{error: "chunk hash mismatch", expected, actual}`（错因定位零成本）
- 落盘 `.run/uploads/tmp/<uploadID>/<chunkIndex>`（目录按 uploadID 隔离，文件名就是下标数字）；置 `UploadedBits[i] = true` → **回写会话** → 200 `{chunk_index}`
- 细节坑：算 MD5 用 `io.Copy(hash, f)` 后 reader 已读到尾，**重新落盘前要 `f.Seek(0, io.SeekStart)`**

**3. `chunk/status` —— 查进度（断点续传第二步）**
- 属主校验同上 → 返回 `{upload_id, uploaded_chunks, total_chunks}`，供前端/人工核对

**4. `chunk/complete` —— 校验齐全 → 合并 → 清理**
- 未齐 → 400 `{error: "not all chunks uploaded", missing: ≤5, completed, total}`
- 齐 → 终目录 `.run/uploads/videos/<accountID>/<20060102>/`，最终文件名 `randHex(16) + ".mp4"`（**扩展名写死 .mp4，不取 session.Filename 的扩展名**）
- 按 index **升序**逐片 `os.Open + io.Copy` 追加进最终文件；任何一片打开/拷贝失败 → 关句柄 + **`os.Remove(finalPath)` 删半成品** + 500（"要么完整要么没有"）
- 收尾：`os.RemoveAll(tmpDir)`、删 session key、删 hash 索引 key → 返回 `{url, play_url}`（绝对 URL）
- 注意：**complete 没有用 `session.FileHash` 复核合并结果**（file_hash 只当续传索引键）——这是原项目留的缺口，见进阶改进

### 客户端配合（原项目前端的调用顺序，验收时用 curl/Postman 等价模拟）

1. 本地切片（原前端 CHUNK_SIZE = 5MB，`total_chunks = ceil(size / 5MB)`）；
2. 用 spark-md5 算**整文件 MD5**（分 2MB 块读，避免整文件进内存）与**每片 MD5**；
3. `chunk/init` → 若返回的 `uploaded_chunks` 非空，过滤掉已传下标（并发 3、失败重试 3）；
4. `chunk/complete` 拿 play_url；
5. 最后才调 `publish` 落库——**上传和发布是两步**。

## 关键设计决策（动手前先回答自己）

**Q1：上传文件放哪、叫什么？** 本地磁盘：
- 直传视频 `.run/uploads/videos/<authorID>/<yyyyMMdd>/<randHex16>.mp4`，封面 `.run/uploads/covers/<authorID>/<yyyyMMdd>/<randHex16>.<ext>`（按作者+日期分目录，防单目录爆炸）
- 分片临时区 `.run/uploads/tmp/<uploadID>/<chunkIndex>`，合并后进 `videos/...`，tmp 整目录删除
- 大小白名单：视频 200MB、封面 10MB（`f.Size <= 0 || f.Size > maxSize`，位移写法 `200 << 20`）
- 扩展名白名单：`.mp4` / `.jpg .jpeg .png .webp`（`strings.ToLower(filepath.Ext(...))` 再比对）
- 文件名一律 `crypto/rand` 16 字节 hex——**绝不用用户原始文件名**（路径穿越/覆盖/特殊字符/重名全覆盖掉）

**Q2：返回给前端的 URL 是绝对还是相对？** 绝对：`scheme://host/static/...`。scheme 取 `TLS != nil → https`，再被 `X-Forwarded-Proto` 头覆盖（兼容反代）；host 用 `c.Request.Host`。路径拼接用 `path.Join`（URL 用 `/`，Windows 下 `filepath.Join` 会出 `\`）。

**Q3：校验放哪层？** 直传：handler 做文件大小/扩展名校验；publish 的 Service 层做 `TrimSpace` 后 title/play_url/cover_url 必填（description 可空）。分片：**没有 service 层**，handler 直接包揽会话管理（原项目如此），校验含属主（`session.AccountID != 本人 → 403`）、下标范围、逐片 MD5。

**Q4：publish 时 username 从哪来？** **JWT claims**：`jwt.GetUsername(c)`（登录/改名时签进 token 的），**不是查库**。注意原项目 `NewVideoHandler` 注入了 `accountService` 但整个 handler 一次都没用——死依赖，你复刻时可以删掉。代价与阶段 1 的 rename 设计呼应：改名后旧 token 里的 username 是旧的，所以 rename 会重签 token。

**Q5：为什么 Video 冗余存 username（反范式）？** Feed 输出每条视频都带作者名，冗余后列表查询零 join。代价：改名后旧视频显示旧名（原项目接受，且 rename 故意不回刷 videos 表）。

**Q6：分片会话存哪、key 怎么设计？** 两把 key，都带 24h TTL：
- `chunk_upload:<uploadID>` → 会话本体（JSON 序列化的 `ChunkUploadSession`）
- `chunk_upload_hash:<accountID>:<fileHash>` → `uploadID`（**续传索引**：按"用户 + 文件内容"定位会话，前端丢了 upload_id 也能恢复）
会话在 Redis 的好处：多实例共享、进程重启不丢、TTL 自动过期。uploadID = `randHex(16) + UnixNano`——随机 + 时间戳双保险防碰撞。

**Q7：有没有"秒传"？** **没有真秒传**。原项目的 hash 索引只做"**续传**"：同一用户同一文件 hash 命中未完成会话时返回已传列表，跳过已传分片；会话一旦 complete 就连 tmp 分片带两把 key 全删了，重传同文件仍要从头上。真秒传（文件已存在直接返回 play_url、零上传）见进阶改进。

**Q8：分片大小、总分片数谁说了算？** 客户端：切片、算整文件 MD5 和每片 MD5、报 `chunk_size/total_chunks`。服务端 `const ChunkSize = 5<<20` 只是参考值（原后端没人引用它，前端自己定了 5MB）。服务端只卡总大小 ≤200MB，**不校验 `chunk_size × total_chunks == file_size`**（恶意/出错声明会到 complete 缺片时才暴露）——缺口，进阶改进补。

**Q9：发布流程完整是什么？（事务 + 本地消息表）** handler 组装 `Video{AuthorID, Username, Title, Description, PlayURL, CoverURL, CreateTime: time.Now()}` → `service.Publish` 开**一个事务**：① `tx.Create(video)`；② 写 `OutboxMsg{VideoID, EventType: "video_published", Status: "pending", CreateTime: video.CreateTime}`（保证"视频入库"和"发消息"原子——阶段 9 的 poller 才消费）；③ `ExtractTags(Title + " " + Description)` 逐个 `FirstOrCreate` Tag + 创建 VideoTag 关联。任何一步失败整体回滚。

**Q10：静态服务怎么配？** `r.Static("/static", "./.run/uploads")`（router 里还有 `SetTrustedProxies(nil)`）。play_url/cover_url 存的就是这套绝对 URL，前端拿到即用。

## 难点清单（本阶段真正难的地方）

1. **分片上传的状态机**：`UploadedBits []bool` 是唯一事实来源，但"位图在 Redis/内存、分片文件在磁盘"是**两个存储**。推演顺序：为什么先落盘再置位？置位后 saveSession 失败会怎样？（答：位图落后于磁盘，下次重传该片，幂等分支 200 兜底，不丢数据）；反过来先置位呢？（位图领先于磁盘，complete 合并时缺文件直接 500）
2. **断点续传闭环**：hash 索引 → init 返回旧 upload_id + 已传列表 → status 核对 → 客户端跳过已传 → complete。四环缺一不可。还要推演边界：会话 TTL 过期后 hash 索引可能还活着——原项目 getSession 失败就当全新上传（索引值指向已死的会话 = 自然失效）
3. **文件校验链**：逐片 MD5 校验防传输损坏（错误响应带 expected/actual）；整文件 file_hash **只当续传索引、complete 不复核合并结果**；扩展名白名单只在直传接口存在，分片 complete 直接写死 `.mp4`。把"哪层校验了什么、什么没校验"列成表
4. **合并的顺序性与失败清理**：分片按 index 升序拼接（客户端切片顺序即字节序）；任一片失败必须 `os.Remove(finalPath)`——不能给用户留下能访问的半个视频
5. **并发与幂等**：前端并发 3 片上传 → 同一会话的"读-改-写"存在竞态（原项目没加锁，靠重复上传幂等 + 最后一次 saveSession 兜底）；同片重传直接 200 是幂等关键
6. **发布事务的一致性**：video + outbox + tag×N 同事务；`ExtractTags` 去重避免重复关联；service 直接摸 `repo.db` 私有字段的分层妥协要心里有数
7. **直传安全三件套 + URL 拼接**：大小/扩展名/随机文件名，`MkdirAll` 先行，磁盘路径 `filepath.Join` 与 URL 路径 `path.Join` 分开

## 亮点（原项目在视频模块的工程亮点）

- **分片上传整套设计**：init（建会话+续传判断）/ upload（逐片校验+幂等）/ status（进度）/ complete（合并+清理），与商用网盘/object storage 分片协议同构，是本项目最有"生产味"的部分
- **hash 索引按"用户+文件内容"定位会话**：前端丢了 upload_id 也能续传（重新 init 即可），断点续传体验闭环
- **逐片 MD5 校验且错误响应带 expected/actual**：传输损坏立刻定位是哪一片、实际算出什么
- **complete 的失败回滚 + 全套清理**：删半成品文件、删 tmp 目录、删会话与索引 key，不留垃圾
- **随机文件名防覆盖/防猜测**：`randHex(16)`，uploadID 还追加 UnixNano 双保险；配合按作者/日期分目录
- **本地消息表（Outbox）雏形**：publish 事务内同写 `video_published` 事件，为阶段 9 的"库和消息最终一致"埋好桩
- **miniredis 单测**：`chunk_handler_test.go` 6 个用例（全流程/断点续传/幂等重传/哈希不匹配/缺片合并/进度查询）——**现成的验收脚本**，直接照抄思路
- **为后续预埋的复合索引**：Feed 与热榜的排序查询直接受益，避免阶段 3/8 再改表

## 常见的坑

- `chunk/upload` 是 multipart，用 `ShouldBindJSON` 会一直绑定失败；字段 tag 是 `form` 不是 `json`
- 分片 MD5 用 `io.Copy` 算完后 reader 已到尾 → 落盘前**必须 `Seek(0)`**，否则存下 0 字节分片
- `path.Join`（URL 用 `/`）和 `filepath.Join`（磁盘路径，Windows 是 `\`）别混用
- `.run/uploads` 子目录不存在时 `SaveUploadedFile`/`os.Create` 失败 → `os.MkdirAll(absDir, 0o755)` 一定要先做
- `file_size` 用 `binding:"required,min=1"`：不传或传 0 直接 400；总大小用 `200 << 20` 位移写法（10 << 20 = 10MB 同理）
- session TTL 24h：过期后 tmp 分片成磁盘孤儿（原项目无清理任务）→ 进阶改进
- Redis 挂了分片四接口 503（原项目行为）；阶段 7 之后可再思考降级方案
- complete 的最终扩展名写死 `.mp4`：将来支持其他格式时记得改这里（直传接口是白名单走扩展名的，两处逻辑不对称）
- `gorm:"autoCreateTime"` 只对零值时间生效；handler 里手动 `CreateTime: time.Now()` 也行（原项目两者都配了，二选一即可）
- `ListByAuthorID` 的参数是 `int64`、别处是 `uint`——原项目的小别扭，照抄或统一均可，但别让 GORM 静默类型转换坑你
- publish 缺 title/play_url/cover_url 是 **400**（service 校验）；绑定失败也走 `apierror.ClassifyHTTPStatus`
- `Description` 的 gorm tag 末尾带分号 `type:varchar(255);`——原项目原样，无实际影响
- nginx 反代时 `client_max_body_size` 要 ≥ 分片大小（5MB）甚至 200MB（直传），否则 413
- `.run/` 一定要进 `.gitignore`（上传的文件不进版本库）
