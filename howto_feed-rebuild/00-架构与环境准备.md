# 00 - 架构总览 与 阶段0：项目骨架

## 全局架构（先刻在脑子里）

```
                        start.sh（一键编排：依赖容器 + 两个 Go 进程 + 前端）
                                              │
        ┌─────────────────────────────────────┴─────────────────────────────────────┐
        │                                                                           │
        ▼                                                                           ▼
┌───────────────────────────────────┐                       ┌───────────────────────────────────┐
│  API 进程  (backend/cmd/main.go)   │                       │  Worker 进程 (backend/cmd/worker)  │
│  godotenv → config → MySQL(必选)   │                       │  config → MySQL(带重试)            │
│  → AutoMigrate → Redis(可选降级)    │                       │  → Redis(可选降级)                 │
│  → RabbitMQ(可选降级) → pprof:6060 │                       │  → RabbitMQ(带重试) → pprof:6061   │
│  → Gin 路由 :8080                  │                       │  声明 4 组拓扑 → 4 个 Worker 消费   │
│  Handler → Service → Repo          │                       │  SocialWorker ──► MySQL           │
└──────┬───────────┬──────────┬─────┘                       │  LikeWorker   ──► MySQL           │
       │           │          │ topic 消息                   │  CommentWorker──► MySQL           │
       ▼           ▼          ▼                             │  PopularityWorker──► Redis(热度)   │
  MySQL(必选)  Redis(可选)  RabbitMQ(可选) ─────────────────► └───────────────────────────────────┘
```

两个进程、一份配置、一个脚本：

- **API 进程**：职责是低延迟响应 HTTP 请求，重活（批量落库、热度计算）全部丢给 MQ
- **Worker 进程**：独立消费 4 条 topic 事件链路（social / like / comment / video.popularity），独立伸缩、独立重启，互不影响
- **start.sh**：把"依赖容器 + Redis + API + Worker + 前端"一条命令拉起，Ctrl+C 全部回收

三条贯穿全程的**降级哲学**（这是本项目最大的工程特色，下面只给结论，"亮点"一节重点展开）：

1. **启动时降级**：Redis/RabbitMQ 连不上 → 置 `nil`，日志提示后继续启动，功能整体禁用
2. **运行时按目标降级**：发 MQ 失败 → 只对失败的目标（MySQL 或 Redis）直接写
3. **请求级降级**：单个 Redis 命令失败 → 回源 MySQL，缓存操作一律 50ms 超时不阻塞主请求

## 阶段 0 目标

把**启动链路**一步到位搭完整（不是只搭一个最小 Gin）：

1. `godotenv` 读 `.env`（读不到只记日志，继续跑）
2. `CONFIG_PATH`（默认 `configs/config.yaml`）加载配置；**文件不存在则用内置默认配置兜底**
3. 所有配置项支持**环境变量覆盖**
4. 连 MySQL（必选，失败 `log.Fatalf`）→ GORM `AutoMigrate` 自动建表
5. 连 Redis：**可选降级**——300ms 超时 Ping，失败置 `nil` 继续启动
6. 连 RabbitMQ：**可选降级**——失败置 `nil` 继续启动
7. 起 pprof（可观测性，可开关，API/Worker 分端口）
8. 挂路由（阶段 0 只有 `/healthz`）→ Gin 起服务

**不写任何业务。** 但"可选降级"这个灵魂从阶段 0 就要长在骨架里：Redis/MQ 的业务方法阶段 7/9 才回填，构造 + Ping + Close 这十几行现在就写，`main.go` 从第一天起就和原项目一个样。

### 1. 配置模块 `internal/config/loadconfig.go`

五个配置段 + 四个函数，yaml tag 全小写：

```go
type Config struct {
    Server              ServerConfig        `yaml:"server"`        // Port int
    Database            DatabaseConfig      `yaml:"database"`      // Host/Port/User/Password/DBName
    Redis               RedisConfig         `yaml:"redis"`         // Host/Port/Password/DB
    RabbitMQ            RabbitMQConfig      `yaml:"rabbitmq"`      // Host/Port/Username/Password

type ObservabilityConfig struct {
    Pprof PprofConfig `yaml:"pprof"`
}
type PprofConfig struct {
    Enabled    bool   `yaml:"enabled"`
    ApiAddr    string `yaml:"api_addr"`     // API 进程的 pprof 监听地址，如 localhost:6060
    WorkerAddr string `yaml:"worker_addr"`  // Worker 进程的，如 localhost:6061
}
```

四个函数（**代码由你写**，签名和语义如下）：

```go
// 读文件 + yaml.Unmarshal + 环境变量覆盖。
// 注意：读文件的错误必须用 %w 包装返回 —— LoadLocalDev 靠 errors.Is(err, os.ErrNotExist) 判断"文件不存在"。
func Load(filename string) (Config, error)

// 环境变量覆盖 yaml 值：只覆盖"非空"的环境变量；数字字段 strconv.Atoi 失败则保留 yaml 原值，不报错（fail-safe）。
func ApplyEnvOverrides(cfg *Config)

// Load 的开发友好包装：文件不存在 → 返回 DefaultLocalConfig() 且 usedDefault=true；
// 其他错误（比如 yaml 语法错）原样返回 err —— 语法错不能静默兜底！
func LoadLocalDev(filename string) (Config, bool, error)

// 硬编码的本地默认值，最后再调一次 ApplyEnvOverrides 让环境变量仍然生效：
//   Server.Port=8080
//   Database: localhost:3306 root/123456/feedsystem
//   Redis:    localhost:6379 123456 db=0
//   RabbitMQ: localhost:5672 admin/password123
//   Pprof:    enabled=true, api_addr=localhost:6060, worker_addr=localhost:6061
func DefaultLocalConfig() Config
```

`ApplyEnvOverrides` 的**完整环境变量清单**（一个不落）：

| 环境变量 | 覆盖目标 |
|---|---|
| `SERVER_PORT` | `Server.Port`（Atoi） |
| `MYSQL_HOST` / `MYSQL_PORT` / `MYSQL_USER` / `MYSQL_DATABASE` | `Database.Host` / `.Port` / `.User` / `.DBName` |
| `MYSQL_ROOT_PASSWORD`、`MYSQL_PASSWORD` | 都写 `Database.Password`。**两个都设时，后处理的 `MYSQL_PASSWORD` 会覆盖前者**——原项目的真实行为，知道即可 |

| `RABBITMQ_HOST` / `RABBITMQ_PORT` / `RABBITMQ_USER` / `RABBITMQ_PASS` | `RabbitMQ.Host` / `.Port` / `.Username` / `.Password` |

### 4. API 入口 `cmd/main.go`（完整链路）

原项目的启动顺序，一步不落：

1. `godotenv.Load()`（失败仅记日志）
2. `configPath := os.Getenv("CONFIG_PATH")`，空则 `"configs/config.yaml"`
3. `config.LoadLocalDev(configPath)` → 按 `usedDefault` 打不同的日志（"using default local config" vs "Config loaded from file"）
4. `db.NewDB(cfg.Database)` → **失败 `log.Fatalf`（必选）** → `db.AutoMigrate` → `defer db.CloseDB`
5. Redis 可选降级块（阶段 0 就写好）：

```go
cache, err := rediscache.NewFromEnv(&cfg.Redis)
if err != nil {
    log.Printf("Redis config error (cache disabled): %v", err)
    cache = nil
} else {
    pingCtx, cancel := context.WithTimeout(context.Background(), 300*time.Millisecond)
    defer cancel()
    if err := cache.Ping(pingCtx); err != nil {
        log.Printf("Redis not available (cache disabled): %v", err)
        _ = cache.Close()   // 立刻关掉，不要再 defer
        cache = nil         // ★ 降级的核心：置 nil
    } else {
        defer cache.Close() // 成功路径才 defer
        log.Printf("Redis connected (cache enabled)")
    }
}
```

   > 为什么 Ping 要 300ms 超时？go-redis 客户端是惰性连接，`NewClient` 不会因为 Redis 没起而报错；真正的"活没活"必须主动 Ping，且不能让它默认 5s 超时拖慢启动。
6. RabbitMQ 可选降级块（结构同上，`rabbitmq.NewRabbitMQ(&cfg.RabbitMQ)`，成功 `defer rmq.Close()`，失败 `rmq = nil`）——**API 进程里 MQ 是可选的**，发不出去有直写兜底（阶段 9）
7. pprof：`observability.NewPprofServer("API", cfg.ObservabilityConfig.Pprof.Enabled, cfg.ObservabilityConfig.Pprof.ApiAddr)`，非 nil 则 `defer Close`
8. `apphttp.SetRouter(sqlDB, cache, rmq)` —— 依赖注入就这一个入口：new Repo → new Service → new Handler → 挂路由（阶段 0 只挂 `/healthz`）
9. `r.Run(":" + strconv.Itoa(cfg.Server.Port))`，失败 `log.Fatalf`；`Run` 阻塞，所有 defer 在进程退出时执行

### 5. Worker 入口 `cmd/worker/main.go`（阶段 9 建，现在读懂）

与 API 进程的四个不同点，决定了它是另一种生物：

1. **依赖全带重试**：`connectWithRetry(name, 10, fn)` —— 指数退避 `1<<i` 秒、封顶 30s，10 次后 `log.Fatalf`。Worker 是后台进程，不依赖 compose 的 healthcheck 等待，自己等依赖起来
2. **启动先声明 MQ 拓扑**：4 组常量 + 4 个 `declareXxxTopology(ch)`（阶段 0 只需知道格式）：

   | exchange / queue | binding key |
   |---|---|
   | `social.events` | `social.*` |
   | `like.events` | `like.*` |
   | `comment.events` | `comment.*` |
   | `video.popularity.events` | `video.popularity.*` |

   queue 都声明为持久化，并带参数 `amqp.Table{"x-dead-letter-exchange": mqrabbit.DLXExchange}`（死信交换机，阶段 9 展开）；**popularity 拓扑只在 `cache != nil` 时声明**——Redis 没起，PopularityWorker 压根不会存在
3. **每个 Worker 一个 goroutine + 独立 Channel + 自动重连**：`runWorkerWithRetry(ctx, name, conn, fn)` —— `conn.Channel()` 失败 5s 重试；`ch.Qos(50, 0, false)` 控制预取（忘 Qos = MQ 把上千条消息推给一个 Worker，内存爆掉）；`fn(ch)` 返回错误且 ctx 未取消 → 5s 后重连
4. **优雅退出**：`signal.NotifyContext(context.Background(), os.Interrupt, syscall.SIGTERM)`；`<-ctx.Done()` 后 `time.Sleep(2 * time.Second)` 给在处理的消息收尾

组装顺序：config → MySQL(重试) → Redis(可选，降级则 PopularityWorker 不起) → RabbitMQ(重试) → 声明拓扑 → new 4 个 repo（`social.NewSocialRepository`、`video.NewVideoRepository` / `NewLikeRepository` / `NewCommentRepository`）→ pprof("Worker", …WorkerAddr) → 4 个 goroutine 跑 `worker.NewXxxWorker(ch, …, queueName).Run(ctx)` → 等待退出信号。

### 6. start.sh（阶段 10 前补，先了解开关）

环境变量全是开关，默认全 1：`START_REDIS` / `START_RABBITMQ` / `START_BACKEND` / `START_WORKER` / `START_FRONTEND` / `STOP_DOCKER`（退出时是否停 compose）。几个值得抄的细节：

- `CONFIG_PATH` 未显式指定且要起 RabbitMQ → 自动切 `configs/config.compose-local.yaml`（因为 compose 把 MySQL 映射到 3307）
- RabbitMQ 起来后用 `rabbitmq-diagnostics -q ping` 探测就绪，最多 30 次、每次 1s；Redis 先 `redis-cli ping` 探测，已在跑就跳过
- 后台进程 PID 写进 `.run/`（这个目录同时也是上传文件的根，路由 `r.Static("/static", "./.run/uploads")`）
- `trap cleanup INT TERM EXIT` 统一回收；**Windows Git Bash 下子进程可能收不到信号，用 `taskkill //PID x //T //F` 兜底**（原项目真实代码，说明作者真在 Windows 上跑过）
- 结尾 `wait` 等所有后台进程，Ctrl+C 全家桶一起退

## 关键设计决策（动手前先想）

| 问题 | 原项目的答案 | 你要不要跟 |
|---|---|---|
| 配置返回值还是指针？ | 值 `(Config, error)`，上层取地址传参 | 均可 |
| 配置文件不存在怎么办？ | `LoadLocalDev` 兜底 `DefaultLocalConfig()`，但 yaml **语法错**照样报错 | 跟（"缺文件能跑、坏文件必须报错"是两条红线） |
| 环境变量怎么进配置？ | 手写 `ApplyEnvOverrides`，一个变量一段 if（进阶可换 viper） | 跟，先体会手写的直白 |
| 缺 `.env` 怎么办？ | `godotenv.Load()` 失败仅记日志，继续跑 | 跟 |
| 建表方式 | AutoMigrate（开发友好；生产应换 SQL 迁移） | 跟 |
| MySQL 时区 | DSN `loc=Local` + 容器 `TZ=Asia/Shanghai` | 跟，否则时间差 8 小时 |
| Redis/MQ 连不上？ | **不 Fatal，置 nil 继续启动**（API 进程）；Worker 的 MySQL/MQ 才重试后 Fatal | **必须跟**，这是全项目骨架的基调 |
| pprof 开关 | yaml `enabled` 控制；`config.docker.yaml` 里关掉；API 6060 / Worker 6061 分端口 | 跟 |
| 两个进程 vs 一个进程 | API 与 Worker 分开：低延迟响应与重活隔离，独立伸缩/重启 | 跟 |

## 常见的坑

- 忘 `parseTime=True` → `sql.Scan` 报错，报错信息完全不指向这里
- `go run cmd/main.go` 和 `go run ./cmd` 不一样：后者才是包方式运行
- **配置路径相对进程工作目录**：必须 `cd backend && go run ./cmd`（原项目 start.sh 就是这么做的），否则 `configs/config.yaml` 找不到——找不到会静默走默认配置，MySQL 端口变成 3306，然后你会去查数据库为什么连不上，兜底太"好用"也是坑
- 3307 端口写成 3306 → 连接拒绝（本机若装有 MySQL 极易踩）
- yaml 值里 `123456` 不加引号可能被解析成八进制/其他类型，密码类一律加引号
- `LoadLocalDev` 兜底返回后忘了给 `usedDefault` 打日志 → 以为读到了配置，其实全是默认值
- `ApplyEnvOverrides` 里数字字段直接 `cfg.Server.Port = v` 编译不过/类型错；必须 `strconv.Atoi` 且失败时**保留原值**而不是报错
- Redis 降级分支里既 `_ = cache.Close()` 又 `defer cache.Close()` → double close；二选一
- `MYSQL_ROOT_PASSWORD` 和 `MYSQL_PASSWORD` 同时设置时后者生效，排查密码问题时容易被第一个骗
- `JWT_SECRET` 不设：本地能跑（随机生成），但重启后所有 token 失效、多副本 token 互不认账

## 难点清单

阶段 0 真正费脑子的地方，动手前逐条想清楚：

1. **`Load` 的错误包装决定 `LoadLocalDev` 的正确性**：`fmt.Errorf("...: %w", err)` 才能让上层 `errors.Is(err, os.ErrNotExist)` 成立。换成 `fmt.Errorf("...: %v", err)`，兜底逻辑就永远不触发——这是 `%w` 和 `%v` 最实际的一课
2. **"缺文件"与"坏文件"分家**：`os.ErrNotExist` → 静默兜底默认配置；yaml 语法错 → 原样返回 error。写反了（语法错也兜底）会排查到怀疑人生
3. **`ApplyEnvOverrides` 的 fail-safe 语义**：环境变量是"建议"不是"命令"——非空才覆盖、Atoi 失败保留原值。想清楚为什么这里不报错（环境变量来自部署环境，解析失败不该让服务起不来）
4. **nil 作为"禁用"标记贯穿全项目**：`cache`/`rmq` 为 nil 表示功能整体禁用，所有使用方必须判 nil。配套技巧是 nil-receiver 安全方法——原项目 redis 客户端的 `Close/Ping/Key` 都写了 `if c == nil { … }`，nil 调用不炸
5. **`NewPprofServer` 的 `(nil, nil)` 约定**：disabled 不是错误。Go 里用"双 nil 返回值"表达"没这东西但一切正常"，调用方要双重判 nil（err 和指针各判一次）
6. **降级分支的资源对称**：成功路径 `defer Close()`，降级路径立刻 `Close()`。漏掉降级分支的 Close，Ping 失败的连接会挂着
7. **go-redis 惰性连接**：`NewClient` 永远"成功"，可用性必须靠带超时的 Ping 主动验证——300ms 这个数字是"启动快"和"误判率"的折中
8. **Worker 的双层重试要分开想**：连接级（`connectWithRetry`，起进程时指数退避）和 channel 级（`runWorkerWithRetry`，运行中断线 5s 重连）作用在不同层，混在一起写就乱了
9. **优雅退出链**：`signal.NotifyContext` 把信号变成 ctx 取消 → 每个 worker 的 `Run(ctx)` 感知退出 → main 再 `sleep 2s` 收尾。三段缺一不可

## 亮点

**降级哲学三条**（本项目最大的工程特色，从这里开始贯穿每一个阶段）：

| # | 名字 | 代码位置 | 具体行为 | 为什么是亮点 |
|---|---|---|---|---|
| 1 | 启动时降级 | `cmd/main.go` Redis/MQ 两个连接块 | 配置错或 Ping 失败 → 打一行日志、置 nil、**服务照常启动**；缓存功能整体禁用，所有请求走 MySQL | 面试常问"Redis 挂了系统会怎样"，这里的答案是"启动都不受影响"。可用性优先于功能完整性 |
| 2 | 运行时按目标降级 | 阶段 9：`middleware/rabbitmq` 发布失败分支 | 发 MQ 失败 → 只对失败的那个目标直接写（该写 MySQL 的直写 MySQL，该更新热度的直写 Redis），其他目标照常 | 降级粒度到"目标"而不是"接口"，接口不会因为 MQ 抖动整体 500 |
| 3 | 请求级降级 | 阶段 7：`middleware/redis` | 每个缓存操作带 50ms 超时，失败/超时 → 回源 MySQL，对用户无感 | 单条命令失败不放大成请求失败；50ms 是"缓存快不过 MySQL 太多就没意义"的取舍 |

三条合起来是一个信念：**缓存和 MQ 都是加速器，不是依赖**。MySQL 才是唯一的真相源。

其他亮点（阶段 0 就能看到全貌的）：

- **零配置可跑**：`LoadLocalDev` + `DefaultLocalConfig`，clone 下来 `go run ./cmd` 就能起，连 config.yaml 都不用写；但写错了配置绝不会静默吞掉
- **一份配置适配三种环境**：三份 yaml 只差 host/端口/pprof 开关，加上 env 覆盖，dev / compose-local / docker 全覆盖，代码零修改
- **pprof 内建且可开关**：独立小包 50 行，API/Worker 分端口，容器环境一键关掉；性能问题随时能抓火焰图，而不是出了问题再补埋点
- **双进程架构**：API 进程里 MQ 是可选的（发不出去有直写兜底），Worker 进程里 MQ 是命根子（重试 10 次后 Fatal）。同一个 MQ，两个进程态度完全不同——按各自职责定依赖等级
- **Worker 韧性是分层的**：进程启动时连接重试（等依赖就绪），运行中 channel 重连（扛 MQ 抖动），Qos 50 控制背压
- **优雅退出**：Ctrl+C → ctx 取消 → worker 收尾 → 2s 缓冲，`docker stop` 也能干净退出
- **start.sh 的一键体验**：五个开关自由组合，就绪探测、PID 管理、Windows 兼容兜底，一个脚本跑全链路
