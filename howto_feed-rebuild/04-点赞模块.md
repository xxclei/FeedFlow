# 04 - 点赞模块（Like）【全量版】

前置：阶段 3。第一个"写热点"模块——**并发下的计数一致性 + 幂等**，也是阶段 9 异步化的地基。这段直写代码现在写的不是废代码，阶段 9 它会原封不动变成"MQ 发布失败时的降级路径"。

> **对齐原则（全程适用）**：最终产出 = 原项目全部功能。本阶段把 4 个接口 + Like 表 + 计数维护 + Feed 回填全部做到位；`cache` / `likeMQ` / `popularityMQ` 三个依赖先传 `nil`（阶段 7/8/9 回填），归属见文末"后续阶段回填清单"。

## 目标

- 点赞 / 取消点赞：写 `likes` 表流水 + 维护 `videos.likes_count` 与 `videos.popularity`
- 判断是否点赞（`isLiked`）、我的点赞列表（`listMyLikedVideos`）
- 补齐阶段 3 留的口子：`BatchGetLiked` 让 Feed 的 `is_liked` 从假变真
- 建立"预检 + 唯一索引"双层幂等防御，为阶段 9 Worker 的 at-least-once 消费铺路

## 接口设计

4 个接口全部挂在 JWT 强鉴权分组下（`jwt.JWTAuth`），accountID 一律从 token 取，**请求体里没有 account_id**（防伪造）。

| 路由 | 鉴权 | 限流(阶段7回填) | 请求 → 响应 |
|---|---|---|---|
| POST /like/like | JWT | 30次/分/账号 | `{video_id}` → `{"message": "like success"}` |
| POST /like/unlike | JWT | 30次/分/账号 | `{video_id}` → `{"message": "unlike success"}` |
| POST /like/isLiked | JWT | - | `{video_id}` → `{"is_liked": true}` |
| POST /like/listMyLikedVideos | JWT | - | **无请求体** → `[Video...]`（空时 `[]` 不是 null） |

错误响应（原项目无统一 wrapper，业务错误统一 500 `{"error": "..."}`，只有参数问题返回 400）：

| 场景 | 状态码 | error |
|---|---|---|
| `video_id` 缺失或 <= 0 | 400 | `video_id is required` |
| 视频不存在 | 500 | `video not found` |
| 重复点赞（预检或 1062 命中） | 500 | `user has liked this video` |
| 未点赞就 unlike | 500 | `user has not liked this video` |
| like/unlike 里 `like` 为 nil 或 ID 为 0 | 500 | `video_id and account_id are required` |

注意两个产品行为：`isLiked` 对**不存在的视频返回 `{"is_liked": false}` 而不报错**（service 直接透传 Count 查询）；`listMyLikedVideos` 返回的是完整 `Video` 对象数组（带 `likes_count`、`popularity`），不是 Like 记录。

## 数据模型

```go
type Like struct {
    ID        uint      `gorm:"primaryKey" json:"id"`
    VideoID   uint      `gorm:"uniqueIndex:idx_like_video_account;not null" json:"video_id"`
    AccountID uint      `gorm:"uniqueIndex:idx_like_video_account;not null" json:"account_id"`
    CreatedAt time.Time `json:"created_at"`
}

type LikeRequest struct {
    VideoID uint `json:"video_id"`
}
```

- 表名 GORM 默认复数 `likes`；**复合唯一索引 `(video_id, account_id)` 是本模块的基石**——数据库层面保证一人一赞，幂等兜底全靠它（索引名 `idx_like_video_account`，video_id 在前）。写完去 `show index from likes` 确认。
- `CreatedAt` 用点赞时刻填充（service 里 `time.Now()` 显式赋值），它是"我的点赞列表"的排序依据。
- 计数不在 Like 表里，而是冗余在 `videos` 表（阶段 2 已建列）：`likes_count int64 not null default 0`、`popularity int64 not null default 0`。**likes 表是流水（真相源），计数是可重建的冗余值**——这个分离是亮点，见下文。

## 关键设计决策（动手前先回答自己）

**Q1：怎么保证不重复点赞？** 双层防御，缺一不可：
1. **Service 先 `IsLiked` 预检**——挡住 99% 的重复请求，给用户友好报错 `"user has liked this video"`；
2. **唯一索引兜底**——预检和插入之间有时间窗，并发双击时两个请求都能过预检，但第二个 INSERT 必撞 1062，捕获后翻译成同样的业务错误。

判断 1062 的标准姿势（service 里有 `isDupKey` 帮助函数，repo 里有 `LikeIgnoreDuplicate`）：

```go
var me *mysql.MySQLError
return errors.As(err, &me) && me.Number == 1062   // 不是 err.Error() 字符串匹配
```

**Q2：计数怎么加？（并发点赞不丢数的核心）** **绝不允许**"读出 likes_count → 内存 +1 → 写回"，也不允许 `SET likes_count = ?` 传算好的绝对值——两个并发请求都读到 5，都写 6，丢一次更新。唯一正确写法是**相对更新的原子 SQL**：

```go
// Like 方向：+1 不会变负，不加 GREATEST
UpdateColumn("likes_count", gorm.Expr("likes_count + 1"))
// Unlike 方向：重复扣减/竞态可能打穿 0，必须夹住下限
UpdateColumn("likes_count", gorm.Expr("GREATEST(likes_count - 1, 0)"))
```

`UPDATE ... SET x = x + 1` 是单条 SQL，InnoDB 对同一行的 UPDATE 由行锁串行化，N 个并发 +1 结果一定是 +N。`UpdateColumn` 纯改列、不走 GORM 钩子。注意**原项目这个 GREATEST 是不对称的**：Like 直写里没有、Unlike 直写里有——因为只有减法才可能把 0 打成负数。

**Q3：插入流水和更新计数要不要同一事务？** 要。`db.Transaction` 里"INSERT likes + UPDATE 计数 + UPDATE popularity"同生共死：插入成功但计数失败会回滚，绝不出现"点赞记录在、计数没加"的漂移。

**Q4：unlike 时怎么知道计数该不该减？** 靠 `Delete` 的 `RowsAffected`：**删到行才减计数**，删 0 行（本来就没点过）直接报错回滚，计数分毫不动。阶段 9 Worker 的幂等是同款套路（`DeleteByVideoAndAccount` 返回 `deleted bool`），现在就养成"先确认副作用真的发生了，再改计数"的习惯。

**Q5：popularity 也要跟着动吗？** 要（热度 = 互动信号，点赞 +1 / 取消 -1，同样在事务里 `GREATEST(popularity ± 1, 0)`）。阶段 8 之前它只写 MySQL 这一列；阶段 8 会加"同步失效 Redis 详情缓存 + 分钟桶 ZincrBy"（`UpdatePopularityCache`，阶段 4 先写 nil-guard 占位）。

**Q6：我的点赞列表怎么查、按什么排？** likes 表 JOIN videos，**按点赞时间倒序**，并且 `Limit(200)` 兜底防一次拉爆：

```sql
SELECT videos.* FROM videos
JOIN likes ON likes.video_id = videos.id
WHERE likes.account_id = ?
ORDER BY likes.created_at DESC
LIMIT 200
```

**Q7：Feed 的 is_liked 怎么批量查（阶段 3 留的口子）？** 一次 `WHERE video_id IN ? AND account_id = ?` 查成 map，绝不逐条查（N+1）。`accountID == 0`（匿名）或 ids 为空 → 直接返回空 map（匿名视角全部 false）。

为什么传 nil 是安全的：service 里所有用到这三个依赖的地方都有 nil 判断（`if s.likeMQ != nil`、`if s.popularityMQ != nil`、`UpdatePopularityCache` 里 `if cache == nil return`）。阶段 4 的行为因此自然退化为"永远走直写事务分支"。推荐**本阶段只写直写事务、不写 MQ 分支**（少写一遍死代码），阶段 9 再插 MQ 优先逻辑；想一步到位按最终结构写也行，nil 判断会自动跳过。

**Like 的直写事务骨架**（本阶段主体，就是阶段 9 的降级代码）：

```
Like(ctx, like):
  1. 校验 like != nil、VideoID/AccountID != 0
  2. VideoRepo.IsExist(videoID)          → 不存在 → "video not found"
  3. repo.IsLiked 预检                    → 已赞 → "user has liked this video"
  4. like.CreatedAt = time.Now()
  5. db.Transaction:
       SELECT id FROM videos WHERE id=?   → 再查一次存在性，ErrRecordNotFound → "video not found"
       INSERT INTO likes (...)            → isDupKey(err) → "user has liked this video"（回滚）
       UPDATE likes_count = likes_count + 1   （gorm.Expr，无 GREATEST）
       UPDATE popularity  = popularity + 1    （gorm.Expr，无 GREATEST）

Unlike(ctx, like):
  1-2. 同上（IsExist + IsLiked 预检，!isLiked → "user has not liked this video"）
  3. db.Transaction:
       DELETE FROM likes WHERE video_id=? AND account_id=?
       RowsAffected == 0 → "user has not liked this video"（回滚，计数不动）
       UPDATE likes_count = GREATEST(likes_count - 1, 0)
       UPDATE popularity  = GREATEST(popularity - 1, 0)
```

事务内第 5 步的"再查一次视频存在性"和事务外的 IsExist 看似重复——事务内那次才是保住数据一致的那次（预检只是体验优化），这个"预检只是体验、约束才是防线"的思想贯穿全项目。

原项目 service 里计数更新是通过 `s.repo.db` 直接拿 gorm.DB 开事务做的（repo 没有暴露 ChangeLikesCount 方法）——能跑，但分层不干净，你可以在 repo 补 `ChangeLikesCount/ChangePopularity`（见进阶改进）。

**Handler 要点**：四个 handler 模式一致——`ShouldBindJSON` 失败或 `req.VideoID <= 0` → 400 `"video_id is required"`（`listMyLikedVideos` **无请求体、不 bind**）→ `jwt.GetAccountID(c)` 取身份 → 调 service 传 `c.Request.Context()` → 失败 500 `{"error"}`，成功按接口表返回。`ListMyLikedVideos` 记得 `videos == nil` 时转 `[]Video{}`，否则空列表会序列化成 `null`。

## 难点清单（本阶段真正难的地方）

1. **点赞计数一致性（并发不丢数）**：三种写法只有一种是错的？——读出加一写回、`SET x = 绝对值` 都丢更新，`SET x = x + 1` 靠行锁串行才对。理解"InnoDB 单行 UPDATE 是原子的、gorm.Expr 是参数化的相对更新"这半页知识，比多写三个模块都值钱。
2. **双层幂等防御的边界推演**：预检通过 → 插入前进程被并发请求插入 → 1062 → 回滚整个事务（计数一条都不会加）。画时间线推一遍：为什么事务回滚保证了"撞键时计数绝对不动"。
3. **GREATEST 的不对称**：+1 不夹、-1 必夹。想清楚"哪种操作可能把计数打穿 0"（重复 unlike、MQ 重复投递），别机械对称。
4. **RowsAffected 语义**：`Delete` 删 0 行不是错误、也不该减计数；`RowsAffected == 0 → 报错回滚`这个判断少写，unlike 竞态下计数会莫名变少。
5. **批量视角与个体视角的统一**：`IsLiked`（单条 Count）和 `BatchGetLiked`（IN 批查成 map）语义必须一致——一条 0/1、一批 true/false 集合，Feed 页面才不会"列表说没点、点进去说点了"。

## 亮点（原项目在点赞模块的工程亮点）

- **唯一键幂等**：`LikeIgnoreDuplicate` / `DeleteByVideoAndAccount` 把"这条副作用到底有没有发生"折叠成一个 `created/deleted bool` 返回值——阶段 9 Worker 在 at-least-once 重复投递下不重复计数，全靠这两个签名设计（幂等能力是提前一个阶段埋好的）。
- **计数与流水分离**：`likes` 表是"谁在什么时候点了什么"的真相源，`videos.likes_count` 只是可随时由流水重算的冗余计数。计数错了有得救（重算），流水丢了才叫丢数据。
- **预检 + 约束双层防御**：预检为用户体验，唯一索引为数据正确性，两层的失败路径最终收敛为同一条业务错误信息。
- **`GREATEST` 下限夹逼**：一行表达式防住负计数，配合索引 `idx_videos_likes_count_id` 保证点赞流游标分页（阶段 3）永远拿到合法值。
- **`BatchGetLiked` 批量化**：把 Feed 每页几十条视频的 is_liked 收敛成一次 IN 查询，N+1 杀手。
- **`listMyLikedVideos` 的 `Limit(200)`**：无游标接口的兜底上限，防全表 JOIN 拉爆。

## 常见的坑

- 唯一索引建反/没建 → 并发测试重复计数；写完 `show index from likes` 确认两列都在 `idx_like_video_account` 里
- `gorm.Expr` 里变更量必须参数化（`likes_count + ?` 或写死字面量均可），别用 `fmt.Sprintf` 拼 SQL
- 预检和插入之间有时间窗，单靠预检挡不住并发双击——1062 分支必写，且判断用 `errors.As` + 错误码 1062，不是字符串匹配
- unlike 忘查 `RowsAffected` → 重复 unlike 时计数被减成 0 以下或凭空变少
- `isLiked` 对不存在的 video 返回 false 而不是报错（原项目行为，service 直接透传 Count）
- Like 的 `CreatedAt` 忘赋值 → `listMyLikedVideos` 排序全乱（GORM 不会替你填零值字段之外的语义）
- 空列表返回 `null` → 前端炸；`ListMyLikedVideos` 里 nil 转 `[]Video{}`
- 撞 1062 后忘记在事务里 return error → 事务不回滚，INSERT 失败了计数却 +1 了
- Feed 侧忘注入 likeRepository → 编译不过或 is_liked 恒 false；`buildFeedVideos` 改完记得阶段 3 的验收用例重跑一遍

## 验收清单

- [ ] 连点 5 次 like → 第 1 次成功、后 4 次 `user has liked this video`，likes_count == 1
- [ ] **并发压测**（ab/hey 或 50 个 goroutine 同时点赞同一视频）→ likes 表只有 1 行、likes_count == 1
- [ ] 两个账号分别点赞同一视频 → likes_count == 2；各自 isLiked 均为 true
- [ ] unlike 后 likes_count == 0，再 unlike → `user has not liked this video`，计数不为负
- [ ] 对不存在的 video_id 点赞 → `video not found`；isLiked 不存在的视频 → `{"is_liked": false}`
- [ ] 不带 video_id / 传 0 → 400 `video_id is required`
- [ ] 登录状态访问 listLatest → 自己点过赞的视频 `is_liked: true`，其他和匿名视角 false
- [ ] listMyLikedVideos 顺序 = 点赞时间倒序；没点过 → 返回 `[]` 不是 null
- [ ] 事务验证：手工把 videos 表某行删掉再点赞 → 报错且 likes 表无残留记录

## 进阶改进

- like 接口改成幂等语义：重复点赞返回 200 `"already liked"` 而不是 500（RESTful 幂等性讨论）
- 计数更新下沉到 repo：`ChangeLikesCount(ctx, videoID, delta)` / `ChangePopularity(ctx, videoID, delta)`，service 不再摸 `repo.db`，分层更干净
- 加 `/like/getLikesCount` 接口（Postman 集合里有、原项目没实现，又一个"比原项目完整"的机会）
- likes_count 漂移自愈：定时任务用 `SELECT video_id, COUNT(*) FROM likes GROUP BY video_id` 校对计数（流水重算冗余，正好用上"计数与流水分离"的设计）

## 后续阶段回填清单（到时回来改，现在不做）

**阶段 7（Redis 缓存）**
- router 里 `NewLikeService(..., cache, ...)` 传入真实 `*rediscache.Client`；`JWTAuth(accountRepository, cache)` 换掉 nil
- 新增 `likeLimiter := ratelimit.Limit(cache, "like_write", 30, time.Minute, ratelimit.KeyByAccount)`，挂到 `/like` 和 `/unlike` 两个路由（写接口限流，读接口不限）

**阶段 8（热榜/热度缓存）**
- `UpdatePopularityCache(ctx, cache, videoID, change)` 写完整版：失效 `video:detail:id=%d` / `video:entity:%d` 两个缓存 key + 分钟桶 `hot:video:1m:<yyyymmddHHMM>` 的 `ZincrBy`（50ms 超时、Expire 2h）。本阶段只写 `cache == nil return` 的占位

**阶段 9（RabbitMQ 异步化）**
- router 传入 `likeMQ` / `popularityMQ`；service 的 Like/Unlike 改造成"双队列发布 + 按目标降级"：`likeMQ` 成功 → `mysqlEnqueued=true`（跳过直写事务），`popularityMQ` 成功 → `redisEnqueued=true`（跳过 UpdatePopularityCache），两个 flag 相互独立、只对失败的目标降级
- 本阶段写好的直写事务**原样保留**，变成 `!mysqlEnqueued` 时的降级路径
- repo 的 `LikeIgnoreDuplicate` / `DeleteByVideoAndAccount` 启用：LikeWorker 消费 `like.events` 时靠它们幂等（1062 → created=false 不动计数；deleted=false 不减计数）
- 事件格式：`LikeEvent{event_id, action, user_id, video_id, occurred_at}` → exchange `like.events`，routing key `like.like` / `like.unlike`；`PopularityEvent{event_id, video_id, change, occurred_at}` → `video.popularity.update`
