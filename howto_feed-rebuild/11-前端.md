# 11 - 前端（可选，可最后做或跳过）

前置：阶段 9。**可选阶段**：后端验收用 Postman 已足够，跳过本篇不影响任何后端能力。但强烈建议至少做一版——浏览器里完整走一遍**用户旅程**（见验收清单），等于对阶段 1-9 的全部成果做一次端到端集成测试，性价比极高。

技术栈刻意极简：**Vue 3（script setup）+ TypeScript + Pinia + vue-router + Vite**，HTTP 用原生 `fetch`（无 axios），UI 手写 CSS（无组件库），MD5 用 `spark-md5`（唯一的"业务"依赖）。原项目规模：10 个已注册路由的视图 + 1 个未路由的调试台、7 个 api 文件、3 个 store、3 个 composable、6 个公共组件。

启动：`cd frontend && npm install && npm run dev`（默认 5173，`/api` 代理到 `127.0.0.1:8080`）；生产走阶段 10 的 compose（frontend 服务已编排）。

## 对接后端的关键点

### 1. Vite 代理（开发期免 CORS）

```ts
server: { proxy: { '/api': {
  target: 'http://127.0.0.1:8080',   // 写死 IPv4：Windows 下 localhost 可能解析成 ::1 导致 ECONNREFUSED
  changeOrigin: true,
  rewrite: p => p.replace(/^\/api/, ''),
}}}
```

前端所有请求都走 `/api` 前缀（`API_BASE = import.meta.env.VITE_API_BASE ?? '/api'`），同源无预检；生产由 nginx 把 `/api/` 反代到 `backend:8080` 并剥掉前缀。

### 2. api 层封装（client.ts）

- **两个出口**：`postJson<T>(path, body, {authRequired?})` 和 `postForm<T>(path, FormData, ...)`——后者**不设 Content-Type**，让浏览器自己带 multipart boundary。
- **authRequired 本地预检**：需要登录的接口在没 token 时直接抛 `ApiError('需要先登录', 401)`，不打无谓请求。
- **token 注入**：有 token 就带 `Authorization: Bearer <token>`；软鉴权接口（Feed 等）匿名也能过，带了就返回 is_liked 个性化数据。
- **统一响应处理**：先 `res.text()` 再尝试 JSON.parse（解析失败降级为文本）；非 2xx 时从 `body.error` 取后端错误信息，抛 `ApiError(message, status, payload)` 并 reportError——页面层只 catch ApiError 读 `.message`。
- **401 处理 → 无感续期**：见下一节。

### 3. auth store：双 token 与 refresh 无感续期（难点 1）

**存储**：access_token / refresh_token 两个 key 存 localStorage，读写都包 try/catch（隐私模式会抛异常）。`claims` 是 computed：解码 JWT payload 拿 `{account_id, username, exp}`——**只用于 UI 展示与判断**（显示 @用户名、"这条评论是不是我发的"、"自己的视频不显示关注按钮"），前端不验签、不参与鉴权，真鉴权永远在后端。

**无感续期流程**（client.ts 内完成，页面层无感知）：

1. 任意请求收到 401，且 `path !== '/account/refresh'`（防死循环守卫）；
2. `tryRefresh()`：裸 fetch POST `/account/refresh` `{refresh_token}` → 后端 Redis 优先、MySQL 兜底比对 → 返回 `{token, account_id, username}`；
3. `auth.setToken(新 access)` → **用新 token 原样重放原请求**（FormData 也可重放）→ 把重放结果返回调用方；
4. refresh 失败（401/网络错）→ `clearTokens()` → 本次请求照常上抛 401 → 页面 toast + 跳登录；
5. **并发单飞**：`isRefreshing` 标志 + 共享 `refreshPromise`，N 个请求同时 401 只发一次 refresh，其余 await 同一个 promise 再各自重放。

**后端契约**：登录返回 `{token, refresh_token, account_id, username}`；refresh 只换发 access token（refresh_token 不轮换，登出/改名/改密时才作废）；改名接口直接返回新 token（旧 token 立即失效，前端 `setToken` 即可）。

### 4. 视频播放：竖滑 Feed（HomeView + useVideoPlayer）

- 滚动容器 `scroll-snap-type: y mandatory`，每屏一个 slide；`onScroll` 用 **requestAnimationFrame 节流**，`activeIndex = Math.round(scrollTop / clientHeight)`。
- 每个 `<video>` 用**函数式 ref** 登记进 `videoMap: Map<id, HTMLVideoElement>`；`playActive` 先暂停其他再播当前。
- **自动播放策略**：video 默认 `muted`（不过浏览器 autoplay 拦截），`play()` 失败静默 catch；用户手动切静音。
- **只渲染 activeIndex±1**（v-show 控制可见），DOM 里 video 元素数量恒定，长列表不卡。
- 编排只发生在视图层：`watch(activeItem)` → nextTick → `playActive` + `loadMoreIfNeeded`；`watch(tab)` → 清 activeIndex/videoMap/scrollTop → `ensureTabLoaded`（懒加载：切到 tab 且列表为空才请求）。
- 预取：`loadMoreIfNeeded(activeIndex)` 在**倒数第 3 条**时用游标拉下一页——正好检验你的分页协议设计得好不好。

### 5. 视频上传：分片 + spark-md5（难点 2，本篇最大亮点）

发布页流水线四段：**分片上传视频 → 整文件上传封面 → publish 落库 → 展示结果**。封面走老的 uploadCover；视频走分片四接口 `/video/chunk/init|upload|status|complete`（howto 阶段 2 未覆盖，属原项目在路线图之外补的能力；后端依赖 Redis，会话 TTL 24h，单文件上限 200MB）：

1. **选文件**：隐藏 `<input type=file>` + 自定义按钮；`URL.createObjectURL` 做本地预览，`onUnmounted` 时 revoke 防内存泄漏。
2. **算文件 MD5**：**不能** `file.arrayBuffer()` 一次读入（大文件爆内存）——按 2MB 循环 `file.slice(offset, end).arrayBuffer()`，`spark.append(buf)` 增量喂，最后 `end()` 出 hex。
3. **init**：POST `{filename, file_size, chunk_size: 5MB, total_chunks, file_hash}` → 后端按 `accountID + file_hash` 查 Redis，已有会话直接返回 `upload_id + uploaded_chunks`（这就是断点续传与秒传判断），新会话生成 upload_id。
4. **待传清单**：`pending = 全部分片 − uploaded_chunks`；为空则直接 complete（秒传）。
5. **并发上传**（手写 worker-pool，不引库）：指针 idx + active 计数，同时最多 3 片在飞；每片 `file.slice` → 算**分片 MD5** → postForm(upload_id, chunk_index, chunk_hash, file)，单片失败重试最多 3 次。
6. **进度条**：uploadedBytes/totalBytes；init 后用 uploadedSet 回推已传字节，注意**最后一片不足 5MB** 要按实际字节数累加，否则百分比算错。
7. **complete**：后端校验齐全后合并 → `{url, play_url}` → uploadCover → `publishVideo {title, description, play_url, cover_url}` → "已发布"卡片（#id / 去播放 / play_url / cover_url）。

file_hash 是会话身份（秒传/续传），chunk_hash 是分片完整性校验——**两个哈希都必须前端算**，这正是 spark-md5 的用武之地。

### 6. Composables 与 stores 的职责划分

| 单元 | 管 | 不碰 |
|---|---|---|
| useVideoFeed | 数据：三 tab 列表状态 + 三套游标（next_time / likes_count_before+id_before / as_of+offset）+ reset/追加语义 + 预取 | DOM、router |
| useVideoPlayer(scrollerRef) | DOM/媒体：rAF 滚动同步、videoMap、play/pause/mute | 任何 API |
| useLikeFollow(needLogin) | 动作：toggleLike（**请求成功后才翻转本地状态**，失败原样不用回滚）、toggleFollow（走 social store 后整表刷新）、share（剪贴板，失败降级 prompt）；每动作带 `busy[key]` 防连点 | 路由跳转——"未登录去哪"由页面注入 needLogin 回调 |
| stores/social | 关注关系两张全量列表 + isFollowing 查询 | — |

页面（HomeView）只做编排：从三个 composable 取状态和方法，用 watch 串起来。边界一乱，HomeView 就会膨胀成巨石组件——动手前先想清楚这条线。

### 7. SSE 通知接入（阶段 12 依赖）

**原项目的事实**：后端在 router.go 里挂了一组通知接口——`GET /notification/stream`（SSE 长连接）、`POST /notification/list`（最近 50 条）、`/notification/markRead`（传 id 单条/不传全部）、`/notification/unreadCount`；点赞/评论/关注事件经 MQ（notification.like/comment/social 三个队列）由 NotificationWorker 写 `notifications` 表并 Push 在线连接；SSE 每 30s 发一行 keepalive 注释。**但原项目前端没有任何 EventSource 代码**——通知中心 UI 是前后端能力缺口。所以：100% 对齐 = 不做；这里讲清楚是因为它是"阶段 12（通知模块）"的前端依赖。

如果做阶段 12，接入要点：

- **EventSource 不能自定义 header** → 后端 SSERequireAuth 支持 `?token=` query：`new EventSource('/api/notification/stream?token=' + auth.token)`；
- `onmessage` 里 JSON.parse 出通知对象 → toast / 红点；历史与未读数走 list / unreadCount，已读走 markRead；
- access token 过期时 SSE 会被 401 断开 → onerror 里先 tryRefresh 再用新 token 重建 EventSource；
- 代理与 nginx 都要**关缓冲**：Vite 代理基本可用，生产 nginx 需对该路径 `proxy_buffering off`（原项目只给 `/static/` 关了，`/api/` 没关——接 SSE 时要补）。

## 亮点

- **依赖极简**：全项目只有 pinia / vue / vue-router / spark-md5 四个运行时依赖——没有 axios、没有 UI 库、没有工具库，说明这些层手写并不难，反而看得清每一步。
- **normalize 防御层**：在 api 边界统一消化 Go 的 `null` 与零值，视图层永远拿到干净的数组/字段——前端代码里见不到 `?? []` 散落各处。
- **统一错误通道**：`ApiError(message, status, payload)` + `app.config.errorHandler` + reportError，错误从 fetch 到 toast 一条链。
- **composable 三分**：数据 / DOM / 动作职责分明，页面只编排——是Composition API 教科书式的分层。
- **手写并发池**：分片上传的 worker-pool（指针 + active 计数）十几行搞定，不引 p-limit，是理解"并发限流"本质的最好练习。
- **上传体验完整**：分片 + 秒传 + 断点续传 + 分片哈希校验 + 进度条 + 本地预览（ObjectURL 并正确 revoke）。
- **生产链路齐全**：多阶段 Dockerfile（node24 build → nginx 托管）+ nginx.conf 处理 SPA try_files、`/api` 反代、`client_max_body_size 300m`（大视频上传不被 413）、`/static` 透传后端文件。

## 复刻建议

- 不必逐像素复刻，**把 10 个页面的 API 调用链对上**即可；样式可以糙，链路不能断。
- 推荐顺序：骨架（vite + router + pinia + AppShell）→ `api/client.ts`（token 注入 + 401）→ 账号三页（注册/登录/设置）→ HomeView 推荐流 → 点赞/评论/关注 → 发布页（先整文件 uploadVideo 跑通，再升级分片）→ 热榜/关注流 → 私信。
- 最低配达标线：一个 FeedView 式调试台页面 + 表单直调 6 组 API，旅程能走通即及格；**分片上传和竖滑播放器是优秀线**。
- 动手前先给 Composables 划好边界（见上表），再写 HomeView。
- 后端配合项：分片上传需要 Redis 在跑（阶段 7）；私信模块 howto 未单独成篇（原项目 `internal/message`，仅 send/list 两接口），MessageView 可当补练素材。

## 常见的坑

- **401 重试死循环**：refresh 必须走裸 fetch 且被排除在重试之外，否则 token 彻底过期时 refresh 自己返回 401 → 又触发 refresh。
- **postForm 手动设 Content-Type** 会丢 multipart boundary → 后端 ShouldBind 失败；FormData 就不要设。
- 大文件 `file.arrayBuffer()` 一次性读入 → 内存爆；必须 slice 分片读。
- Windows 下 Vite 代理 target 写 `localhost` 可能解析成 IPv6 `::1` → ECONNREFUSED；写死 `127.0.0.1`（原项目专门注释了这一点）。
- localStorage 在隐私模式 setItem 会抛异常 → 所有读写包 try/catch。
- 不 muted 的 video 调 `play()` 会被浏览器 autoplay 策略拒绝 → 默认静音 + catch 吞错，取消静音交给用户。
- Go nil slice 序列化成 `null` → 前端 `.map` 直接 TypeError → normalize 层兜底。
- 生产 nginx 不配 `client_max_body_size` → 大视频上传 413。
- `listLikesCount` 首屏请求不带游标字段（undefined 不序列化），始终带 0 语义不同——对照 `api/feed.ts` 的条件拼 body。
- 别以为 error-reporter 生产分支真的上报成功了——后端没有 `/error-report` 端点，404 被 catch 静默吞掉。

## 进阶改进

- **SSE 通知中心**（见关键点 7）——"阶段 12"的前端落点：红点、通知列表、已读。
- 关注关系改用 Set 增量维护（原项目 follow/unfollow 后整表刷新 getAllVloggers，人多了请求量大）。
- 评论分页（后端 listAll 全量，前端只能照单全收，练阶段 3 的游标正好用上）。
- token 改存 httpOnly cookie（localStorage 有 XSS 风险）；refresh token 加旋转（一次一换）。
- 上传并发池抽成通用工具；直传对象存储（预签名 URL），后端只发凭证。
- 竖滑列表虚拟滚动（目前 v-show 全量挂载 video 元素，列表上百条会吃内存）。
