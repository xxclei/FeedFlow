# 01 - 账号模块（Account）+ JWT 鉴权

前置：阶段 0。这是第一个业务模块，也是**鉴权体系**的地基，值得写慢。

## 目标

注册（bcrypt）、登录（签发 JWT + 单会话 token）、登出、改密（强制下线）、改名（重签 token）、按 ID/用户名查询；以及两个鉴权中间件 `JWTAuth`（强）和 `SoftJWTAuth`（软，阶段 6 用）。

## 接口设计

| 路由 | 鉴权 | 请求 → 响应 |
|---|---|---|
| POST /account/register | 无 | `{username,password}` → `{message}` |
| POST /account/login | 无 | `{username,password}` → `{token}` |
| POST /account/changePassword | 无 | `{username,old_password,new_password}` → `{message}` |
| POST /account/findByID | 无 | `{id}` → `{id,username}` |
| POST /account/findByUsername | 无 | `{username}` → `{id,username}` |
| POST /account/logout | JWT | `{}` → `{message}` |
| POST /account/rename | JWT | `{new_username}` → `{token}`（新 token！） |

## 数据模型

```go
type Account struct {
    ID       uint   `gorm:"primaryKey" json:"id"`
    Username string `gorm:"unique" json:"username"`
    Password string `json:"-"`   // 敏感字段不序列化！
    Token    string `json:"-"`
}
```

## 关键设计决策（写之前先回答自己）

**Q1：密码怎么存？** bcrypt（`golang.org/x/crypto/bcrypt`）。哈希在 **Service 层**做（handler 不碰加密，repo 不懂业务）。校验用 `bcrypt.CompareHashAndPassword`，绝不查出来比较明文。

**Q2：JWT 里放什么、怎么撤销？** Claims = `{account_id, username}` + RegisteredClaims（HS256，24h，ExpiresAt/IssuedAt/NotBefore）。
撤销方案是**单会话 token 模型**：`account.token` 列只存"当前有效的那个 token"——
- 登录：覆盖旧 token（顶号下线）
- 改名：事务里同时更新 username 和**新签的 token**（旧 token 立即失效）
- 改密：更新密码哈希后调 Logout（全部下线）
- 登出：清空 token
中间件校验时**比对请求里的 token 和存储的 token 是否一致**，不一致 = 已撤销。这就是"数据库即黑名单"——不需要单独的黑名单表。

**Q3：secret 放哪？** 环境变量 `JWT_SECRET`，空则回落默认值（原项目如此；进阶：空值直接 fatal 更安全）。

**Q4：中间件怎么把身份传给 handler？** `c.Set("accountID", claims.AccountID)`，配套 `GetAccountID(c *gin.Context) (uint, error)` 帮助函数（注意 `c.Get` 拿出的是 `any`，要 `.(uint)` 断言）。

**Q5：注册时用户名冲突怎么识别？** 捕获 MySQL 错误码 1062（dup key）转成业务错误 → HTTP 409。**不要**先查一遍再插入（有并发窗口）。

## 实现提示

JWT 部分（`internal/auth/jwt.go`，独立于 account，供中间件和 service 共用）：

```go
func jwtSecret() []byte
func GenerateToken(accountID uint, username string) (string, error)   // HS256
func ParseToken(tokenString string) (*Claims, error)   // ParseWithClaims + 校验 alg
```

`ParseToken` 的 keyFunc 里**必须校验签名算法**（防算法混淆攻击）：

```go
if token.Method.Alg() != jwt.SigningMethodHS256.Alg() { return nil, errors.New("unexpected signing method") }
```

鉴权中间件骨架（`internal/middleware/jwt/jwt.go`）：

```
JWTAuth:   无 Authorization header → 401
           格式非 "Bearer xxx"    → 401
           ParseToken 失败        → 401
           check() 校验存储 token
SoftJWTAuth: 无 header → 直接 c.Next()（匿名放行，阶段 6 Feed 用）
             有 header 但非法 → 401（带了就必须是对的）
check():   （阶段 7 会插入 Redis 优先逻辑，现在直接查 DB）
          FindByID → account.Token == "" 或 != 请求 token → 401 "token has been revoked"
          通过 → c.Set(accountID/username) → c.Next()
```

Repo 层要点：
- `RenameWithToken` 用 **`db.Transaction`** 把"改名"和"写新 token"放进一个事务
- 所有 Update 之后检查 `result.RowsAffected == 0` → 返回 `gorm.ErrRecordNotFound`

路由分组（`internal/http/router.go` 第一次亮相）：

```go
accountGroup := r.Group("/account") { /* 公开 5 个接口 */ }
protected := accountGroup.Group("")
protected.Use(jwt.JWTAuth(accountRepository, cache))   // cache 现在传 nil
{ /* logout, rename */ }
```

## 常见的坑

- `Password`/`Token` 忘加 `json:"-"` → 密码哈希直接返回给前端（安全事故级 bug）
- 断言 `c.Get("accountID").(uint)`：GORM 主键是 uint，断言成 int64 会 panic/失败
- `SplitN(header, " ", 2)` 后不检查 `len(parts)!=2` → 越界 panic；`Bearer` 大小写用 `EqualFold`
- 改密接口用 username 定位用户（原项目如此），意味着你得先知道明文旧密码——注意它和 rename 的鉴权设计不一致，是原项目的一个粗糙点，你可以改进为"从 token 取 accountID"
- bcrypt 的 `DefaultCost`(10) 首次注册会明显耗时（~100ms），是正常现象

## 验收清单

- [ ] 注册 → 登录拿到 token → 用 `Authorization: Bearer <token>` 调 logout 成功
- [ ] 登出后**用同一个 token** 再调 logout → 401 token has been revoked
- [ ] 重复注册同名 → 409
- [ ] 改名后返回新 token，旧 token 立即 401
- [ ] 改密成功后旧 token 全部失效，新密码能登录
- [ ] 数据库里 password 是 `$2a$10$...` 格式

## 进阶改进

- 登录/改密失败返回 401/400 而不是笼统 500（原项目登录失败返回 500）
- `JWT_SECRET` 为空时启动报错
- changePassword 改为 JWT 鉴权 + 从 token 取用户（不需要再传 username）
- 加一个统一的错误码结构 `{code, message}`
