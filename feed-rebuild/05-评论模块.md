# 05 - 评论模块（Comment）

前置：阶段 4。结构与点赞同构，练"照着成熟模式举一反三"，重点在**属主权限校验**。

## 目标

发表评论、删除评论（仅作者）、列出视频全部评论；评论数参与热度。

## 接口设计

| 路由 | 鉴权 | 请求 → 响应 |
|---|---|---|
| POST /comment/listAll | 无 | `{video_id}` → `[comment...]` |
| POST /comment/publish | JWT | `{video_id, content}` → `{message}` |
| POST /comment/delete | JWT | `{comment_id}` → `{message}` |

## 数据模型

```go
type Comment struct {
    ID        uint      `gorm:"primaryKey" json:"id"`
    Username  string    `gorm:"index" json:"username"`   // 冗余，同 Video
    VideoID   uint      `gorm:"index" json:"video_id"`
    AuthorID  uint      `gorm:"index" json:"author_id"`
    Content   string    `gorm:"type:text" json:"content"`
    CreatedAt time.Time `gorm:"autoCreateTime" json:"created_at"`
}
```

## 关键设计决策

**Q1：谁能删评论？** Service 层 `GetByID` 后比对 `comment.AuthorID != accountID → "permission denied"`。**注意**：Handler 从 JWT 取 accountID 传入，不能信任请求体里的任何身份字段。

**Q2：和点赞模块的架构差异？** 模式完全同构（校验 → 双目标写入），差异只有两点：
- 评论没有"唯一约束"（一人可多发），所以没有 1062 分支，幂等性弱（阶段 9 会讨论 MQ 重复消费 → 原项目靠 EventID 字段预留，实际未做去重，这是可改进点）
- 删评论走 `GetByID + Delete`，属主校验必须在**入队之前**做（不能把"能否删"的判断交给异步）

**Q3：热度怎么算？** 发评论 popularity +1。删评论原项目**没有 -1**——这是一个已知瑕疵（榜单虚高）。复刻时建议你补上（删评论时记录 videoID 一并 -1），并体会"事件里要带够上下文"这个教训：原项目 `comment.delete` 事件只传 commentID，Worker 得先查回评论才知道 videoID。

## 实现提示

publish 事务直写（同 like 的骨架）：

```
Publish(video, author, content):
  1. TrimSpace 校验 content 非空、video 存在
  2. handler 已查出 username 填入
  3. db.Transaction:
       INSERT comment
       UPDATE popularity +1
```

Repo：`CreateComment` / `DeleteComment` / `GetAllComments(videoID)` / `GetByID` / `IsExist`。

## 常见的坑

- content 全是空格 → TrimSpace 后必须拦截
- 删除时先查后删之间评论可能已被删 → `Delete` 的 RowsAffected==0 当成功幂等处理即可
- listAll 不分页（原项目如此）——评论多时是隐患，进阶可加游标分页（练阶段 3 的模式）

## 验收清单

- [ ] A 发布评论成功，listAll 可见（含 username）
- [ ] B 删 A 的评论 → permission denied；A 自己删 → 成功
- [ ] 删除后 popularity 相应 -1（你的改进版）
- [ ] 对不存在的视频发评论 → video not found
