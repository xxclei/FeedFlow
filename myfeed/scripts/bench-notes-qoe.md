## 一、为什么需要这个模块

`bench-notes-video-delivery.md` 的结论是"瓶颈在 12 Mbps 上行、服务端差了 960 倍"。
但那次测量同时暴露了一个**结构性问题**：

> "能撑 33 人"是**假的安全感** —— 不是架构挣来的，是上传者**碰巧**传了 0.36 Mbps 的素材。
> 项目**没有转码**，码率 100% 由上传者决定。只要有人传手机原片（1080p / 10~15 Mbps），
> 边界立刻塌到"一个人看都卡"。

要把码率决定权从上传者手里收回服务端，就需要一个**能证明它有效的仪表盘** ——
否则"优化完了变好了"只能靠感觉说。这就是 QoE 埋点。

**而且它必须排在最前面做**，因为基线只能在动手改之前测。这是本项目一贯的方法论
（`bench-notes-like-mq.md` 也是先测基线再加缓存）。

## 二、口径：每个数是怎么定的

这一节是整个模块最值钱的部分。字段名谁都写得出来，**口径写错了表面完全看不出来**。

### 2.1 优先级：卡顿 > 码率稳定 > 首帧

工业界的排序是有实证依据的，不是偏好：哥伦比亚大学对 40 万+ YouTube 会话的研究给出

- 一次卡顿对用户留存的影响 ≈ **3 次码率切换**
- 首帧每慢 1 秒 → 放弃率 **+5.8%**
- 播放中途码率**升高**（不是降低）也会让放弃率涨 **4 倍**

所以 `stall_count` / `stall_total_ms` 是这张表里最重要的两列，`startup_ms` 排第三。
排序体现在表的列顺序、以及下面前端注释里反复强调"别只看首帧"。

### 2.2 `waiting` 而不是 `stalled`（前端最容易被改坏的一条）

| 事件 | 语义 | 什么时候触发 |
|---|---|---|
| `waiting` | 播放**停了在等数据** | 用户感受到的"卡了"，很常见 |
| `stalled` | 尝试取数据但 **3 秒以上一点没拿到** | 更严重但**少见得多** |

网络"慢到不够流畅"时 `waiting` 一直触发、`stalled` 根本不触发。
**用 `stalled` 计数会得到一个系统性偏低的卡顿率 —— 表现是"看板说很流畅，用户说很卡"。**

### 2.3 首次缓冲不算卡顿

`waiting` 在**第一次播放之前也会触发**（那是在做初始缓冲，也就是首帧等待期）。
把它算成卡顿会同时污染两个指标：卡顿数 +1，而且 `stall_total_ms` 里塞进了整个首帧时长。

判据是 `firstPlayingAt`：**只有"已经播出过画面了"之后的 `waiting` 才算卡顿。**
（`useQoE.ts` 里 `onWaiting` 的第一行，那条 early return 删不得。）

### 2.4 `played_ms` 是卡顿率的**分母**，所以它必须防拖进度条

`timeupdate` 约 4Hz，正常 delta ≈ 0.25 秒。用户把进度条从 10:00 拖到 1:00:00，
delta 就是 3000 秒 —— 直接累加会让 `played_ms` 远超视频时长，
**静默地把卡顿率压到接近 0**（数字看着正常，只是全错）。

所以累加条件是 `delta > 0 && delta < 1`：上界 1 秒远大于正常的 0.25、
远小于任何有意义的 seek；下界排除往回拖。

### 2.5 `stall_count` 和 `stall_total_ms` 都要，缺一不可

10 次 100ms 的卡顿（几乎无感）和 1 次 1000ms 的卡顿（很难受）：

| | count | total |
|---|---|---|
| 10 次 × 100ms | 10 | 1000 |
| 1 次 × 1000ms | 1 | 1000 |

**任一单独看都会得出错误结论。** 工业界常用的 `ratio = stall_total_ms / played_ms`
用的是后者（本项目 `stall_ratio` 就是这个口径，**不是**"有卡顿的会话占比"）。

### 2.6 `avg_bitrate_kbps > 0` ≡ "这条来自 HLS"

直传 mp4 没有档位概念，恒为 0。所以这个字段**同时**是判别式，不另加 `is_hls` 布尔列 ——
那个列会造出 "is_hls=true 但 avg_bitrate_kbps=0"（HLS 单档没切过）这种自相矛盾的行。

它和 `tier_switches` 必须一起看：**切换 0 次可能是"很稳定"，也可能是"永远卡在最低档"**
（带宽一直不够，ABR 放弃了）。

### 2.7 一次播放 = 一行（upsert），不是一事件一行

客户端有**三条**刷出路径：组件卸载 / 标签页切后台（`visibilitychange`）/ 页面卸载（`pagehide`），
同一次播放可能全部触发。

- 一事件一行 → 量大约 100 倍，而且每个问题都得先聚合
- 一次播放一行 + `session_id` 唯一索引 + **upsert** → 量小 100 倍，且直接可查

`upsert` 的"后写覆盖先写"正好是**正确语义**：计数器只增不减，越晚的刷出携带的快照越完整。

**刻意不加"只发一次"的守卫**：用户切到后台再切回来接着看，第二次上报的数据更全；
加守卫会把"切回来看的那段时间"整个丢掉。

### 2.8 明确**不做** MOS

标准是 ITU-T P.1203（输出 1~5 的 MOS）。本项目不做 —— 那个加权公式需要
**主观评分数据集来标定权重**，没有的话算出来的 MOS 只是个好看的假数。
存原始指标、看分布，更有用也更诚实。

## 三、后端验收（已实测通过）

### 3.1 建表与索引

```
show index from qoe_events;
  idx_qoe_session      NON_UNIQUE=0   session_id            ← UNIQUE，upsert 的键
  idx_qoe_video_time   NON_UNIQUE=1   (video_id, created_at) ← 两列复合
  idx_qoe_events_account_id            account_id
```

复合索引必须两列：`video_id` 单列不够 —— "某条视频最近的表现"这个最高频查询
永远带时间范围，两列才走得动。

⚠ **表名踩过一个坑**：GORM 默认把 `QoEEvent` 解析成 `qo_e_events`（`QoE` 不在它的
commonInitialisms 表里，被拆成 `Qo_E_Event`），而 `repo.go` 里分位数那条**裸 SQL**
写的是 `qoe_events` —— 两边会分叉。后果不是启动报错，而是**只有 `/qoe/stats` 炸
"table doesn't exist"**，写入侧一切正常。已用显式 `TableName()` 钉死，理由见 `entity.go`。

### 3.2 实测结果

| 用例 | 期望 | 实测 |
|---|---|---|
| 空表 `stats` | 200，`stall_ratio` 是 **0 不是 NaN** | ✅ 200 |
| 游客上报（无 token） | `account_id = 0` | ✅ |
| 同 `session_id` 报两次 | 仍是**一行**，值取第二次 | ✅ |
| 合法 token 上报 | `account_id = 9` | ✅ |
| 无效 token | **401**（软鉴权仍掐断无效凭证） | ✅ |
| 空 `session_id` / `video_id=0` / 超长 | 400 | ✅ |
| 非法 JSON | 400 | ✅ **（原来 500，已修，见 3.3）** |
| 超大数值 | 被夹到常量上限 | ✅ `played_ms→86400000`、`startup_ms→600000` |
| `video_id` 过滤 | 分位数分母跟着变小 | ✅ n=4 vs 全局 n=7 |

最后一条特别值得记：`video_id=177` 时 `startup.n = 4`、全局时 `n = 7`。
**这证明过滤条件确实写在 CTE 内部** —— 写在外面的话分母恒等于全表行数，
分位数会静默算错（数字看着正常，只是不对）。这是 `repo.go` 里 `rawWindowSQL`
和 `rawArgs` 必须成对出现的唯一原因。

### 3.3 顺手修的一个全项目 bug

`apierror.ClassifyHTTPStatus` 对 `ShouldBindJSON` 的错误一律 `default → 500`。

但 `*json.SyntaxError` / `*json.UnmarshalTypeError` 的含义是**客户端发的东西不合法**，
回 500 等于说"服务端崩了"，与事实相反。对**本项目**最要命的一条：
手工 curl 调试时字段名写错或漏个引号，返回 500 —— 看起来完全像后端坏了，
于是整条链路被重新怀疑一遍。（这条已经踩过，见记忆里的 `gin-ignores-unknown-json-fields`。）

已加两个 case → 400。`feed/handler.go` 里那两处硬编码的 `c.JSON(400, ...)`
现在是冗余的（不再是错的），可以留着。

**`created_at` 的一个反直觉点**：它存的是**首次**写入的时刻，upsert 不刷新它。
所以 handler 响应里回显的 `created_at` 在重复上报时会比库里的新 ——
它表示"这次播放什么时候开始的"，正好是 stats 时间窗该用的口径（要稳定，不要最新），
但**不能拿响应里的值当落库结果用**。

## 四、基线（**待采集**）

### 4.1 为什么还空着

QoE 的数字全部来自浏览器 JS 的计时（`performance.now()` / `played` / `waiting` 事件），
**脚本造不出来** —— curl 只能验证接口形状，造出来的数是合成数，不是基线。

所以这一节必须由**一次真实播放**产生。

### 4.2 采集方法

1. 后端在跑（见 §4.4），前端 `npm run dev` 在跑
2. 浏览器打开任意一条视频的详情页 `/video/:id`，**点播放，看 20~30 秒**
3. 切走或关掉页面（触发刷出）
4. 取数：

```bash
curl -s -X POST http://127.0.0.1:8080/qoe/stats \
  -H "Content-Type: application/json" -d '{"video_id":0,"days":-1}'
```

`days: -1` = 不限时间。默认（`days: 0`）是最近 **7 天** —— 因为播放侧任何改动
（缓存头、ABR、降级）都会改变 QoE，跨改动的全时段均值是个混合两个世界的假数。

### 4.3 ⚠ 采集时机的硬约束

**必须在阶段 C 之前采。** 理由：阶段 C 会把 `r.Static` 换成带
`Cache-Control` / `ETag` 的自定义处理器，那会**改变存量 mp4 的播放行为**
（重复加载命中缓存而不再整份重拉）—— 采晚了就不是"改之前"了。

阶段 B（上传门禁探测）对播放零影响，可以在它前后任意时刻采。

顺带记一个**已知的基线污染**：阶段 A 本身把 `preload="auto"` 改成了 `"metadata"`
（原来那个和组件自己"点了才放"的设计矛盾，用户没点就白拉 38 MB）。
这次改动会让 **首帧 `startup_ms` 变大、白传字节变少**。
所以下面采到的 `startup_ms` 是"preload 已改"之后的数。
两个数必须一起看 —— 只看首帧会得出"这个改动把播放搞慢了"的错误结论。
（如果之后想要 preload 的 A/B 对照，它是一次上下一行的开关。）

### 4.4 采集时的环境（已核实）

- Docker 三容器 Up：`myfeed-mysql` / `myfeed-redis` / `myfeed-rabbitmq`
- 后端：`.run/myfeed.exe`（**已含 `/qoe/*` 路由**），监听 8080
  - ⚠ 原来的 `go run ./cmd` 进程已被停掉换成这个二进制。要改回 `go run` 需先停掉它
- 前端：vite dev server 在跑（node，PID 48988）

| 指标 | 值 | 说明 |
|---|---|---|
| `total_sessions` | _待填_ | |
| `guests` | _待填_ | |

> 不同性质的东西：这个文件是**播放体验的观测口径**（数字来自浏览器 JS 计时），
