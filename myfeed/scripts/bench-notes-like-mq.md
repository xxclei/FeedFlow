# 阶段9（RabbitMQ）点赞链路的 before/after 记录

CSV 里的 label：`before-mq-likecycle` / `after-mq-likecycle`，group = `like-mq`。

**这两行的数字不能和 CSV 里其他行直接比。** 其他行是 hey 打出来的并发吞吐，
这两行是**顺序单请求延迟**。原因见下 —— 这条路 hey 根本测不了。

**这两行之间也不能比 `qps` 和 `total_sql` 两列**（`sql_per_req` 和三个延迟可以比）：

- `qps`：before 是纯发请求的墙钟，after 的墙钟**包含了每次等待落库**（1.15 秒
  里有约 0.85 秒是在等一致性）—— 两个数不同口径。
  真正的吞吐没测，见第三节第 2 条。
- `total_sql`：两行都是 **341**，这个数**是对的、也是本次实验的重点** ——
  它说的是"整个系统为同样的 60 个请求付了同样的 SQL"。
  但 after 那行 `sql_per_req = 2.00` 只是**请求侧**的，
  worker 侧还有 3~4 条没算进去。两列的统计范围故意不同：
  一个回答"用户等的那段有多重"，一个回答"系统总共多累"。

## 一、为什么 hey 测不了 `/like/like`

两个坑，任何一个单独出现都会让结论完全错误。

### 坑 1：已赞短路（致命）

`/like/like` 是**有状态、一次性**的接口。同一个账号对同一个视频：

| 第几次请求 | 走的路径 | SQL |
|---|---|---|
| 第 1 次 | 预检 → 事务 → 计数 → 缓存 | **6** |
| 第 2 次起 | 在"已赞预检"那一行就返回 500 | **2** |

hey 跑 8000 次，7999 次走的都是那 2 条 SQL 的短路路径。

于是会得到这样一份"对比"：

```
优化前：2 SQL/请求
优化后：2 SQL/请求
结论：MQ 没有任何用
```

**完全错误**，因为被改的那一层（事务里那 6 条 SQL）在 7999 次里一次都没走到。
这是 `bench-must-target-instrumented-route` 那个坑的变体：
**路由打对了，但请求根本没进到要测的那一层。**

### 坑 2：限流

`like_write` 限流是 **30 次/分/账号**，而且 `like` 和 `unlike` **共用**同一个桶。
key 实测为 `v1:ratelimit:like_write:<account_id>`。

hey 跑到第 31 次全是 429 —— 测的就变成限流器了。

---

## 二、用的什么测（`.run/likebench`）

一个一次性 Go 程序，循环 N 轮，每轮：

```
DEL v1:ratelimit:like_write:1     ← 绕开限流
POST /like/like     计时          ← 成功路径，状态变成"已赞"
DEL v1:ratelimit:like_write:1
POST /like/unlike   计时          ← 成功路径，状态回到"未赞"
```

一赞一取消，**状态回到原点**，所以每一次请求都是完整成功路径。

为什么用 Go 而不是 curl：curl 每次要起一个进程 + 建 TCP 连接，
实测那种开销会盖过被测的 15ms，测出来的是 curl 不是服务器。

---

## 三、这个测法的诚实交代

三点必须写清楚，否则以后回看会误读：

1. **删限流 key 是测试专用操作。** 限流器在优化前后都存在、开销恒定，
   在 before/after 对比里互相抵消；但不删它就跑不出 100 个样本。
   **所以这个数字是"成功路径的单请求延迟"，不是"生产 QPS"。**
2. **顺序发，不是并发。** 61 req/s 是"一次一个"的节奏，
   **不是吞吐上限**。行锁竞争造成的尾延迟要靠多账号并发才能压出来 ——
   这条路的并发测试还没做。
3. **URL 字段填的是 `/like/like`**，但实际每一轮是 `like` + `unlike` 两次请求，
   所以 `sql_per_req = 5.50` 是两者的**加权平均**（6 和 5，见下表），
   不是单看 `like` 的 6。

## 四、基线（改动前，2026-09-14）

环境：本机，服务端 `127.0.0.1:8080`，Redis 在路径上（`on`），视频 279，账号 1。

### 每请求开销（逐条实测，不是估算）

| 操作 | SQL | Redis（应用侧） |
|---|---|---|
| **点赞成功** | **6** | **4** = 2 `DEL` + 1 `ZINCRBY` + 1 `EXPIRE` |
| **取消点赞成功** | **5** | 同上 4 |
| 重复点赞（预检短路） | 2 | 0 |

> 6 与 5 的差是**故意的**：`Unlike` 跳过了事务内的 `IsExistTx` 复查
> （见 `internal/video/like_service.go:152`）。不是 bug。

限流中间件另外消耗 **2 个 Redis 命令/请求**（`GET` + `INCR`），
优化前后不变，不计入上表的"应用侧 4"。

### 延迟（30 轮 = 60 个成功路径请求）

| 指标 | 值 |
|---|---|
| 样本数 | 60 |
| 响应码 | 全部 200 |
| 错误 | 0 |
| mean | 15.74 ms |
| min | 12.82 ms |
| **p50** | **15.66 ms** |
| **p95** | **19.21 ms** |
| **p99** | **23.47 ms** |
| max | 23.47 ms |
| 顺序吞吐 | 61.1 req/s |

### 这组数字的交叉验证（重要）

跑之前 / 跑之后读 `SHOW GLOBAL STATUS LIKE 'Com_stmt_execute'`：

```
403646  →  403987      差 = 341
```

预测值：30 轮 × (6+5) + 预热 (6+5) = **341**。**分毫不差。**

这一条比延迟数字本身更值钱 —— 它证明 60 个样本**每一个都真的进了事务**，
没有一个掉进短路分支。没有这个校验，前面那些好看的 p99 可能全是在测
"2 条 SQL 的失败路径"。

Redis 同理，逐项对得上（`zincrby` +62、`expire` +62、
`del` +186 = 应用 2×62 + 测试台自己删限流 key 的 62）。

录像结束状态已还原：视频 279 → `likes_count=0, popularity=1`，`likes` 表 3 行不变。

## 六、before / after 对比

### ① 延迟：用户等的时间，快 3.7 倍

| 指标 | before | after | 变化 |
|---|---|---|---|
| 写延迟 mean | 15.74 ms | 4.35 ms | **−72%** |
| **写延迟 p50** | **15.66 ms** | **4.28 ms** | **−73%** |
| 写延迟 p95 | 19.21 ms | 4.83 ms | −75% |
| 写延迟 p99 | 23.47 ms | 6.27 ms | −73% |
| 一致性延迟 p50 | 0（结构性） | 14.25 ms | 新出现 |

**"写延迟"就是用户按下点赞到看到成功提示的时间。** 这是 MQ 换来的东西。

### ② 端到端：反而慢了 18%

但把一致性延迟加回去 —— 也就是"从用户点击，到别人刷新时真的能看到这个赞"：

```
before:  15.66 ms          （返回时就已经落库了）
after:   4.28 + 14.25 = 18.53 ms
```

**18.53 / 15.66 = +18%。**

这是本次实验**最值得记住的一条**，也是我事先没料到的那条：
**MQ 没有让系统变快，它让系统变慢了一点点**（多出一次 publish + 一次 consume 的往返），
但它把这 14ms 的等待**从用户身上挪到了系统身上**。

### ③ SQL：总量分毫不差，只是换了个人做

实测（停掉 worker 把两侧分开量，用 sleep 代替轮询以免测试台的查询污染计数器）：

| 环节 | before | after |
|---|---|---|
| 点赞请求（用户等的那段） | **6** | **2** |
| 取消点赞请求 | **5** | **2** |
| LikeWorker 消费 like 消息 | — | **4** |
| LikeWorker 消费 unlike 消息 | — | **3** |
| PopularityWorker（只写 Redis） | — | 0 |
| **一次「赞+取消」的系统总 SQL** | **11** | **11** |

```
like   整轮（请求+worker）: 6        （before: 6，全在请求里）
unlike 整轮（请求+worker）: 5        （before: 5，全在请求里）
一次「赞+取消」系统总 SQL: 11        （before 实测 = 6+5 = 11）
```

**11 = 11。一条 SQL 都没省。**

请求侧之所以从 6 降到 2，是因为那 4 条（插流水 + 两个计数 UPDATE）**整个搬到了
worker 进程**，不是消失了。Redis 侧同理：同步路径的 `ZINCRBY` / `EXPIRE`
搬到了 PopularityWorker。

这是"**异步不是优化，是重排**"最干净的证据。

## 七、结论：这次改动的收益到底是什么

按用户当初的问题"在性能上有帮助吗，还是用户体验上有帮助"逐条回答：

| 维度 | 答案 | 证据 |
|---|---|---|
| 单请求延迟 | **有，−73%** | p50 15.66 → 4.28 ms |
| 端到端总耗时 | **没有，+18%** | 15.66 → 18.53 ms |
| 系统总工作量（SQL） | **完全没有，11 = 11** | 见上 |
| 扛下游抖动 | **有，而且是最大的一条** | 见下 |
| 吞吐上限 | **没测**（见"诚实交代"第 2 条） | — |

### 真正值钱的是"扛"这一条，它没体现在延迟数字里

before 的时候，**Redis 或 MySQL 抖 200ms，用户的点赞请求就跟着卡 200ms**，
抖到超时就是 500，用户看到红字、数据也没了。

after 之后，**用户那 4ms 只取决于「消息有没有写进 socket」**。
MySQL 挂了、Redis 挂了、worker 进程死了 —— 用户全都无感，照样秒回 200，
消息静静堆在队列里（实测：停掉 worker，`like.events` 里积压 1 条、
`video.popularity.events` 里积压 1 条，worker 一启动 2 秒内全部补完）。

**这才是这次改动真正买到的东西。** 它不体现在 p99 上，
体现在"下游挂了之后用户还看不看得出来"上 ——
而这正好就是文档 Q1 说的"worker 崩了 API 照常服务"。

### 代价（必须一起说，否则就是报喜不报忧）

1. **可见性延迟 14ms。** 点了赞立刻刷新，可能还是没赞的状态。
   产品上要接受这一点（原项目接受）。
2. **端到端慢 18%。**
3. **调试变难。** 现在一次点赞跨两个进程、两条队列、两个消费者 ——
   出问题时要先回答"消息发出去了吗""worker 收了吗""落库成功了吗"，
   而 before 只需要看一个 HTTP 请求的堆栈。
4. **多了两个进程**（API + worker）要部署、要监控、要重启。

### 我事先的预期 vs 实际

我在第五节写的预期是"**延迟大概不会明显变好，甚至可能持平**"。

**实测打脸了 —— 写延迟降了 73%，比预期好得多。**
但打脸的方向值得记下来：延迟变好是因为**工作的确被移走了**，
而不是因为系统变强了；所以同时"端到端变慢"和"总 SQL 不变"也一并成立。

**三个数要一起看才是完整的**：单看 −73% 会得出"MQ 是个性能优化"的错误结论。
