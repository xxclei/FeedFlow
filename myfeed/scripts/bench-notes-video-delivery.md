# 视频分发实测记录 —— 瓶颈定位与优化决策

日期：2026-09-15
范围：`/static` 这条路上的**分发**（不是上传、不是业务逻辑）
起因：讨论"多人同时用链接看视频会不会卡"，需要先知道瓶颈在哪一层

> 这份记录的目的是**把"该做什么优化"这个决定建立在实测上**。
> 结论先说：**瓶颈是 12 Mbps 的上行带宽，服务端差了 960 倍。
> 三个杠杆里两个改不动，只剩"减少传输次数"——所以优化只做三件小事，然后停。**

---

## 一、测量方法

三件事的测量**互相独立**，分别用不同手段：

| 量什么 | 怎么测 | 为什么这样测 |
|---|---|---|
| 互联网上/下行 | `curl` 打 Cloudflare 公开测速端点 | 唯一能测出**出网**真实速率的方法 |
| 服务端吞吐/并发/CPU | 自建 `cmd/staticprobe` 探针服务 | 见下 |
| 素材码率/时长 | `scripts/mp4_probe.py` 解析 mp4 头 | 机器上没有 ffprobe，不装也能量 |

### 为什么用探针服务而不是 myfeed.exe

`cmd/main.go` 里数据库是**硬依赖**：

```go
if err != nil { log.Fatalf("连接数据库失败: %v", err) }
```

而当时 Docker 没运行，MySQL / Redis / RabbitMQ 全都不在 —— **myfeed.exe 起不来**。

但这次要量的三件事（首帧 / 并发上限 / 服务端吞吐）**全部发生在 `r.Static` 这一条路上**，
和 DB 一点关系都没有。所以 `cmd/staticprobe/main.go` 里那行

```go
r.Static("/static", "./.run/uploads")
```

和 `internal/http/router.go:82` 的调用**逐字相同**，参数也一样。

⚠ **诚实边界**：探针是**替身**，不是真服务。它没有 SSE 长连接、没有 outbox 轮询。
所以它量出来的是**服务端能力的上界** ——
- 如果探针都扛不住，真服务肯定扛不住
- 探针扛得住，真服务还要再验一次（但这次差距是 960 倍，结论不会翻）

## 二、网络层：这才是墙

```
--- DOWN 30MB ---  bytes=30000000 time=8.345142  speed=3594905   -> 28.76 Mbps
--- DOWN 50MB ---  bytes=50000000 time=31.599720 speed=1582292   -> 12.66 Mbps
--- UP   10MB ---  bytes=10000000 time=6.675237  speed=1498074   -> 11.99 Mbps
```

| 方向 | 实测 | 备注 |
|---|---|---|
| **上行** | **12.0 Mbps** | 一次测量，波动小 |
| 下行 | 12.7 ~ 28.8 Mbps | **两次差一倍多**，Wi-Fi 波动很大 |

### 和 Wi-Fi 链路速率的区别（重要）

```
WLAN  LinkSpeed = 144.4 Mbps     <- 这是空口协商速率，不是出网速率
```

**差 12 倍。** 这两个数经常被混为一谈，但：

- **144.4 Mbps** 是网卡和路由器协商出来的**链路层 PHY 速率**
- **12 Mbps** 是实际能把字节送出**互联网**的速率

而且 144.4 Mbps 这个数本身就偏低 —— 网卡是 Wi-Fi 6E / 160MHz（理论 2402 Mbps），
协商到 144.4 说明**连的是 2.4GHz 或信号很弱**（144.4 = 2x2 / 20MHz 的典型值）。

### 一句话

**任何"能撑多少人"的计算，都必须用 12 Mbps 算，不能用 144.4 Mbps 算。**

## 三、服务端：完全无辜

| 指标 | 实测 | 对比上行 |
|---|---|---|
| 单流吞吐 | **9.38 Gbps**（116 MB / 0.104 s） | 780× |
| **30 并发完整下载** | **30/30 成功，聚合 11.53 Gbps** | **960×** |
| CPU | **0.9 ms / MB**（约 1 核跑满） | — |
| 首帧 TTFB | **1.0 ~ 1.4 ms** | — |
| 磁盘顺序读 | 2426 MB/s = 20 Gbps | 1600× |

```
服务端能力   11.53 Gbps  ████████████████████████████████████  960×
上行带宽       12 Mbps   █                                        1×
```

**服务端差了将近三个数量级。它是无辜的。**

### CPU 那一行是"无零拷贝"的指纹

0.9 ms/MB ≈ 1 核跑满，这是**用户态拷贝**的特征。走 `TransmitFile` 的话 CPU 会低得多。

原因是查 GOROOT 发现的：

```go
// net/sendfile_windows.go
func supportsSendfile() bool { return windows.SupportUnlimitedTransmitFile() }

// internal/syscall/windows/version_windows.go
var SupportUnlimitedTransmitFile = sync.OnceValue(func() bool {
	info := getVersionInfo()
	return info.productType != VER_NT_WORKSTATION   // ← 客户端版 Windows = false
})
```

注释原文：

> Workstation and client versions of Windows limit the number of concurrent
> TransmitFile operations allowed on the system to a maximum of **two**.

**Windows 客户端版（Win10/11 Home/Pro）最多 2 个并发 `TransmitFile`，
所以 Go 干脆完全不用** —— `net/sendfile.go:23` 第一行就是 `if !supportsSendfile() { return }`。

**后果**：这台机器上每个字节都要 **2 次额外的 CPU 拷贝**（32KB 缓冲区）。

**推论**：想要零拷贝得上 Linux。**nginx on Windows 撞同一个限制** ——
所以"换 nginx"在 Windows 上买不到这一条。

### 码率：0.36 Mbps（低得超出预期）

```
n=111  avg bitrate=0.36 Mbps  avg size=38.2 MB  avg dur=14m11s
       median bitrate=0.36 Mbps
```

**这批素材是长视频**（平均 14 分 11 秒），不是短视频 —— 所以 38 MB 对应的是低码率。

0.36 Mbps 是什么概念：B站 360p 约 0.5 Mbps。**这批素材画质在 360p 以下。**

`moov` 原子（元数据）**全部在文件头**。这意味着浏览器能立刻拿到时长/尺寸开始播，
不需要先下完整个文件。

## 五、首帧时间的规律（本次最有价值的发现）

```
首帧 = RTT + 缓冲字节数 ÷ 每人分到的带宽
```

实测目标：缓冲 3 秒 = 184 KB（按 0.49 Mbps 算）

| 场景 | 每人带宽 | 首帧实测 | 算术值 `184KB ÷ 速率` |
|---|---|---|---|
| 独占上行 | 12 Mbps | **0.14 s** | 0.12 s |
| 8 人分享 | 1.2 Mbps | **1.22 s** | 1.22 s |
| 24 人分享 | 0.49 Mbps ← 该视频码率 | **3.00 s** | 3.02 s |
| 33 人分享 | 0.36 Mbps ← 平均码率 | **4.05 s** | 4.09 s |

**实测值和纯算术吻合到 0.05 秒以内** —— 这证明**服务端贡献可忽略，首帧 100% 由带宽决定**。

### 这张表是"卡"的数学定义

| 每人带宽 vs 码率 | 缓冲行为 | 结果 |
|---|---|---|
| **>** 码率 | 缓冲一直涨 | 首帧快，全程流畅 |
| **=** 码率 | **永远攒不起来** | 首帧 = 要攒的秒数，**稍有抖动就卡** |
| **<** 码率 | 缓冲一直缩 | **播到一半必卡** |

看第三、四行：3.00s / 4.05s **正好等于"3 秒缓冲 ÷ 该比例"** ——
它不是巧合，**它就是"带宽刚好等于码率时缓冲攒不起来"的直接体现**。

⚠ **这是个悬崖，不是斜坡**：24 人首帧 3 秒，25 人缓冲开始缩，**再往上就是播到一半卡住**。
TCP 公平分享让所有人一起滑过这个悬崖 —— 所以现象是"**没有一个人被拒绝，
但所有人都体验不好**"，而不是"后来者被挡在门外"。

## 六、瓶颈结论

| 层 | 实测 | 相对上行 | 会先撞墙吗 |
|---|---|---|---|
| 磁盘顺序读 | 20 Gbps | 1600× | ❌ |
| 服务端（30并发） | 11.53 Gbps | 960× | ❌ |
| Wi-Fi 空口 | ~80 Mbps 实际 | 6.7× | 仅局域网观众 |
| **互联网上行** | **12 Mbps** | **1×** | ✅ **就是这堵墙** |

### 能撑多少人

| 素材 | 码率 | 12 Mbps 能撑 |
|---|---|---|
| 这批素材（平均） | 0.36 Mbps | **33 人** |
| 这批素材（最大那条） | 0.49 Mbps | **24 人** |
| **手机原片 1080p** | 10~15 Mbps | **不到 1 人** |

⚠ **这个"33 人"是假的安全感**：

它不是架构挣来的，是**上传者碰巧传了低码率视频**。项目**没有转码**，码率 100%
由上传者决定 —— 只要有一个用户传手机原片，边界立刻塌到"一个人看都卡"。

**这才是"没有转码"的真实代价：它是个隐藏的定时炸弹，不是一个可以忽略的配置问题。**

## 七、测出来的问题

### 7.1 `/static` 完全没有任何缓存头（确认）

```
HTTP/1.1 206 Partial Content
Accept-Ranges: bytes          ✅
Content-Type: video/mp4       ✅
Last-Modified: ...            ✅
（无 Cache-Control）            ❌
（无 ETag）                     ❌
```

`206` 和 `Accept-Ranges` 都正常（Range 请求可用），但只有 `Last-Modified`。

浏览器会**猜**一个新鲜度：`(现在 − Last-Modified) × 10%` —— 不可靠、跨浏览器不一致。

**代价可以算出来**：

```
平均一个文件 38.2 MB ÷ 12 Mbps = 25.5 秒
```

**用户每刷新一次页面，就吃掉 25.5 秒的整条上行。** 10 个人各刷一次 = 4.25 分钟整条上行占满 ——
期间**所有人都在卡**。

### 7.2 `preload="auto"` 与"点了才放"的设计矛盾（新发现）

`frontend/src/components/player/VideoPlayer.vue`：

```
第 10 行：  preload="auto"      <- 告诉浏览器"立刻开始下载"
第 27 行：  <!-- 大播放键浮层。**不自动播放**...统一成"点了才放"，行为确定。 -->
```

**这两句是矛盾的。** 组件的设计意图是"用户点了才放"，但同时又指示浏览器 aggressively 预加载。
用户进播放页、看一眼、没点播放就退出 —— 这中间已经拉走了一段 38 MB 的文件。

## 八、明确**没有**测到的

- **真实外网观众的首帧**。缺 RTT：loopback 的 RTT ≈ 0，真实网络 20~50ms。
  可以忽略，但确实是缺的。
- **上行路径的实际表现**。老问题：**localhost 不过网卡**，
  本机压测走 loopback，测不出 WLAN 那一层。
  要补这个，唯一办法是**用一个不在本机的客户端**（手机连 4G/5G 访问）。
- **卡顿率**。要做真卡顿率得要真浏览器 + 远端客户端，本次只测了"首帧时间"这个代理指标。
- **Chrome `preload="auto"` 的实际预加载字节数**。7.2 的"矛盾"是客观的（代码摆在那），
  但"到底白传了多少 MB"没量 —— 需要真浏览器 + 抓包。

## 十、决策

**三个杠杆里，两个改不动：**

| 杠杆 | 能动吗 | 为什么 |
|---|---|---|
| 增加带宽 | ❌ | 12 Mbps 是运营商给的 |
| 减少单次字节 | ❌ | 素材已 0.36 Mbps（比目标还低 8 倍）；封面中位 53 KB |
| **减少传输次数／浪费** | ✅ | **唯一剩下的** |

**所以视频分发的优化只做这三件，映射到三个浪费来源：**

| # | 做什么 | 消除哪种浪费 | 成本 |
|---|---|---|---|
| 1 | `preload="auto"` → `metadata` | 用户没看就走 | **1 行** |
| 2 | 加 `Cache-Control` + `ETag` | 用户重看/刷新 | **~15 行** |
| 3 | 上传时校验码率 | 有人传手机原片 | 几十行 |

**明确不做**：

- **HLS / 转码（第 2 档）** —— **结构性无收益**。ABR 的作用是"带宽不够时降档"，
  但**素材码率已经触底（0.36 Mbps），没有更低的档可以降**。
  这不是"暂时不做"，是"在这个素材集上没有可降的空间"。
- **对象存储 + CDN（第 3 档）** —— 需要钱和外部依赖，且**没有真实的多地场景可以验证**。
- **封面压缩** —— 数据证明封面基本正常（242/245 是 1280x720，中位 53 KB），
  只有 3 个异常值（手机截图 1236x2750）。**不值得为 3 个文件做一条管线。**

**做完这三件，视频分发这块就结束** —— 剩下的瓶颈（12 Mbps）不在代码能碰到的地方。
把这个结论本身记下来，比继续堆技术更有价值。
