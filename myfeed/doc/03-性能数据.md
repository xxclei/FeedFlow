## 0. 测量纪律（读后续数字前必看）

| 项 | 约定 | 为什么 |
|---|---|---|
| **SQL 计数器** | `SHOW GLOBAL STATUS LIKE 'Com_stmt_execute'` | **绝不用 `Questions`** —— 它混进握手与 `Com_stmt_prepare`，实测报出 **1.84 / 2.10** 这种非整数 |
| **单位** | CSV 里 `p50/p95/p99` 原值是**秒**，展示时 ×1000 转 ms | |
| **压测工具** | `hey`（无状态路由）+ **自建一次性 Go 程序**（有状态路由） | 见下 |
| **有状态路由** | `like` / `comment` / `social` **hey 打不了** | 同一账号连打 8000 次，**7999 次**走的是"已点赞短路"路径，会得出"优化无效"的完全错误结论 |
| **高频压测** | 每次请求前 `DEL` 限流 key | 否则 `like_write = 30/min`、`comment_write = 10/min`、`social_write = 20/min` 会让后半段全是 429 |
| **SQL 归因** | 关键结论用 **MySQL general log 逐条归因** | 部分消费者（Timeline / Notification / OutboxPoller）跑在 **API 进程**里，停 `worker.exe` 关不掉 |
| **降级取 before** | **停掉 RabbitMQ 容器**触发同步直写 | 干净地拿到异步化之前的行为 |

### 三个会伪装成"功能坏了"的测量陷阱

1. **打错路由**：JWT 缓存第一次压测"完全没变化"，因为 `bench.bat` 打的是**公开路由** `/video/getDetail`，JWT 中间件根本没跑。
2. **无条件带 token**：`bench.bat` 对每个 POST 都发 JWT，标 `none` 的路由实际全带着 token 跑 `SoftJWTAuth.check()`（每请求 1 次 Redis GET，`cmdstat_get:calls=100` 是铁证）。
3. **worker 消费只要 ~10ms**：跑完立刻关 general log **只记到 61 条**（预期 100），必须 `sleep 3` 再关。

## 3. 反直觉 #1：防击穿锁的 100ms 悬崖 ★

200 并发 · 统计 `Com_stmt_execute` 增量。

| DB 注入延迟 | 无锁 SQL | **有锁 SQL** | 无锁 avg | **有锁 avg** |
|---|---|---|---|---|
| 0 ms | 7 | **1** | 40.8 ms | 38.8 ms |
| 60 ms | 44 | **1** | 98.6 ms | 96.0 ms |
| **150 ms** | 200 | **200（完全失效）** | 275.0 ms | **302.8 ms（比不加锁还慢）** |

**悬崖位置可以算出来**：`detailLockWaitRounds × detailLockWaitStep = 5 × 20ms = 100 ms`。

- DB 没慢到 100ms 时：锁把 **200 条 SQL 压到 1 条**，效果完美
- 超过 100ms 时：**等待轮次在 DB 返回之前就打完了** → 每个请求都自己去查 DB → 锁退化成纯粹的多余往返
- 而且因为多了一轮轮询，**比完全不加锁还慢 10%**

**修法**：`20ms × 100 = 2s`。改后 DB 慢到 150ms 时"等的人约 160ms vs 不等的人 275ms"。

> **这是全项目最值钱的一条实测** —— 因为它说明"加了分布式锁"这件事**在某些负载区间是有害的**，
> 而那个区间**可以算出来**，不靠感觉。

### 5.4 首帧公式（预测 vs 实测）

`首帧 = RTT + 缓冲字节数 ÷ 每人分到的带宽`，目标缓冲 3 秒 = **184 KB**（按 0.49 Mbps）

| 并发 | 每人带宽 | 实测首帧 | 算术预测 |

## 6. 反直觉 #2~#4

### 6.1 反直觉 #2：声明值 `BANDWIDTH` 偏乐观

最坏一格（**480p 带音轨**）**峰值段是声明值的 110%**。
→ **阶段 E 的过载预算核算不能直接用声明值**，否则每一档低估 **0~10%**。

### 6.2 反直觉 #3：`preload` 优化会让首帧变差

`preload="auto"` → `metadata` 之后：

- 浏览器不再在用户按播放之前拉**媒体数据**，只拉文件头（拿时长/尺寸）
- **首帧 `startup_ms` 变大**（要等按播放才开始拉）
- **同时白传的字节变少**

> **两个数必须一起看。** 只看首帧会得出"这个改动把播放搞慢了"的错误结论 ——
> 而真相是它把"用户没看就走"的那部分浪费消掉了。

### 6.3 反直觉 #4：QoE 的两个卡顿率指向相反的事

| 口径 | 值 |
|---|---|
| 会话口径 `stalled_sessions / total` | **28.6%（2/7）** |
| 时长口径 `stall_ratio` | **2.70%** |

**不合成一个数**，因为不一致时指向完全相反的两件事：

- 前者高后者低 = **很多次很短的卡顿**
- 前者低后者高 = **少数几次很长的卡顿**（这些人大概率直接流失了）

> 另：**`p95 = p99 = 9003 ms`（n=7）** —— n 太小时分位数退化成最大值，
> 所以这是**一次**很慢的首帧在拉高整列，不是"普遍 9 秒"。**样本太少，不下结论。**

### 9.1 看板真实数据（不是构造的）

**证伪 CTE 边界**：`video_id=177` 时 `startup.n = 4`，全局 `n = 7`（证明过滤条件写在 CTE 内部）。
**夹值验证**：超大数值被夹到 `played_ms → 86400000`、`startup_ms → 600000`。
**默认 `days: 0` = 最近 7 天**。

### 9.2 口径设计（三个容易写反的地方）

| 口径 | 选择 | 理由 |
|---|---|---|
| 卡顿判据 | **`waiting` 而不是 `stalled`** | `stalled` 要求"超过 3 秒一点都没拿到"，**更严重但更少见**；网络慢到"有数据但不够流畅"时 `waiting` 一直触发而 `stalled` 根本不触发 → 会得到**系统性偏低**的卡顿率（"看板说很流畅，用户说很卡"） |
| 首次缓冲 | **不算卡顿** | `waiting` 在第一次播放之前也会触发（那是首帧等待）。算成卡顿会同时污染两个指标：卡顿数 +1、`stallTotalMs` 里塞进整个首帧时长 |
| `timeupdate` 增量 | **卡 `0 < delta < 1` 秒** | 拖进度条会产生 3000 秒的 delta，而 `played_ms` 是卡顿率的**分母** —— 不卡上界会**静默地把卡顿率压到接近 0** |

> **已知的口径问题（未修，因为它是"定义"不是"实现"）**：
> `t0` 取的是 bind（组件挂载）时刻，而 `firstPlayingAt` 是用户**按下播放**之后才有的。
> 两者之间如果用户发呆 30 秒，`startup_ms` 就是 30 秒 ——
> 它量的是"进详情页到看到画面"，而不是"按播放到看到画面"。
> 要修就得改口径，而**口径一旦改，已记录的数据就不可比了**。
