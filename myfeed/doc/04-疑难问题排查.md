## 1. `java` 搜不到但 `redis` 搜得到 ★★★

### 症状

搜 `java` / `Java` / `JAVA` **全部 0 条**，而库里 **103 条**标题就以 `java-redis…` 开头。
搜 `redis` **正常返回**。前端显示"没有找到相关视频"——
**没有任何报错、日志、异常。**

### 根因（四层，每层都能单独让人查不出来）

**（1）索引里没有含字母 `a` 或 `i` 的 bigram。**

`ngram_token_size=2` 时每个 token 都是 bigram，而 InnoDB 默认停用词表里
**有单字母 `a` 和 `i`**（另有 14 个两字词 `an/as/at/be/by/de/en/in/is/it/of/on/or/to`）。
ngram 的"含停用词"判定是**子串**判定 —— 于是含 `a` / `i` 的 bigram 整条被丢掉：

```
"java"   → ja / av / va          三个全含 a，**全丢** → 一个字都搜不到
"banana" → 同理，全丢
"redis"  → re ✓ / ed ✓ / di（含 i）✗ / is（本身是停用词）✗ → 还剩两个，能搜到
```

**所以"java 搜不到、redis 搜得到"不是巧合也不是数据问题，是这条规则。**

隔离探针表实测：`ab de di is iq ja av va ad` 全 0，
`bc cd ef gh yz re ed qj jv` 全命中；把 `innodb_ft_enable_stopword` 关掉之后**全部命中**。

**（2）建索引时关了停用词，但紧接着被 `OPTIMIZE TABLE` 开着停用词重建了一遍。**

`search_index.go` 一直有 `SET SESSION innodb_ft_enable_stopword = OFF`，写对了；
问题是它和 `OPTIMIZE TABLE videos` **不在同一条连接上** ——
`db.Exec` 从池里拿到的是默认 `ON` 的连接。

而 InnoDB 的 `OPTIMIZE TABLE` 是 `ALTER TABLE … FORCE` 的映射，
**整表重建、包含全文索引**，重建时按**当前会话**的设置切词。
MySQL 自己会说这句：`Table does not support optimize, do recreate + analyze instead`。

**即"建好"之后被"重建成坏的"**，`SET SESSION` 那一行等于没写。

**（3）索引一旦建错就永久错下去。**

`EnsureFulltextIndex` 当时只做"不存在才建"，索引存在就直接 `return nil`，
只打一句"解析器未能自动校验，请人工确认一次"—— **而没有人会去人工确认**，
所以这句警告在启动日志里躺了很久。

**（4）最后一公里：零命中被当成"库里没有"。**

`LexicalSearcher.Search` 只有 AND→OR 两档，两档都空就返回空列表。
**空集的语义是"没有这个视频"，而真实原因是"检索不可信"—— 两者长得一模一样。**

### 为什么难查

- 全程**零报错**：不是崩溃、不是异常，是"正确地返回了一个空集"
- **"java 搜不到、redis 搜得到"这个现象本身没有因果味** ——
  看起来像数据问题（"是不是没有 java 的视频"）或分词问题（"是不是不支持英文"）
- 真凶是**索引的内容**，而索引不对外可见。除非专门去查 `MATCH ... AGAINST`，
  从外部看到的永远只是"搜索没结果"

### 修法

1. **把写索引内容的三步钉在同一条连接上**：`SET … OFF` / `DROP+ADD` / `OPTIMIZE`
   全塞进同一个 `db.Connection` 闭包，恢复会话变量用 `defer`（中间任何一步 return 都不会跳过它）。
2. **让索引自己记着配方**：`ALTER TABLE … WITH PARSER ngram COMMENT 'myfeed-ft:ngram-n2-sw0'`，
   启动时读 `information_schema.STATISTICS.INDEX_COMMENT` 和当前应有的配方比，
   **不一致就重建**。配方里带 `ngram_token_size`，因为它是全局变量，改了不会报错、只会让已有索引搜不出东西。
3. **给 LIKE 补第三档**：AND → OR → **LIKE 兜底**，报新 mode `like-fallback`。
   走到那一档说明"索引连一条都没命中"，而 LIKE 不看索引，是唯一还能给出正确答案的手段。

### 验收

| | 修前 | 修后 |
|---|---|---|
| `MATCH … AGAINST('java')` | **0** | **103** |
| `MATCH … AGAINST('di')` | **0** | **104** |
| `POST /feed/search {"query":"java"}` | 0 条 | **50 条** |

兜底那一档单独验过：故意用"停用词 ON + 写上正确指纹"制造一个**指纹看不出来**的坏索引，
搜索仍然返回 50 条，日志打 `全文索引零命中，LIKE 兜底救回 50 条 —— 索引可疑`。

### 教训

> **① `SET GLOBAL innodb_ft_enable_stopword = 0` 不影响当前会话** ——
> 用它验证会得到"改了也没用"的假结论（我自己先踩了一次，白查了一轮）。
>
> **② 指纹只能保证"没被建错"，保证不了"没被建坏"。** 所以第 3 条兜底不是重复劳动。
>
> **③ 最值钱的一句**：*空集的语义是"没有这个视频"，而真实原因是"检索不可信" —— 两者长得一模一样。*
> 一个返回错误答案但不报错的系统，比一个崩溃的系统难查一个数量级。

## 2. `crypto.randomUUID is not a function` ★★★

### 症状

上云当天，**选完文件点上传，队列里一个条目都不出现**。控制台：

```
_plugin-vue_export-helper-BMK0NYmP.js:1 TypeError: crypto.randomUUID is not a function
    at Proxy.v (index-DB-n4dyN.js:3:44035)
    at HTMLInputElement.n (index-DB-n4dyN.js:2:6049)
```

### 根因

**`crypto.randomUUID()` 只在安全上下文里存在。**
安全上下文 = `https://`、`localhost`、`127.0.0.1`、`file://`。

除此之外（包括 `http://192.168.x.x` 和 `http://<公网IP>`），
**`crypto` 这个对象在，但 `randomUUID` 这个方法根本没挂上去。**

### 为什么难查

**① 它在本地永远测不出来 —— 这是最关键的一点。**

本地开发跑在 `localhost` 上，而 **localhost 被浏览器特批为安全上下文**。
所以这一条在本机**永远测不出来**，它是"上云"这个动作本身带出来的，不是代码新引入的。

**② 报错跟"网络"毫无关系，但一换地址就出现。**

第一反应很容易跑去查 nginx 和后端配置（**这次就查了半天**），
而真凶在浏览器的一个 API 可用性规则里。

**③ 这个项目已经因此炸过两次，而且第一次的注释写得很准。**

`useQoE.ts` 里原本有一句注释：
> "有人用局域网 IP 访问的话，整个播放器会因为一个埋点字段而崩"

写得完全正确 —— 但**兜底只写在了那一个调用点上**，上传队列那一处**忘了**。

### 修法

不是打补丁，是**把兜底逻辑从调用点抽出来**：

```
frontend/src/utils/uuid.ts    ← newId()：优先 randomUUID，退到 16 字节随机 hex
frontend/src/composables/useQoE.ts      → 改用 newId()
frontend/src/stores/uploadQueue.ts      → 改用 newId()
```

抽出来的理由是：**"兜底写在每个调用点上，就是会漏"** ——
一个文件写了、另一个文件忘了，而忘了的那个**只在非安全上下文（也就是只在线上）暴露**。

抽出来后可以随时跑这条检查：

```bash
grep -rn 'crypto\.randomUUID' frontend/src/
# 应该只剩 utils/uuid.ts 一处。多出来的每一处都是下一个待炸点。
```

> 顺带一提：退化的第一档是 `crypto.getRandomValues`，它**不受**安全上下文限制
> （不涉及密钥派生，所以没被闸住）—— 也就是说在 http 下这条路依然是通的，
> 真正兜底的只有 `Math.random` 那一支。

### 教训

> **"知道这个坑"和"每个地方都处理了"是两件事。**
> 前者只保证你写对一处；后者要求你**把知识放进一个不可能被绕过的地方**。

## 3. `Cannot read properties of null (reading 'reduce')` ★★

### 症状

上传某个文件时报：

```
Cannot read properties of null (reading 'reduce')
```

发生在 `chunkUploader.ts` 的 `init.uploaded_chunks.reduce(...)`。

### 根因

`UploadedChunks()` 里的 `var indices []int`，**零次 `append` 时返回 nil**，
而 **Go 的 nil slice 会被 `encoding/json` 编成 `null`，不是 `[]`**。

触发路径**很窄但很真实**：

1. 会话建好了、**却一片都没落到盘上**（第一次传就断了）
2. 然后重试
3. 重试时 `InitChunkUpload` 命中断点续传分支（`file_hash` 相同、分片几何一致）
4. 走的就是这个函数 —— 此时 `UploadedBits` 全是 `false`，
   循环里那个 `append` **一次都没执行**，于是 `indices` 原样返回 nil

### 为什么难查

- **报错信息（"reading 'reduce'"）指不到是哪个字段**，更指不到后端
- 触发条件叠加了两个"窄"：会话存在 **且** 落地块数为零
  —— 正常上传永远碰不到，只有"失败后重试"这个组合才出现
- 前端拿到的 `null` 和 `[]` 在 JS 里都能 `.length` 吗？不能，但**只有 `.reduce` 才炸** ——
  如果当初写的是 `for (const i of uploaded_chunks)`，`null` 同样会炸；
  如果写的是 `uploaded_chunks?.length`，就**静默地少传一片**

### 修法（两端都改）

**后端 —— 修在函数内部，不是修在调用点：**

```go
func (s *ChunkUploadSession) UploadedChunks() []int {
    indices := make([]int, 0, len(s.UploadedBits))   // ← 永远非 nil
    for i, uploaded := range s.UploadedBits {
        if uploaded { indices = append(indices, i) }
    }
    return indices
}
```

**前端 —— 保留一层兜底：**

```ts
const uploadedChunks = init.uploaded_chunks ?? []
```

### 教训

> **同一个 handler 里"新建会话"那条路（`chunk_handler.go:200`）特意写了 `[]int{}`** ——
> 说明这个坑当初是**知道**的，只是没落在函数内部。
>
> **"知道这件事"和"每一个返回点都做对"是两件事。**
> 写进函数里，两个调用点就同时对了；写进调用点，就只对了那一处。
>
> 前端留兜底的理由不是"不信任后端"，而是：**这里没有中间地带** ——
> `null` 进来，`reduce` 抛异常，整个文件的上传当场死掉。
> 兜底买到的是"最坏情况退化成重传一遍"，而排查成本远大于那一行。

## 4. 加了分布式锁反而更慢 ★★★

### 症状

写了个防缓存击穿的分布式锁，在正常情况下效果完美（200 并发下 SQL 从 7 条压到 1 条）。
但**在某些负载下，它的效果完全消失，而且比不加锁还慢**。

### 根因

200 并发，数 `Com_stmt_execute` 增量：

| DB 注入延迟 | 无锁 SQL | **有锁 SQL** | 无锁 avg | **有锁 avg** |
|---|---|---|---|---|
| 0 ms | 7 | **1** | 40.8 ms | 38.8 ms |
| 60 ms | 44 | **1** | 98.6 ms | 96.0 ms |
| **150 ms** | 200 | **200（完全失效）** | 275.0 ms | **302.8 ms（更慢）** |

**悬崖位置可以精确算出来**：`detailLockWaitRounds × detailLockWaitStep = 5 × 20ms = 100 ms`

锁的实现是"拿不到锁就等 20ms 再试，最多试 5 轮"。
当 DB 慢到 **150ms** 时，**等待轮次在 DB 返回之前就打完了** ——
每个请求试完 5 轮放弃、然后自己跑去查 DB，于是：
**锁退化成了纯粹多余的一轮轮询**，SQL 一条没省，还多花了 100ms 的等待。

### 为什么难查

- 锁**在低延迟下工作得非常好**，任何"正常"的验证都会显示它有效
- 失效的区间是**由两个配置常量的乘积决定的**，而这两个常量写在两个不同的地方
- 表现是"**性能没有改善**"而不是"**功能坏了**" —— 没人会去排查一个"没变差"的改动

### 修法

把等待预算改成 `20ms × 100 = 2s`。改后 DB 慢到 150ms 时
"等的人约 160ms vs 不等的人 275ms"。

### 教训

> **分布式锁的等待预算必须大于"最坏情况下 DB 的响应时间"，而那个值不是感觉出来的，是可以从两个配置算出来的。**
>
> 更要紧的是：**"加了锁"这件事在某些负载区间是有害的**，而那个区间可以算出来。
> 如果只测轻负载，会带着一个"在高负载下放大会变成负优化"的实现上线。

## 5. 「缺少文件指纹」 ★★

### 症状

上传队列里某一行直接落 `失败 / 缺少文件指纹`。

### 根因

**`queued` 这个状态有两个来源，`drain()` 分不清**：

| 来源 | 含义 |
|---|---|
| 指纹算完了 | **可以传了** |
| `addPicked` 创建时的初始状态 | **那时指纹还不存在** |

`drain()` 只认 `state`，于是没算过指纹的 item 也会被捞进上传阶段。
三条能造出来的路径：

| | 触发 |
|---|---|
| α | **算指纹/上传途中再补选文件** —— `hashPass()` 撞上"已有一轮在跑"，老写法 `if (hashRun) return hashRun` 直接把**那一轮**的 promise 还了回来；而那一轮是 `for (const it of items.value)`，数组对象在循环开始就定死，`concat` 是**换新数组** → 新文件对它彻底隐形 |
| β | **暂停 → 继续** —— `pause()` 会 `hashAc.abort()`，循环里每个 item 立刻抛 AbortError → 全部退回 `queued`（**一个指纹都没有**）；而 `resume()` 只 `wake()`，没重跑哈希 → 必现整批失败 |
| γ | **对循环已越过的 item 点重试** —— `retryItem` 置 `queued` 后 `await hashPass()`，撞上同一轮陈旧 promise，而它按数组顺序早被跳过了 |

### 修法（四处）

1. `runHashPass` 改成 `for(;;)` + **每轮重新 `find` 活数组**，
   判据从 `state === 'queued'` 换成 `state === 'queued' && !prints.has(id)`
   —— **只有 `prints` 能回答"这一个到底算过没有"**
2. `hashPass()` 从"有在跑就返回它"改成**串成一条链**（`hashChain = hashChain.then(run, run)`）
3. `resume()` 走 `hashPass().then(wake)`
4. `drain()` 加兜底闸门：捞到的 `queued` 若没有指纹，不跑它，改成 `void hashPass()` 推回哈希通道

### 教训

> **一个状态字段承载两种语义，是并发 bug 的温床。**
> `queued` 想问两个问题 —— "能不能传"和"算过没有" ——
> 而这两个问题的答案**不由同一个数据源决定**。
>
> 修法不是"多判一个条件"，而是**把两个问题分开**：
> "能不能传"看 `state`，"算过没有"看 `prints`。

## 6. 算完指纹还在干等 ★

### 症状

批量选了 20 个大文件，界面上每个文件都显示"排队中"，
**没有任何一个开始上传**，而且**第 1 个文件要等最后一个文件的指纹算完才动**。

### 根因

```ts
await hashPass()    // ← 顺序遍历，循环体里没有 wake()
wake()
```

`runHashPass()` 是顺序遍历、循环体里**没有** `wake()`。
后果：**完全没有流水线** —— 20 个 500MB 的文件 = **先顺序读完 10GB**，
而且每个算完指纹的行都被置成 `queued` / `排队中` 然后干等。

### 修法

原来那么写是为了按内容指纹判重（同哈希会塌进同一个 upload_id）。
但**判重只要求"自己算完"，不要求"别人也算完"**：
改成边算边往 `Map<fileHash, item>` 里登记，算出这一个的瞬间就能定它是不是重复，然后立刻 `wake()`。

判重发生在置成 `queued` **之前**，所以 `drain()` 不可能先抢走一个本该是 duplicate 的文件。

**配套加了一条护城河**：`markDuplicates()` 遇到 `state === 'duplicate'` 直接 `continue`。
不加的话，一个已被增量判成 duplicate 的 item 会在收尾那趟里被登记成 leader，
于是它和它真正的 leader **互相指认 → 环形等待，两个都不传**。

### 教训

> **这是增量判重才会出现的问题，老的"一趟定生死"写法碰不到。**
> 优化一个流程的顺序时，要重查它原本依赖的隐含前提 ——
> 原来"必须整批算完"是那个简单实现**顺带**提供的保证。

## 7. 应用连不上 MySQL 了 ★★

### 症状

一次 16 种模式 × 8000 请求的压力扫描跑到一半，
**应用开始返回 500，日志里连 MySQL 都拨不出去**。

### 根因

`TIME_WAIT` 从 **1687 推到 15502**，而 **Windows 动态端口段只有 16384**。

连接池**没有配置**（`SetMaxOpenConns` / `SetMaxIdleConns` 都是默认值），
每条 SQL 都可能新建一个连接，短时间内耗尽本地端口。

### 为什么难查

- 报错是"连不上数据库"，**指向数据库**，而真凶在**客户端操作系统的端口分配**
- 数据量大时才出现 —— 小规模压测完全正常
- `TIME_WAIT` 是**累积**的，跑得越久越容易撞上

### 修法

`SetMaxOpenConns(50)` + `SetMaxIdleConns(50)`。

### 教训

> **"连不上数据库"的第一反应通常是查数据库，但连接是双向的。**
> 客户端资源耗尽的症状和数据库故障一模一样。

## 8. SSE 首字节 30 秒 ★★

### 症状

SSE 长连接在浏览器里**要等 30 秒才收到第一帧**。

### 根因

| | 首字节 |
|---|---|
| 直连 `127.0.0.1:8080` | **0.07 s** |
| 经 `localhost:5173/api`（vite 代理） | **30.02 s** |

**卡了整整一个 keepalive 周期。** 而应用侧的 keepalive 是 30s。

### 为什么难查

**这个坑在直连测试里永远看不到 —— 只有走浏览器那条路才会暴露。**

我当时是用 `curl` 直连后端测的，`0.07s`，全绿，于是得出了"SSE 正常"的结论。
**而真相是代理那一层在缓冲响应。**

### 修法

SSE 响应头必须显式禁掉中间层的缓冲（`X-Accel-Buffering: no` /
`proxy_buffering off`），且 `proxy_read_timeout` 要大于 keepalive 周期。
修后直连 0.06s / 经 vite **0.03s**。

### 教训

> **这一族问题在本项目里出现了 3 次**：
> ① SSE 经代理缓冲（本案例）② Windows curl 把中文按 GBK 发出去、看起来像后端乱码
> ③ 直连测不到代理那一层。
>
> **共同点：直连测试全绿，会得出"功能正常"的错误结论。**
> 只要链路里有代理 / 网关 / CDN，"直连测过了"就**不算测过** ——
> 流式响应还要另测"首字节时间"，不能只测"最终有没有收到"。

## 9. 新视频永远排在旧视频后面 ★★

### 症状

上云后（迁移了旧数据），**新上传的视频永远排在旧视频后面，翻到第一页看不见自己刚传的东西**。

不报错、零日志。

### 根因

DSN 是 `...&parseTime=True&loc=Local`，而**全项目没有一处设置 `time.Local` 或 `TZ`**。
开发机是 UTC+8，**官方 `golang` / `debian` / `mysql` 镜像默认都是 UTC**。

- 迁移过来的旧数据：`create_time` 是 **UTC+8 的墙钟字面量**
- 上云后新写入的：**UTC 墙钟**，比旧数据**早 8 小时**

而 feed 是按 `create_time DESC` 排序的 → **旧的排前面**。

> 从数据库角度看，**旧数据全部"来自未来"**。

### 修法

**两边必须一起设**：`TZ=Asia/Shanghai` 设在 **api、worker、mysql 三个容器**上，
**并且运行镜像里必须装 `tzdata`** —— 否则 `TZ` 环境变量会被忽略、`time.Local` 仍是 UTC，**设了等于没设**。

> 宁可两边都不设（都是 UTC，自洽），也不要只设一半。

### 教训

> **时区问题的特征是：它不产生错误，它产生"看起来对但顺序错了"的数据。**
> 而排序是 feed 的全部意义。
>
> "墙钟字面量 + `loc=Local`"这个组合，把时区责任推给了**运行环境**，
> 而运行环境在容器化时被换掉了。

## 10. `mode` 恒为 `lexical-only`（可观测性缺口）

### 症状

前端调试面板上，检索的 `mode` 字段**永远是 `lexical-only`**，
`ngram` / `ngram-or` / `like` / `like-fallback` 一个都不会出现。

### 根因

`service.go` 那段 switch 在 `runVec=false` 时**直接给 `lexical-only`**，
**丢掉了词法那一路自己的形态**。而向量那一路没接线，`runVec` 恒为 false。

### 代价

**"搜索为什么搜不到"少了一个现成读数。**
第 1 号案例（`java` 搜不到）要是能一眼看到 `like-fallback` 会好查得多 ——
那说明索引是坏的，而不是"库里没有"。

### 修法（未做）

给 `Result` 加一个 `lexical_mode` 字段 —— **别改 `mode` 的语义**，
`mode` 回答的是"哪几路跑了"，两个维度是正交的。
且 **`Mode` 会被冻结进游标**，`cursor.go` 要一起改。

### 教训

> **可观测性缺口不会让功能失效，所以永远不会被测试发现** ——
> 它只在**下一次排查**的时候收利息。
>
> 修它的正确姿势是**加一个正交的字段，而不是改现有字段的语义**：
> 把两种信息挤进一个字段，两个都会变得不可靠。

## 11. 手滑删别人的视频就被静默登出 ★

### 症状

点别人视频的删除键 → **被静默登出**。

### 根因

后端删别人的视频返回 **401**，而前端 `client.ts:214` 对**任何** 401 都 `clearTokens()`。

401 的语义是"你没登录"，403 的语义是"你登录了但没权限"。
**用 401 表达权限不足，等于告诉客户端"你的凭证失效了"。**

### 修法

改成 403（评论模块当初为完全相同的理由已经改过一次，这次对齐）。

### 教训

> **HTTP 状态码不是给人看的描述，是给客户端程序的指令。**
> 客户端会对它做自动行为（刷新 token、清凭证、重试），
> 所以**用错状态码 = 触发客户端的错误自动行为**。

## 12. 「全部时间」实际是最近 7 天（零值歧义）

### 症状

QoE 看板的"全部时间"选项，传 `days=0`，**实际只查了最近 7 天**。
看板上完全看不出来。

### 根因

后端把 `0` 解释成"用默认值 7 天" ——
**Go 的零值既表示"没传"也表示"我就要 0"，那边选了"零值即默认"。**

### 修法

全部时间只能传**负数**（前端用 `-1`）。

### 教训

> **任何想表达"不限时间"的地方传了 0，都是一个静默的 7 天。**
>
> 零值歧义是 API 设计的经典坑：一旦某个字段的零值被赋予了"默认"的含义，
> 它就**再也无法表达零值本身**。

## 13. 解码器泄漏 ★

### 症状

「我的作品」页面，作品一多，**页面变卡、内存上涨**。

### 根因

以前每个作品挂一个 `<video preload="none">` —— 作品一多就是几十个解码器常驻。
而 **Chrome 对同时活跃的 video 元素有硬上限（约 75 个）**。

### 修法

- 卡片上的封面改成 **canvas 抽帧后上传的静态图**，不再用 `<video>`
- 播放器卸载时必须 **`pause()` + `removeAttribute('src')` + `load()`** ——
  **三步缺一不可**，只靠组件销毁元素会一直攥着解码器
- 结果：**整个应用只剩一个真 `<video>` 元素**（详情页那个），加上抽帧时临时创建的一个

### 教训

> **`preload="none"` 不等于"不占资源"** —— 它只是不预加载数据，
> 元素本身和它的解码器仍然存在。
>
> 顺带一个反向的坑：**别用 `<KeepAlive>` 解决"返回列表丢状态"** ——
> 被 deactivate 的组件**不会触发 `onUnmounted`**，
> 播放器那三步释放就静默不跑了，正好制造这个泄漏。

## 14. MQ 恢复 20 秒后仍降级（未修）★

### 症状

RabbitMQ 容器恢复之后，应用**仍然停留在降级（同步直写）状态**，
过了 20 秒也没有恢复。

### 根因

所有"5 秒后重连"的循环在**空转**。
`amqp.Dial` 在**整个包里只出现一次** —— 也就是说重连逻辑走到了别的地方，没有真正重建连接。

### 状态

**未修**，记录在 `PROGRESS.md`。影响是"MQ 短暂抖动后会长期停留在降级路径上"，
业务不挂（降级是完整的），但异步化的收益会一直拿不到。

### 教训

> **降级路径太完整，会掩盖降级本身。**
> 因为降级之后功能一切正常，**没有任何症状提示"你现在跑在降级上"**。
>
> 这类"降级看不到"的问题，标准解法是**把降级状态暴露成一个可观测指标**
> （日志、`/healthz` 里的字段、看板），而不是让它安静地工作。

## 附：几次测量方法本身的翻车（不是产品的 bug）

这些不进产品代码，但**比产品 bug 更值钱** —— 因为它们会让你对**没有 bug 的代码**做出错误结论。

| # | 翻车 | 错误结论 |
|---|---|---|
| 1 | 用 `Questions` 当 SQL 计数器 | 报出 **1.84 / 2.10** 这种非整数才发现不对（它混进握手和 `Com_stmt_prepare`） |
| 2 | JWT 缓存压测打的是**公开路由** | "JWT 缓存完全没变化" —— 中间件根本没跑 |
| 3 | `bench.bat` 对每个 POST **无条件发 token** | 标 `none` 的路由实际全带着 token 跑软鉴权（`cmdstat_get:calls=100` 是铁证） |
| 4 | **没清限流桶** | comment publish ×20 得到 **10 个 200 + 10 个 429**；social 连打 10 次 follow **只有第 1 次成功** → 得出"social 只要 3.1 条 SQL"的错误结论 |
| 5 | 用 hey 打有状态路由 | like 跑 8000 次，**7999 次走"已点赞短路"** → "优化前后都是 2 条 SQL，MQ 没用" |
| 6 | general log 跑完立刻关 | worker 消费只要 **~10ms**，只记到 **61 条**（预期 100）。必须 `sleep 3` |
| 7 | 总数相减做 SQL 归因 | 被后台消费者污染 —— `TimelineConsumer` / `NotificationWorker` / `OutboxPoller` **都在 API 进程里**，停 `worker.exe` 关不掉 |
| 8 | RabbitMQ 管理 API 查队列条数 | 立刻查 `probe.events=1 / probe.events.dlx=0`（"像死信完全没工作"），**等 8 秒**再查变 `0 / 2` —— `collect_statistics_interval` 滞后 5000ms |
| 9 | 种错缓存 key（`v1:video:detail:383` 漏了 `id=`） | 请求返回了**正确值**，看起来像"这个 bug 不存在" |
| 10 | 测试断言写错了字面量 | "**不只没用，还挡住了它要找的东西**" |
| 11 | 直连测 SSE | 全绿，得出"SSE 正常"的结论（见案例 8） |
| 12 | 用 `SET GLOBAL` 验会话变量 | "改了也没用"的假结论（`SET GLOBAL` 不影响当前会话） |

> **共同的教训**：
> **① 计数器 / 路由 / 前置条件只要错一个，"优化无效"的结论就完全错误，而且看不出错误。**
> **② 测量代码里的 bug 比产品代码里的 bug 更危险** —— 产品 bug 会让你看到错误的结果，
> 测量 bug 会让你**相信一个错误的结论**。
