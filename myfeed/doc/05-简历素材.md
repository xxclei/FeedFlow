## 三、✅ 可以直接写（数字有据、口径清楚）

### 规模

- Go 后端 **98 文件 / 22,219 行**，Vue3 + TS 前端 **63 文件 / 13,402 行**，合计约 **3.6 万行**
- **45 个 REST API**，**18 个**后端模块，**12 个**前端页面，**6 条** MQ 业务链路

### 缓存（阶段 7）

- **视频详情缓存：SQL 1.00 → 0.00 /req，QPS 4944 → 21648（+338%），p50 15.9ms → 2.9ms**
  —— 且 21648 正好落回 `/healthz` 的 21454，说明数据库开销被**完全消除**
- **最新流三级缓存（ZSET 冷热分离）：QPS 3563.96 → 4391.36，p50 21.7 → 17.7ms**
- **关注流缓存：SQL 1.00 → 0.00 /req，QPS 4054.84 → 5265.30（+30%），p50 19.2 → 14.3ms**
- **微优化：调换两条 Redis 命令的顺序，砍掉 1 次往返 → QPS +9.4%**，
  用 `INFO commandstats` 精确验到 2 条命令/请求
- 建立基线：**0 条 SQL 时 21454 QPS，每多一条 SQL 掉到 ~5000** → 缓存生效的判据是"落回基线"

### 异步化（阶段 9）

- **点赞 MQ 异步化：请求侧写延迟 15.74 → 4.35ms（−72%）**，
  p50 −73% / p95 −75% / p99 −73%
- **同时实测出端到端 15.66 → 18.53ms（+18%）、系统总 SQL 11 = 11**
  → 结论：**"异步不是优化，是重排"**，真正买到的是**缩短请求路径 + 抗下游抖动**
- **对比两条范式**：评论链路请求侧 SQL **−60% ~ −67%**，关注链路 **0%**（一条没省）
  → **省不省取决于原来有没有跨表事务，不取决于"用没用 MQ"**
- 交叉验证：`Com_stmt_execute` 差值 **341**，与预测值 `30 × (6+5) + 预热` **分毫不差**
- **Outbox 首次端到端**：245 条 pending → 分三批 **100/100/45** 投完，`ZCARD` = 245

### 检索

- **`FULLTEXT + ngram` 检索缺陷修复：`MATCH AGAINST('java')` 从 0 → 103 条，
  `POST /feed/search` 从 0 → 50 条**
- 根因：InnoDB 默认停用词表含**单字母 `a` / `i`**，含它们的 bigram 在索引期被整条丢弃
  （`java` → `ja/av/va` 全丢；`redis` → `re/ed` 存活）
- 叠加根因：`OPTIMIZE TABLE` 在**另一条连接**上用错误的会话变量把索引重建坏了
- 修法：**索引自记配方指纹**（`INDEX_COMMENT`）+ **三档降级（AND → OR → LIKE 兜底）**

### 并发 / 性能反模式

- **实测出分布式锁的失效悬崖**：等待预算 `5 轮 × 20ms = 100ms`，
  DB 延迟 ≥150ms 时锁**完全失效且比不加锁更慢**（275ms → 302.8ms）；改为 2s
- **定位 Windows 端口耗尽**：`TIME_WAIT` 1687 → **15502**，超过动态端口段 16384 后
  应用连 MySQL 都拨不出去；修法 `SetMaxOpenConns(50)` + `SetMaxIdleConns(50)`

### 部署（阶段 10）

- **Docker 多阶段构建 + Docker Compose 单栈部署到公网**（腾讯云轻量应用服务器，IP + 80 端口）
- **只有 nginx 发布端口**，MySQL / Redis / RabbitMQ 全部 `expose` 走内网
- 补 `http.Server` + `signal.NotifyContext` 优雅关闭（原来 `gin.Run` 下
  三个 `defer` 全不执行、正在投递的 outbox 批次被腰斩、SSE 全硬断）
- **发现并修复 `JWT_SECRET` 为空时回落到硬编码默认密钥的安全隐患**（且原实现不打印任何警告）
- **发现并修复容器时区导致的 Feed 排序错乱**（新视频永远排在旧视频后面，不报错零日志）

### 只在生产暴露的缺陷（两条）

- **`crypto.randomUUID is not a function`** —— 该 API 只在安全上下文（https / localhost）存在；
  本地 `localhost` 被浏览器特批为安全上下文，**这是"上云"这个动作本身带出来的 bug**
- **`Cannot read properties of null (reading 'reduce')`** —— Go 的 nil slice 被
  `encoding/json` 编成 `null` 而不是 `[]`

### 播放链路（扩展）

- **转码三档 HLS（1080p / 720p / 480p），码率保真度 93.8% ~ 106.7%**，
  峰值段不超过均值的 103%
- 45MB 素材转码 **5.308s**，产出 29.3MB / 19 文件；**幂等重投 7ms**
- **前端动态 `import` 分包：`VideoDetailView` 597.46 kB → 22.58 kB（首屏体积降 26 倍）**，
  `hls.js` 独立 chunk 574.74 kB，按播放才构造
- **定位分发瓶颈**：服务端单流 9.38 Gbps、30 并发聚合 11.53 Gbps（**960× 于需求**），
  而真正的瓶颈是 **12 Mbps 上行**；首帧公式 `RTT + 缓冲 ÷ 人均带宽` 预测与实测**吻合到 0.05 秒以内**
- **识别出"能撑 33 人"是假的安全感** —— 135 条素材里 128 条是 1080p 却只有
  0.16~1.16 Mbps，**分辨率与码率脱钩**
- QoE 埋点与看板：7 次真实会话、`stall_ratio` 2.70%、首帧 p50 1437ms

## 六、面试最值得讲的 5 个故事

按"含金量 / 别人讲不出来"排序。

### 故事 1：我优化了一次，然后把结论推翻重写了 ★★★

**问题**：点赞是同步写事务，一次要打 6 条 SQL，写延迟 15.7ms。

**做法**：改成 MQ 异步落库（Outbox + Worker）。

**结果**：写延迟 **15.74 → 4.35ms（−72%）**，看起来是大胜。

**然后我继续测了两个数**：

- **端到端** 15.66 → **18.53ms（+18%）**
- **系统总 SQL** 11 → **11（没变）**

**结论**：**异步不是优化，是重排。** 请求侧的 SQL 从 6 降到 2，但代价搬到了 worker；
总工作量一点没少，端到端因为多了两次 MQ 往返反而更慢。
异步真正买到的是**请求路径变短（DB 连接占用时间下降）+ 抗下游抖动**。

**加分点**：我还做了**范式对比** —— 评论链路请求侧 SQL 降 60~67%，
但关注链路**一条都没降**（因为关注原本就没有跨表事务）。
所以**省不省取决于原来有没有跨表事务，不取决于"用没用 MQ"**。

> **面试官想听的是"你以为你优化了，然后你证明了自己没优化"。**
> 这个项目里我还测出过另外两次无效/负优化：分布式锁在 DB 延迟 ≥150ms 时
> **比不加锁还慢 10%**；`preload` 优化会让**首帧指标变差**（同时白传字节变少）。

### 故事 2：`java` 搜不到，但 `redis` 搜得到 ★★★

**症状**：搜 `java` / `Java` / `JAVA` 全部 **0 条**，而库里 **103 条**标题就以
`java-redis…` 开头；搜 `redis` **正常**。**零报错、零日志、零异常。**

**排查**：建隔离探针表逐一验证 `ab de di is iq ja av va ad` **全 0**，
`bc cd ef gh yz re ed qj jv` **全命中**；关掉 `innodb_ft_enable_stopword` 后**全部命中**。

**根因（四层，每层都能单独让人查不出来）**：

1. **InnoDB 默认停用词表里有单字母 `a` 和 `i`**。`ngram_token_size=2` 时每个 token 都是 bigram，
   而 ngram 的"含停用词"判定是**子串**判定 ——
   `java` → `ja / av / va` **三个全含 a，全丢**；`redis` → `re / ed` 存活。
2. **建索引时关了停用词，但紧接着被 `OPTIMIZE TABLE` 开着停用词重建了一遍** ——
   因为 `SET SESSION` 与 `OPTIMIZE` **不在同一条连接上**。而 InnoDB 的 `OPTIMIZE` 是
   `ALTER TABLE … FORCE`，整表重建包含全文索引，按**当前会话**切词。
   **即"建好"之后被"重建成坏的"。**
3. **索引一旦建错就永久错下去** —— 当时的实现只做"不存在才建"。
4. **零命中被当成"库里没有"** —— 空集的语义是"没有这个视频"，
   而真实原因是"检索不可信"，**两者长得一模一样**。

**修法**：

1. **三步钉在同一条连接上**（`SET` / `DROP+ADD` / `OPTIMIZE` 塞进同一个 `db.Connection` 闭包，
   恢复会话变量用 `defer`）
2. **让索引自己记配方**：`ALTER TABLE … WITH PARSER ngram COMMENT 'myfeed-ft:ngram-n2-sw0'`，
   启动时读 `information_schema.STATISTICS.INDEX_COMMENT` 比对，不一致就重建
3. **给 LIKE 补第三档兜底**（AND → OR → LIKE），走到那一档说明索引可疑，
   而 LIKE 不看索引，是唯一还能给出正确答案的手段

**验收**：`MATCH AGAINST('java')` **0 → 103**；`POST /feed/search` **0 → 50 条**。

**加分点**：我还**故意造了一个"指纹看不出来"的坏索引**，验证兜底那一档仍然能救回 50 条。

> **最值钱的一句**：*指纹只能保证"没被建错"，保证不了"没被建坏"。*
> 所以第 3 条兜底不是重复劳动 —— **一个返回错误答案但不报错的系统，
> 比一个崩溃的系统难查一个数量级。**

### 故事 3：加了分布式锁，反而更慢 ★★★

**做法**：为防缓存击穿写了分布式锁（拿不到就等 20ms 重试，最多 5 轮）。

**验证**：200 并发下数 `Com_stmt_execute`，正常情况下 SQL 从 7 条压到 **1 条**，效果完美。

**然后我把 DB 延迟往上推**：

| DB 延迟 | 无锁 SQL | 有锁 SQL | 无锁 avg | 有锁 avg |
|---|---|---|---|---|
| 0 ms | 7 | **1** | 40.8 ms | 38.8 ms |
| 60 ms | 44 | **1** | 98.6 ms | 96.0 ms |
| **150 ms** | 200 | **200（完全失效）** | 275.0 ms | **302.8 ms（更慢）** |

**根因**：等待预算 `5 轮 × 20ms = 100ms`。当 DB 慢到 150ms 时，
**等待轮次在 DB 返回之前就打完了** —— 每个请求试完 5 轮放弃、然后自己跑去查 DB。
锁退化成**纯粹多余的一轮轮询**，SQL 一条没省，还多花 100ms。

**修法**：改成 `20ms × 100 = 2s`。改后 DB 慢到 150ms 时"等的人约 160ms vs 不等的人 275ms"。

> **这条的价值在于"悬崖位置可以算出来"** ——
> 它等于两个配置常量的乘积，而不是试出来的经验值。
> 更一般地说：**"加了锁"在某些负载区间是有害的，而那个区间可以算。**

### 故事 4：这两个 bug 本地永远测不出来 ★★

| Bug | 根因 | 为什么本地测不出 |
|---|---|---|
| `crypto.randomUUID is not a function`（选完文件点上传，队列一个条目都不出现） | 该 API **只在安全上下文存在**（https / localhost / 127.0.0.1 / file://）；`http://<公网IP>` 下 `crypto` 对象在、**方法没挂上去** | 本地跑在 `localhost`，**被浏览器特批为安全上下文** |
| `Cannot read properties of null (reading 'reduce')` | `UploadedChunks()` 里 `var indices []int` **零次 `append` 时返回 nil**，**Go 的 nil slice 编成 `null` 而不是 `[]`** | 触发路径很窄：**会话建好、却一片都没落盘**，然后重试走断点续传分支 |

**修法不是打补丁**：

- 第一条**把兜底逻辑从调用点抽成一个 `newId()` 工具** —— 因为同一个项目里
  **已经炸过两次**（QoE 埋点那处写对了、上传队列那处忘了）。
  抽出来之后可以跑一条检查：`grep -rn 'crypto\.randomUUID' frontend/src/` 应该只剩一处。
- 第二条**修在函数内部而不是两个调用点** —— 因为同一个 handler 里"新建会话"那条路
  特意写了 `[]int{}`，说明这个坑当初是**知道**的，只是没落在函数内部。

> **两条共同的教训**：
> **① "知道这个坑"和"每个地方都处理了"是两件事。**
> **② 兜底写在调用点上，就是会漏** —— 而漏掉的那个只在线上暴露。

### 故事 5：我先测出"能撑 33 人"，然后发现那是假的安全感 ★★

**第一轮测量**：本机 `curl` 打自建的静态文件替身，测出
**服务端单流 9.38 Gbps、30 并发聚合 11.53 Gbps**，也就是**比需求快 960 倍**。
于是有了结论："不需要做转码/HLS。"

**然后我觉得不对，把整条链路重算了一遍**：

- 真正的瓶颈是 **12 Mbps 家宽上行**（`WLAN LinkSpeed = 144.4 Mbps`，**差 12 倍**）
- 首帧公式 `RTT + 缓冲字节数 ÷ 每人分到的带宽`，预测与实测**吻合到 0.05 秒以内**
- **"能撑 33 人"成立的唯一原因是上传者碰巧传了低码率** ——
  135 条素材里 **128 条是 1080p 却只有 0.16~1.16 Mbps**，**分辨率与码率脱钩**
  （带宽开销只有 1080p 档位目标的 **1/12**）

**于是推翻了自己的结论**，做了上传质量门禁 + 三档 HLS 转码。

**加分点**：后来普查 **135 条存量素材，发现 0 条会触发转码** ——
因为最低档 480p 阈值是 1250 kbps，而全库最大只有 1156 kbps。
这个"转码上线后一条都没触发"的结果本身就是那个病的最佳证据。

> **面试官想听的是"我用一个正确的测量，推翻了自己一个错误的结论"。**
> 而且那个错误结论不是拍脑袋来的 —— 它是**真的测出来的**，
> 只是测的是**不是瓶颈的那一段**（服务端），因为 localhost 不过网卡。

| 追问 | 答法 |
|---|---|
| **"这些数字是怎么测的？"** | `hey` 无状态路由 + 自建 Go 程序打有状态路由；SQL 用 `Com_stmt_execute`（**不用 `Questions`**，它会混进握手和 prepare，报出 1.84 这种非整数）；关键结论用 **MySQL general log 逐条归因**，因为部分消费者跑在 API 进程里，停 worker 关不掉 |
| **"为什么写延迟降了 73% 你却说没优化？"** | 因为端到端 **+18%**、系统总 SQL **11 = 11**。异步只是把工作从请求路径搬到了 worker。真正的收益是**缩短请求路径**和**抗抖动**，不是延迟 |
| **"异步化之后一致性怎么保证？"** | 分成两层：**业务一致性**靠 Outbox（与业务行同事务写，Poller 幂等重投）；**可观测一致性**是压测里显式等的（after 的"一致性等待" p50 14.25ms 就是这个）。失败模式是"延迟可见"而不是"数据丢失" |
| **"MQ 能不能提升吞吐上限？"** | **不能。** 该测的是"单请求占用 DB 连接时长"和"并发下 p99 / 错误率"。直接测 QPS 上限大概得到"没变化"，容易被误读成 MQ 没用 |
| **"分布式锁怎么选等待预算？"** | 必须**大于最坏情况下 DB 的响应时间**。这个项目里是 `轮数 × 步长 = 5 × 20ms`，DB 慢到 150ms 时失效且更慢 —— 所以改成了 2s |
| **"上云之后性能变好了还是变差了？"** | **没有测过。** 而且预期是**变慢** —— 家里上行 12 Mbps，轻量服务器的峰值带宽通常只有 3~6 Mbps。上云买到的是**公网可达 + 稳定 IP + 不占家里带宽**，不是更快。（本地 9.38 Gbps 是环回，不过网卡） |
| **"你最大的收获是什么？"** | 测量能力。这个项目里我保留了 **12 次"测量方法本身翻车"的记录**（计数器用错、打错路由、没清限流桶、跑完立刻关 general log…）。**测量代码里的 bug 比产品代码里的 bug 更危险** —— 产品 bug 让你看到错误的结果，测量 bug 让你**相信一个错误的结论** |
| **"还有什么没做？"** | 见 [01-架构与规模.md](01-架构与规模.md) §10 的 10 条已知缺口 + [03-性能数据.md](03-性能数据.md) §11 的 9 条未测项。最该做的是**过载降级（阶段 E）**和**向量检索接线**；最该测的是**并发吞吐**和**云服务器上的真实数据** |
