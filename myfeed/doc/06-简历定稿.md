## 一、定稿（3 条）

```
myfeed-短视频 Feed 系统（个人项目）
代码: https://github.com/xxclei/golang-learn
技术栈: Go Gin GORM MySQL Redis RabbitMQ JWT ffmpeg Vue3 TypeScript Docker nginx

项目简介: 一个从零实现的短视频内容平台，覆盖投稿上传、Feed 分发、互动、检索、实时通知与多档 HLS 转码播放全链路。针对视频平台"Feed 分发读放大"、"写链路跨表事务阻塞"与"大文件传输 / 多码率播放"三类痛点，基于 Redis ZSET 三级缓存、RabbitMQ 异步化与分片直写实现了系统架构。
```

- **Feed 分发架构**：设计 Redis ZSET 三级缓存（热榜 ZSET + 冷快照 + MySQL 兜底）承载 Feed 分发，视频详情接口 QPS 4944 → 21648（+338%）、p50 15.9ms → 2.9ms，吞吐精确落回"零 SQL"基线；另设计推拉结合架构（写扩散 + 大 V 拉取回查），解决最新流全局无个性化、关注流读时 JOIN 这两个极端 —— 发布事件经 Outbox 异步 fan-out 至粉丝收件箱，以粉丝数阈值切出头部账号写入 bigv 集合并跳过扩散，规避 O(粉丝数) 的写放大。

- **写链路异步化**：引入 RabbitMQ 将点赞写链路全链路异步化（Outbox 模式 + 独立 Worker 消费），请求侧写延迟 15.74ms → 4.35ms（−72%）、p99 同降 73%，解决同步事务长时间占用数据库连接的问题，并以幂等投递保证最终一致；进一步量化收益边界，实测端到端 15.66ms → 18.53ms（+18%）、系统总 SQL 11 条不变，据此确认异步的真实收益是缩短请求路径与抗下游抖动而非降低延迟，并通过评论（请求侧 SQL −60~67%）与关注（0%）的范式对比，归纳出收益取决于原本有无跨表事务。

- **大文件传输与多码率播放**：分片以 Truncate 预分配最终文件、按偏移直写（io.NewOffsetWriter），完成时仅一次 os.Rename，全程无合并步骤，避免临时文件峰值与"最后拼一遍"的窗口期，逐片 MD5 校验支持弱网中断续传；解析 moov 做上传质量门禁并产出 1080p / 720p / 480p 三档 HLS，码率保真度 93.8% ~ 106.7%，45MB 素材转码 5.3s、幂等重投 7ms。

**压测口径**：以上性能数据均为单机 127.0.0.1（hey，n=8000 / c=80），SQL 计数取 `Com_stmt_execute` 而非 `Questions`。

## 三、英文版

```
myfeed — Short-video Feed System (personal project)
Code: https://github.com/xxclei/golang-learn
Stack: Go, Gin, GORM, MySQL, Redis, RabbitMQ, JWT, ffmpeg, Vue 3, TypeScript, Docker, nginx
```

A from-scratch short-video platform covering chunked upload, feed distribution, social
interactions, search, SSE notifications and multi-bitrate HLS playback. Reworked the distribution
architecture around a three-tier Redis cache, RabbitMQ async decoupling and offset-based chunk
writes.

- **Feed distribution**: designed a three-tier Redis ZSET cache (hot ZSET + cold snapshot + MySQL
  fallback) — detail endpoint **4,944 → 21,648 QPS (+338%)**, p50 **15.9ms → 2.9ms**, landing
  exactly on the zero-SQL baseline; also designed a hybrid push/pull feed (write fan-out with
  big-V pull-back), capping write amplification via a follower-count threshold.

- **Write-path async**: introduced RabbitMQ to fully async-decouple the like path (outbox pattern,
  dedicated worker), cutting request-side write latency **72%**; further quantified the benefit
  boundary — end-to-end latency *rose* 18% with total SQL unchanged (11 = 11) — establishing that
  async **reorders** work rather than reducing it, and a three-path comparison pinned the benefit
  to removing cross-table transactions from the request path.

- **Large-file transfer & playback**: parts are written straight into the final file at their
  offset, so completion is a single `os.Rename` with no merge step; `moov`-based upload gating
  produces three HLS renditions at **93.8–106.7%** bitrate fidelity.

*Benchmarks: single host, `127.0.0.1`, hey n=8000/c=80; SQL counted via `Com_stmt_execute`.*

## 四、写法要点：参照的四份范例提炼出的句式

| 特征 | 范例里的样子 | 本稿的落实 |
|---|---|---|
| **`**小标题**：具体信息`**，小标题是**名词短语**、命名"产出物" | `**项目流程：**`、`语义层DSL确定化转化：`、`多路召回字段纠错：`、`**可观测、有保障Harness**：` | `**Feed 分发架构**：`、`**写链路异步化**：`、`**大文件传输与多码率播放**：` |
| **一条 = 一个交付物**，条内可并列多个动作 | `多路召回字段纠错` 一条里同时含向量化建索引 + 加权召回 + LLM 纠正 | `Feed 分发架构` 一条里同时含三级缓存 + 推拉结合 |
| **一句到底不分段**，条内用 `；` `——` 衔接 | 范例每条都是一个连续段落 | 同上，去掉了 markdown 换行 |
| **技术名词内嵌句子**，不另起加粗 | `BGE-small-zh-v1.5将 630 字段名向量化建索引` | `按偏移直写（io.NewOffsetWriter）`、`（Outbox 模式 + 独立 Worker 消费）` |
| **量化收尾** | `字段存在性召回率从 92% 提升至 98%` | `QPS 4944 → 21648（+338%）、p50 15.9ms → 2.9ms` |

**上一版的问题**：我用动词开头（"设计 Redis..."/"引入 RabbitMQ..."）串成长段落。
范例的实际做法是 **`名词短语小标题` + `：` + 具体信息** —— 小标题让扫读的人
**3 秒内知道这条讲的是什么产出**，比读完整句才知道要快得多。这是"按产出写"的关键。

## 五、刻意去掉了"定位并修复 XXX"这类条目

初稿里有两条调试叙事（ngram 检索静默失效的四层根因、两个只在生产环境暴露的缺陷）。
**从简历里删掉了**，理由：

- **简历的职责是展示"造了什么"，不是"修了什么"。** 筛简历的人找的是能力信号，
  而"我修了一个很深的 bug"需要 3 分钟才能讲清价值，在 30 秒的筛选里反而是噪音。
- **修复类内容有更好的舞台。** 它们全部保留在 [05-简历素材.md](05-简历素材.md) §六 的
  五个面试故事里，而且是那里**含金量最高**的部分 —— 面试官想听"你踩过什么坑、怎么定位的"。
- **简历上写"修复"，容易被追问"那原来是谁写的"。** 个人项目的修复故事，
  讲出来是"我调试能力强"，写在纸上容易被读成"代码质量差"。

> **一句话**：bug 故事留给嘴，别留在纸上。

## 七、关于那行"压测口径"

你的手改版把口径那句从项目简介里删了。我把它**压到最短、单独放最后一行**保留了，原因：

- 删掉之后，`QPS 4944 → 21648` 这种数字会变成**没有环境的绝对断言**。
  面试官一问"什么机器上测的"，答"本机单机"和简历上默认暗示的"生产环境"
  落差很大，反而扣分。
- 保留它的**正面价值**比看起来大：主动写 `Com_stmt_execute` 而非 `Questions`，
  是内行信号 —— 会踩这个坑的人，面试官会默认其它数字也真测过。
- 成本只有一行，不占正文。**如果你还是不想要，直接删掉那一行即可**，
  其余内容不受影响。

## 八、推拉结合放进简历 —— 你要准备好怎么答

第 1 条现在含"推拉结合架构"，所以**一定会被问"这个做了吗"**。诚实答案是：
**没有，只有设计**。措辞已写成"**架构设计**"（不是"实现"），不算说谎，
但你必须能接住追问。

**标准答法**（三句话，别绕）：

> **"设计完成，代码没写。"**
> 因为它是现有分发架构的必然下一步 —— 前置条件刚好在这一阶段全部就位：
> Outbox 投递链路已经在跑（实测 245 条 pending 分三批投完）、
> `zset.go` 的 `ZAdd` / `ZRemRangeByRank` / `ZRevRangeByScore` 原语齐全、
> 现有游标语义在收件箱上依然成立。所以我先把方案定下来，但没有为它编造性能数字。

**被追问"那为什么不写"**，给一个真实的技术理由：

> 写扩散的唯一死穴是 **O(粉丝数) 的写放大**，而本项目只有本机单机环境、
> 没有真实粉丝规模，**做出来也测不出意义** —— 加一个 worker 容易，
> 但没有数据支撑的"优化"就是自欺。这也是这个项目里我一直没做的事：
> 不为没测过的东西声称收益。

**被追问阈值怎么定**：

> 阈值是**唯一的旋钮**，它决定头部切到哪。本项目没有真实粉丝分布数据，
> 所以我在设计文档里**明确写了"未做压测，不声称任何性能收益"** ——
> 定一个数字容易，但那个数字会是编的。

## 九、面试追问自保清单

见 [05-简历素材.md](05-简历素材.md) §七 —— 8 条高频追问与答法，最关键的三条：

| 追问 | 一句话答法 |
|---|---|
| "这些数字怎么测的？" | hey 打无状态路由 + 自建 Go 程序打有状态路由（`like` 用 hey 打 8000 次有 7999 次走"已点赞短路"，会得出完全错误的结论）；SQL 用 `Com_stmt_execute`；关键结论用 general log 逐条归因 |
| "写延迟降 73% 为什么说没优化？" | 端到端 **+18%**、总 SQL **11 = 11**。异步只是把工作从请求路径搬到 worker，真正买到的是缩短请求路径和抗抖动 |
| "上云后性能变好还是变差？" | **没测过**，且预期变慢 —— 家里上行 12 Mbps，轻量服务器峰值通常 3~6 Mbps。上云买的是公网可达 + 稳定 IP + 不占家里带宽 |

## 十、备用条目库（需要加长时从这里挑）

按"如果要第 4 条，加哪个"排序：

1. **Feed 检索（`FULLTEXT + ngram`）** —— 三档降级（AND → OR → LIKE 兜底）+ 索引配方指纹
   （写入 `INDEX_COMMENT`，启动时比对不一致即重建）+ 支持中文模糊检索的复合游标。
   *只讲"实现了什么"，不带"修复"叙事。*
2. **分布式防击穿锁的失效边界** —— 等待预算 = 轮数 × 步长（5 × 20ms = 100ms）；
   DB 延迟 0ms 时把 200 并发下的 SQL 从 7 条压到 1 条，延迟到 150ms 时锁完全失效且更慢
   （275.0 → 302.8ms）。属分析条目，面试讲比写纸上好。
3. **SSE 实时通知** —— 长连接推送 + 三队列广播副本 + 未读红点，keepalive 30s。
4. **部署形态** —— 仅 nginx 发布端口，MySQL / Redis / RabbitMQ 一律 `expose` 走内网。
