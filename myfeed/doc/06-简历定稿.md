## 一、定稿（3 条）

```
FeedFlow-短视频内容分发平台（个人项目）
代码: https://github.com/xxclei/FeedFlow
技术栈: Go Gin GORM MySQL Redis RabbitMQ JWT ffmpeg Vue3 TypeScript Docker nginx

项目简介: 一个从零实现的短视频内容平台，覆盖投稿上传、Feed 分发、互动、检索、实时通知与多档 HLS 转码播放全链路。针对视频平台"Feed 分发读放大"、"写链路跨表事务阻塞"与"大文件传输 / 多码率播放"三类痛点，基于 Redis ZSET 三级缓存、RabbitMQ 异步化与分片直写实现了系统架构。
```

- **冷热分层缓存与推拉结合分发架构**：设计 Redis ZSET 三级缓存（热榜 ZSET + 冷快照 + MySQL 兜底）承载 Feed 分发，视频详情接口 QPS 4944 → 21648（+338%），吞吐精确落回"零 SQL"基线；另设计推拉结合架构（写扩散 + 大 V 拉取回查），解决最新流全局无个性化、关注流读时 JOIN 这两个极端 —— 发布事件经 Outbox 异步 fan-out 至粉丝收件箱，以粉丝数阈值切出头部账号写入 bigv 集合并跳过扩散，规避 O(粉丝数) 的写放大。

- **跨表事务消解与写链路异步化**：引入 RabbitMQ 将点赞写链路全链路异步化（Outbox 模式 + 独立 Worker 消费），请求侧写延迟降低 72%，解决同步事务长时间占用数据库连接的问题，并以幂等投递保证最终一致；进一步量化收益边界，实测端到端反而升高 18%、系统总 SQL 不变，据此确认异步的真实收益是缩短请求路径与抗下游抖动而非降低延迟，并通过评论与关注两条链路的范式对比，归纳出收益取决于原本有无跨表事务。

- **无合并分片直写与多档 HLS 播放链路**：分片以 Truncate 预分配最终文件、按偏移直写（io.NewOffsetWriter），完成时仅一次 os.Rename，全程无合并步骤，避免临时文件峰值与"最后拼一遍"的窗口期，逐片 MD5 校验支持弱网中断续传；解析 moov 做上传质量门禁并产出 1080p / 720p / 480p 三档 HLS，码率保真度 93.8% ~ 106.7%。

**压测口径**：以上数据均为单机 127.0.0.1（hey，n=8000 / c=80），SQL 计数取 `Com_stmt_execute` 而非 `Questions`。

## 三、英文版

```
FeedFlow — Short-video Content Distribution Platform (personal project)
Code: https://github.com/xxclei/FeedFlow
Stack: Go, Gin, GORM, MySQL, Redis, RabbitMQ, JWT, ffmpeg, Vue 3, TypeScript, Docker, nginx
```

A from-scratch short-video platform covering chunked upload, feed distribution, social
interactions, search, SSE notifications and multi-bitrate HLS playback. Reworked the distribution
architecture around a three-tier Redis cache, RabbitMQ async decoupling and offset-based chunk
writes.

- **Tiered caching & hybrid push/pull distribution**: designed a three-tier Redis ZSET cache
  (hot ZSET + cold snapshot + MySQL fallback) — detail endpoint **4,944 → 21,648 QPS (+338%)**,
  landing exactly on the zero-SQL baseline; also designed a hybrid push/pull feed (write fan-out
  with big-V pull-back), capping write amplification via a follower-count threshold.

- **Cross-table transaction removal & async write path**: introduced RabbitMQ to fully
  async-decouple the like path (outbox pattern, dedicated worker), cutting request-side write
  latency **72%**; further quantified the benefit boundary — end-to-end latency *rose* 18% with
  total SQL unchanged — establishing that async **reorders** work rather than reducing it.

- **Merge-free chunked upload & multi-bitrate playback**: parts are written straight into the
  final file at their offset, so completion is a single `os.Rename` with no merge step;
  `moov`-based upload gating produces three HLS renditions at **93.8–106.7%** bitrate fidelity.

*Benchmarks: single host, `127.0.0.1`, hey n=8000/c=80; SQL counted via `Com_stmt_execute`.*

| 特征 | 范例里的样子 | 本稿的落实 |

1. **动词开头串长段落** —— 范例的实际做法是先给名词短语小标题再展开，

## 五、刻意去掉了"定位并修复 XXX"这类条目

初稿里有两条调试叙事（ngram 检索静默失效的四层根因、两个只在生产环境暴露的缺陷）。
**从简历里删掉了**，理由：

- **简历的职责是展示"造了什么"，不是"修了什么"。** 筛简历的人找的是能力信号，
  而"我修了一个很深的 bug"需要 3 分钟才能讲清价值，在 30 秒的筛选里反而是噪音。
- **修复类内容有更好的舞台。** 它们全部保留在 [05-简历素材.md](05-简历素材.md) §六 的
  五个面试故事里，而且是那里**含金量最高**的部分 —— 面试官想听"你踩过什么坑、怎么定位的"。
- **简历上写"修复"，容易被追问"那原来是谁写的"。** 个人项目的修复故事，
  讲出来是"我调试能力强"，写在纸上容易被读成"代码质量差"。

> **一句话**：bug 故事留给嘴，别留在纸上。

## 七、关于那行"压测口径"

你的手改版曾把口径那句从项目简介里删掉。我把它**压到最短、单独放最后一行**保留了，原因：

- 删掉之后，`QPS 4944 → 21648` 这种数字会变成**没有环境的绝对断言**。
  面试官一问"什么机器上测的"，答"本机单机"和简历上默认暗示的"生产环境"
  落差很大，反而扣分。
- 保留它的**正面价值**比看起来大：主动写 `Com_stmt_execute` 而非 `Questions`，
  是内行信号 —— 会踩这个坑的人，面试官会默认其它数字也真测过。
- 成本只有一行，不占正文。**如果你还是不想要，直接删掉那一行即可**，
  其余内容不受影响。

## 八、推拉结合放进简历 —— 你要准备好怎么答

第 1 条现在含"推拉结合架构"，所以**一定会被问"这个做了吗"**。诚实答案是：
**没有，只有设计**。措辞已写成"**架构设计**"（不是"实现"），不算说谎，
但你必须能接住追问。

**标准答法**（三句话，别绕）：

> **"设计完成，代码没写。"**
> 因为它是现有分发架构的必然下一步 —— 前置条件刚好在这一阶段全部就位：
> Outbox 投递链路已经在跑（实测 245 条 pending 分三批投完）、
> `zset.go` 的 `ZAdd` / `ZRemRangeByRank` / `ZRevRangeByScore` 原语齐全、
> 现有游标语义在收件箱上依然成立。所以我先把方案定下来，但没有为它编造性能数字。

**被追问"那为什么不写"**，给一个真实的技术理由：

> 写扩散的唯一死穴是 **O(粉丝数) 的写放大**，而本项目只有本机单机环境、
> 没有真实粉丝规模，**做出来也测不出意义** —— 加一个 worker 容易，
> 但没有数据支撑的"优化"就是自欺。这也是这个项目里我一直没做的事：
> 不为没测过的东西声称收益。

**被追问阈值怎么定**：

> 阈值是**唯一的旋钮**，它决定头部切到哪。本项目没有真实粉丝分布数据，
> 所以我在设计文档里**明确写了"未做压测，不声称任何性能收益"** ——
> 定一个数字容易，但那个数字会是编的。

## 十、备用条目库（需要加长时从这里挑）

按"如果要第 4 条，加哪个"排序：

1. **Feed 检索（`FULLTEXT + ngram`）** —— 三档降级（AND → OR → LIKE 兜底）+ 索引配方指纹
   （写入 `INDEX_COMMENT`，启动时比对不一致即重建）+ 支持中文模糊检索的复合游标。
   *只讲"实现了什么"，不带"修复"叙事。*
2. **分布式防击穿锁的失效边界** —— 等待预算 = 轮数 × 步长（5 × 20ms = 100ms）；
   DB 延迟 0ms 时把 200 并发下的 SQL 从 7 条压到 1 条，延迟到 150ms 时锁完全失效且更慢
   （275.0 → 302.8ms）。属分析条目，面试讲比写纸上好。
3. **SSE 实时通知** —— 长连接推送 + 三队列广播副本 + 未读红点，keepalive 30s。
4. **部署形态** —— 仅 nginx 发布端口，MySQL / Redis / RabbitMQ 一律 `expose` 走内网。
