## 一、主推版（4 条）

```
myfeed-短视频 Feed 系统（个人项目）
代码: https://github.com/xxclei/golang-learn
技术栈: Go Gin GORM MySQL Redis RabbitMQ JWT ffmpeg Vue3 TypeScript Vite Docker nginx
```

**项目简介**: 一个从零实现的短视频内容平台（Go + Vue3，约 3.6 万行、45 个 REST API、12 个前端页面），
覆盖投稿上传、Feed 分发、互动、检索、实时通知与多档 HLS 转码播放全链路。
针对视频平台"Feed 分发读放大"、"写链路跨表事务阻塞"与"大文件传输 / 多码率播放"三类痛点，
基于 Redis ZSET 三级缓存、RabbitMQ 异步化与分片直写重构了系统架构，
并将全部优化以单机压测（hey，n=8000 / c=80）做前后对比验证，SQL 计数统一取
`Com_stmt_execute` 而非 `Questions`，以排除握手与 prepare 的干扰。

---

设计 Redis ZSET 三级缓存（热榜 ZSET + 冷快照 + MySQL 兜底）承载 Feed 分发，视频详情接口 SQL 由 1.00 条/请求降至 0.00 条，QPS 4944 → 21648（+338%），p50 15.9ms → 2.9ms，吞吐精确落回"零 SQL"基线（21454 QPS），证明数据库开销被消除而非转移至别处；关注流同样实现 SQL 零化、QPS 提升 30%，最新流经 ZSET 冷热分离后 QPS 3564 → 4391。

引入 RabbitMQ 将点赞写链路全链路异步化（Outbox 模式 + 独立 Worker 消费），请求侧写延迟 15.74ms → 4.35ms（−72%）、p99 同降 73%，解决同步事务长时间占用数据库连接的问题，并以幂等投递保证最终一致（首次端到端验证 245 条 pending 分三批投完，ZSET 计数与预期分毫不差）；进一步量化收益边界，实测端到端 15.66ms → 18.53ms（+18%）、系统总 SQL 11 条不变，据此确认异步的真实收益是缩短请求路径与抗下游抖动而非降低延迟，并通过评论（请求侧 SQL −60~67%）与关注（0%）的范式对比，归纳出收益取决于原本有无跨表事务。

设计 Feed 推拉结合架构（写扩散 + 大 V 拉取回查），解决最新流全局无个性化、关注流读时 JOIN 这两个极端。发布事件经 Outbox 异步 fan-out 至粉丝收件箱，以粉丝数阈值切出头部账号写入 bigv 集合并跳过扩散，规避 O(粉丝数) 的写放大；收件箱以 ZREMRANGEBYRANK 剪枝控制内存增长；读取端将收件箱与 bigv 两路归并，复用现有复合游标语义；并明确"新关注不回填历史"与消费端幂等去重两项决策。

采取分片直写与多档 HLS 实现大文件上传与多码率播放，分片以 Truncate 预分配最终文件、按偏移直写（io.NewOffsetWriter），完成时仅一次 os.Rename，全程无合并步骤，避免临时文件峰值与"最后拼一遍"的窗口期，逐片 MD5 校验支持弱网中断续传；解析 moov 做上传质量门禁并产出 1080p / 720p / 480p 三档 HLS，码率保真度 93.8% ~ 106.7%，45MB 素材转码 5.3s、幂等重投 7ms；前端按需动态 import 分包，详情页首屏体积 597.46 kB → 22.58 kB。

## 三、英文版

```
myfeed — Short-video Feed System (personal project)
Code: https://github.com/xxclei/golang-learn
Stack: Go, Gin, GORM, MySQL, Redis, RabbitMQ, JWT, ffmpeg, Vue 3, TypeScript, Vite, Docker, nginx
```

A from-scratch short-video platform (~36k LoC, 45 REST endpoints, 12 SPA views) covering chunked
upload, feed distribution, social interactions, search, SSE notifications and multi-bitrate HLS
playback. Reworked the distribution architecture around a three-tier Redis cache, RabbitMQ
async decoupling and offset-based chunk writes, validating every optimization with before/after
benchmarks (hey, n=8000/c=80 on a single host; SQL counted via `Com_stmt_execute`, not `Questions`).

Designed a three-tier Feed cache (hot ZSET + cold snapshot + MySQL fallback): the detail endpoint
went from 1.00 to 0.00 SQL per request, 4,944 → 21,648 QPS (+338%), p50 15.9ms → 2.9ms, landing
exactly on the zero-SQL baseline — DB cost eliminated rather than moved.

Introduced RabbitMQ to fully async-decouple the like write path (outbox pattern, dedicated worker),
cutting request-side write latency 15.74ms → 4.35ms (−72%) and removing long-lived DB connection
usage from the request path, with idempotent delivery for eventual consistency; further quantified
the benefit boundary — end-to-end latency rose 18% (15.66ms → 18.53ms) with total SQL unchanged
(11 = 11) — establishing that async *reorders* work rather than reducing it, and a three-path
comparison pinned the real benefit to removing cross-table transactions from the request path.

Designed a hybrid push/pull feed (write fan-out with big-V pull-back), capping write amplification
via a follower-count threshold, trimming inboxes with `ZREMRANGEBYRANK`, and merging both paths
while reusing the existing composite-cursor semantics.

Implemented chunked upload and multi-bitrate playback: parts are written straight into the final
file at their offset, so completion is a single `os.Rename` with no merge step; `moov`-based upload
gating produces three HLS renditions at 93.8–106.7% bitrate fidelity; route-level code splitting
cut a view's first-load bundle from 597.46 kB to 22.58 kB.

## 四、参照优秀简历提炼的写法（以及上一版哪里不对）

把你给的三份范例拆开，行文是有一套固定句式的：

| 特征 | 范例 | 本稿的落实 |
|---|---|---|
| **动词开头**，不做加粗小标题 | "设计 Redis+Lua 实现…"、"引入 RocketMQ 将…"、"采取分片上传与断点续传机制" | 四条分别以 设计 / 引入 / 设计 / 采取 开头 |
| **一句到底**，中间不分行不分段 | 范例每条都是一个连续段落，2~4 句 | 每条都是单段，去掉了上一版的 `**加粗标题**` + 换行 |
| **技术名词内嵌句子** | "基于 Redis Lua 原子完成…"、"结合 MySQL 条件扣减、唯一索引与消费幂等控制" | "以 Redis ZSET 三级缓存…"、"（Outbox 模式 + 独立 Worker 消费）"、"按偏移直写（io.NewOffsetWriter）" |
| **问题 → 方案 → 效果** 三段式 | "解决超卖问题，保障数据一致性" | "解决最新流全局无个性化、关注流读时 JOIN 这两个极端" |
| **量化收尾** | "将 60s+ 上传接口响应时间压缩至 50ms 以内" | "QPS 4944 → 21648（+338%），p50 15.9ms → 2.9ms" |

**上一版的问题是语体不对**：我用了大量的 markdown 加粗小标题 + 多段分栏，
那是**技术文档**的写法（读起来像 wiki），不是**简历**的写法。
简历要在 30 秒内被扫完，靠的是"每句都有信息密度"，而不是"结构清晰"。

## 五、刻意去掉了"定位并修复 XXX"这类条目

初稿里有两条调试叙事（ngram 检索静默失效的四层根因、两个只在生产环境暴露的缺陷）。
**从简历里删掉了**，理由：

- **简历的职责是展示"造了什么"，不是"修了什么"。** 筛简历的人找的是能力信号，
  而"我修了一个很深的 bug"需要 3 分钟才能讲清价值，在 30 秒的筛选里反而是噪音。
- **修复类内容有更好的舞台。** 它们全部保留在 [05-简历素材.md](05-简历素材.md) §六 的
  五个面试故事里，而且是那里**含金量最高**的部分 —— 面试官想听"你踩过什么坑、怎么定位的"。
- **简历上写"修复"，容易被追问"那原来是谁写的"。** 个人项目的修复故事，
  讲出来是"我调试能力强"，写在纸上容易被读成"代码质量差"。

> **一句话**：bug 故事留给嘴，别留在纸上。

## 七、推拉结合已放进简历 —— 你要准备好怎么答

第 3 条现在是简历里的条目，所以**一定会被问"这个做了吗"**。诚实答案是：**没有，只有设计**。
措辞已写成"**架构设计**"（不是"实现"），不算说谎，但你必须能接住追问。

**标准答法**（三句话，别绕）：

> **"设计完成，代码没写。"**
> 因为它是现有分发架构的必然下一步 —— 前置条件刚好在这一阶段全部就位：
> Outbox 投递链路已经在跑（实测 245 条 pending 分三批投完）、
> `zset.go` 的 `ZAdd` / `ZRemRangeByRank` / `ZRevRangeByScore` 原语齐全、
> 现有游标语义在收件箱上依然成立。所以我先把方案定下来，但没有为它编造性能数字。

**被追问"那为什么不写"**，给一个真实的技术理由：

> 写扩散的唯一死穴是 **O(粉丝数) 的写放大**，而本项目只有本机单机环境、
> 没有真实粉丝规模，**做出来也测不出意义** —— 加一个 worker 容易，
> 但没有数据支撑的"优化"就是自欺。这也是这个项目里我一直没做的事：
> 不为没测过的东西声称收益。

**被追问阈值怎么定**：

> 阈值是**唯一的旋钮**，它决定头部切到哪。本项目没有真实粉丝分布数据，
> 所以我在设计文档里**明确写了"未做压测，不声称任何性能收益"** ——
> 定一个数字容易，但那个数字会是编的。

> ⚠️ **风险提示**：这条是全稿唯一一条**没有实测支撑**的内容。
> 如果不想被追问，删掉即可 —— 4 条变 3 条，其余三条全是硬数字。

## 九、备用条目库（需要加长时从这里挑）

按"如果要第 5 条，加哪个"排序：

1. **分布式防击穿锁的失效边界（分析）** —— 等待预算 = 轮数 × 步长（5 × 20ms = 100ms）。
   DB 延迟 0ms 时锁把 200 并发下的 SQL 从 7 条压到 1 条；延迟推到 150ms 时锁**完全失效且比不加锁更慢**
   （275.0 → 302.8ms）。修法把预算提到 2s，使悬崖位置由**可计算的常量**而非经验值决定。
2. **Feed 检索（`FULLTEXT + ngram`）** —— 三档降级（AND → OR → LIKE 兜底）+ 索引配方指纹
   （写入 `INDEX_COMMENT`，启动时比对不一致即重建）。*只讲"实现了什么"，不带"修复"叙事。*
3. **SSE 实时通知** —— 长连接推送 + 三队列广播副本 + 未读红点，keepalive 30s。
4. **部署形态** —— 仅 nginx 发布端口，MySQL / Redis / RabbitMQ 一律 `expose` 走内网。
