## 一、主推版（7 条，一页放得下）

### 项目名与定位

> **myfeed · 短视频 Feed 系统**（个人项目）
> 代码：`github.com/xxclei/golang-learn`

### 技术栈

```
后端  Go 1.26 · Gin · GORM · MySQL 8（FULLTEXT + ngram）· Redis 7
      RabbitMQ（topic + 死信 + 广播副本）· JWT 双 token · ffmpeg
前端  Vue 3 · TypeScript · Vite · Pinia · hls.js · SparkMD5
工程  Docker（多阶段构建）· Docker Compose · nginx · hey · MySQL general log
```

### 项目简介

> 从零实现的短视频 Feed 系统（Go + Vue3，**约 3.6 万行 / 45 个 REST API / 12 个前端页面**），
> 覆盖投稿 → 分发 → 互动 → 检索 → 实时通知 → 转码播放全链路，并以
> Docker Compose + nginx 单栈部署上线公网。
> 针对 **Feed 读放大、写链路跨表事务阻塞、中文模糊检索静默失效** 三类问题做了优化，
> **每一项都有前后对比实测**；压测环境为单机 `127.0.0.1`（hey，n=8000 / c=80），
> SQL 计数统一取 `Com_stmt_execute` 而非 `Questions`，以排除握手与 prepare 的干扰。

### 核心条目

**① Feed 三级缓存（Redis ZSET 冷热分离 + MySQL 兜底）**

视频详情接口 SQL **1.00 → 0.00 条/请求**，QPS **4944 → 21648（+338%）**，p50 **15.9ms → 2.9ms**；
吞吐精确落回"0 条 SQL"基线（21454 QPS），证明数据库开销是被**消除**而非转移到别处。
关注流同样 SQL 1.00 → 0.00、QPS **+30%**；最新流做 ZSET 冷热分离后 QPS 3564 → 4391。

**② 点赞链路 MQ 异步化（Outbox 模式 + 独立 Worker），并量化出异步收益的真实边界**

请求侧写延迟 **15.74 → 4.35ms（−72%）**，p99 同样 −73%，看似大胜；
继续测端到端与系统总 SQL 后得到 **15.66 → 18.53ms（+18%）、总 SQL 11 = 11 条不变**。
据此判定"**异步不是优化，是重排**"，真实收益是**缩短请求路径**（DB 连接占用时长下降）与抗下游抖动。
进一步做范式对比：评论链路请求侧 SQL 降 **60~67%**，关注链路**一条未降** ——
**省不省取决于原本是否存在跨表事务，而不取决于是否引入 MQ**。
Outbox 幂等投递首次端到端验证：245 条 pending 分三批投完，ZSET 计数 **245** 分毫不差。

**③ 定位并修复 `FULLTEXT + ngram` 中文检索静默失效**

`MATCH AGAINST('java')` 返回 **0 条**（库中确有 103 条匹配），而 `redis` 正常，**零报错、零日志**。
根因四层叠加：InnoDB 默认停用词表含单字母 `a`/`i`，ngram 的"含停用词"是**子串**判定，
导致含 `a` 的 bigram 在建索引期被整条丢弃（`java` → `ja/av/va` 全丢，`redis` → `re/ed` 存活）；
且 `OPTIMIZE TABLE`（等价整表重建、含全文索引）在**另一条连接**上以错误的会话变量
把索引**重新建坏**——"建好之后又被建坏"。
修法为**让索引自记配方指纹**（写入 `INDEX_COMMENT`，启动时比对，不一致即重建）
+ **三档降级**（AND → OR → LIKE 兜底），检索结果 **0 → 50 条**。

**④ 算出分布式防击穿锁的失效悬崖**

等待预算 = 轮数 × 步长（5 × 20ms = 100ms）。实测 DB 延迟 0ms 时，锁把 200 并发下的 SQL 从 7 条压到 **1 条**；
但延迟推到 **150ms** 时锁**完全失效且比不加锁更慢**（275.0 → **302.8ms**）——
因为等待轮次在 DB 返回之前就打完了，锁退化成纯粹多余的一轮轮询。
修法把预算提到 2s，使悬崖位置由**可计算的常量**而非经验值决定。

**⑤ 分片上传 + 断点续传（全程无合并步骤）**

`init` 用 `Truncate` 预分配最终文件，各分片以 `io.NewOffsetWriter(f, index×chunk_size)` **按偏移直写**，
`complete` 仅一次 `os.Rename` —— 不存在"最后拼一遍"的窗口期与临时文件峰值。
逐片 MD5 校验、服务端记录已落盘分片索引，弱网中断后可续传。

**⑥ 多档 HLS 转码播放链路 + QoE 埋点看板**

上传门禁解析 `moov` 判定是否需要转码，产出 1080p / 720p / 480p 三档，
**码率保真度 93.8% ~ 106.7%**（峰值段不超过均值的 103%）；
45MB 素材转码 **5.3s**、**幂等重投 7ms**。
前端按需动态 `import` 分包，`VideoDetailView` 首屏体积 **597.46 kB → 22.58 kB**。

**⑦ 容器化部署，并修复两个"本地不可能复现"的缺陷**

Docker 多阶段构建 + Compose 单栈 + nginx 入口，**仅 nginx 发布端口**，
MySQL / Redis / RabbitMQ 一律 `expose` 走内网（避免弱密码数据库直接对公网开放）。
修复：`crypto.randomUUID` 仅在安全上下文存在（`localhost` 被浏览器特批，`http://公网IP` 下方法未挂载）；
容器默认 UTC 与 DSN `loc=Local` 冲突，导致新写入视频的时间戳比旧数据早 8 小时，
**Feed 按时间倒序时新视频永远排在后面，且不报错、无日志**。

## 三、英文版

> **myfeed — Short-video Feed System** (personal project) · Go / Gin / MySQL / Redis / RabbitMQ / Vue 3
>
> A from-scratch short-video platform: ~36k LoC, 45 REST endpoints, 12 SPA views — publishing,
> five feed streams, social interactions, `FULLTEXT + ngram` search, SSE notifications, and
> multi-bitrate HLS playback; deployed as a Docker Compose stack behind nginx.
> Every optimization is backed by before/after benchmarks (hey, n=8000/c=80 on a single host;
> SQL counted via `Com_stmt_execute`, not `Questions`).
>
> - **Caching** — detail endpoint **1.00 → 0.00 SQL/request, 4,944 → 21,648 QPS (+338%)**,
>   p50 **15.9 → 2.9 ms**, landing exactly on the zero-SQL baseline — DB cost eliminated, not moved.
> - **Async** — MQ-based like path cut request-side write latency **72%**, yet end-to-end
>   latency *rose* **18%** with total SQL unchanged (11 = 11), showing async **reorders** work
>   rather than reducing it; a three-path comparison pinned the real benefit to removing
>   cross-table transactions from the request path.
> - **Search** — root-caused a silent `FULLTEXT + ngram` failure (`java` returned 0 vs 103 matches):
>   InnoDB's stopword list contains single letters `a`/`i`, and ngram matches stopwords as
>   **substrings**, dropping every bigram containing `a`; compounded by `OPTIMIZE TABLE`
>   rebuilding the index with wrong session variables on a different connection.
>   Fixed with an index-recipe fingerprint + three-tier fallback; **0 → 50 results**.

## 四、为什么这么写（每条的设计意图）

| 写法 | 意图 |
|---|---|
| 项目简介里**一次性**交代压测环境 | 把"本机单机、n=8000/c=80"放在开头，后面的数字就都是**有口径的**。既守住了诚实底线，又比逐条加括号清爽 |
| 主动写"SQL 计数用 `Com_stmt_execute` 而非 `Questions`" | 这是**内行信号**。会踩这个坑的人，面试官会默认其它数字也测过 |
| ① 缓存放在第一条 | 最标准的"优化成功"叙事，先给筛简历的人一个确定的锚 |
| ② 异步写成"**并量化出收益边界**" | 不是"我失败了"，是"我**测出了适用边界**"。这是全文最值钱的一条 —— 90% 的候选人写"引入 MQ 提升性能"，写不出反面结论 |
| ② 里补范式对比（评论 −60~67% / 关注 0%） | 证明结论是**归纳出来的规律**，不是单点结论。一句话把深度拉开 |
| ③ 检索强调"零报错零日志" | 点明难度等级：**返回错误答案但不崩溃的系统，比崩溃的系统难查一个数量级** |
| ④ 锁写成"**算出**悬崖" | 关键词是"算"不是"调"。它等于两个配置常量的乘积，说明你理解机制而非调参 |
| ⑤ 分片强调"**无合并步骤**" | 大多数人的分片上传是"传完再拼一遍"。指出这一点，暗示你考虑过临时文件峰值与窗口期 |
| ⑦ 强调"**本地不可能复现**" | 这是唯一一条**只有真正部署过**才能写出来的内容 |

## 五、刻意没写的（以及为什么）

| 不写 | 原因 |
|---|---|
| **"高并发"** | 并发吞吐与饱和点**完全没测**。现有数据全是顺序单发，点赞那条 61.1 req/s 是"一次一个"的节奏，不是上限。写了必被追问 QPS 上限 |
| **"支撑 33 人同时播放"** | 是假的安全感 —— 135 条素材里 128 条是 1080p 却只有 0.16~1.16 Mbps，**分辨率与码率脱钩**，"能撑 33 人"成立只因上传者碰巧传了低码率 |
| **"MQ 提升性能 / 提升吞吐"** | 见 ② —— 总 SQL 一条没少。写"提升性能"会被追问 QPS 而答不上 |
| **向量检索 / 语义搜索** | `embed.go` / `vector_repo.go` 完整可用，但 `router.go` 传的是 `nil`，**没有构造点**。属于代码在、功能不在 |
| **过载降级 / 动态 master / 503** | 阶段 E 未开始 |
| **"上线后全链路健康"** | 上云时 MQ 处于降级运行状态（凭据未对齐），后来才修 |
| **"生产环境实测数据"** | 所有性能数字都是本机。**唯一涉及"云"的部分是能跑通，不是性能** |
| 任何 QPS / 延迟数字**不加口径** | 云端一个数都没测过 |

> **Feed 推拉结合（Write Fan-out + Big-V Pull）方案设计**

**放与不放的权衡**（想清楚再决定）：

- **放的好处**：体现架构设计能力与"知道下一步该做什么"，而不是做完就停。
- **不放的理由**：**代码未实施**。写了大概率被追问"为什么没做"，而且简历上
  一条"设计了但没实现"容易被读成凑数。
- **我的建议**：**如果面试是聊技术（而非筛简历），口头讲**；落在纸面上就不放。
  这一条在面试里是加分项，在简历筛选里是减分项 —— 时机不对。

## 七、面试追问自保清单

见 [05-简历素材.md](05-简历素材.md) §七 —— 8 条高频追问与答法，其中最关键的三条：

| 追问 | 一句话答法 |
|---|---|
| "这些数字怎么测的？" | hey 打无状态路由 + 自建 Go 程序打有状态路由（`like` 用 hey 打 8000 次有 7999 次走"已点赞短路"，会得出完全错误的结论）；SQL 用 `Com_stmt_execute`；关键结论用 general log 逐条归因 |

## 八、投递前还剩的事

1. **push 到 GitHub** —— 本地 `main` 领先远端 7 个提交且历史已重写，需要 `git push --force-with-lease`。
   简历上挂链接前先推上去，否则面试官点开是空的。

   这是面试官点进仓库的**第一眼**，可以直接把本文 §一 改写成 README 的项目简介 + 核心条目。

   考虑改名为 `myfeed`（GitHub 会自动重定向旧链接）。

   （含 `123456` 等本地开发凭据）处理掉，虽然只是 localhost 凭据，但公开仓库里出现密码观感不好。
