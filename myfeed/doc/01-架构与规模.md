## 3. 数据模型

`AutoMigrate` 列表是**全项目唯一的"模块注册表"** —— 忘加一行的后果不是编译错误，
而是第一次真实请求打进来才炸 `Table 'myfeed.x' doesn't exist`。

| 表 | 阶段 | 关键点 |
|---|---|---|
| `accounts` | 1 | 密码 bcrypt；`avatar_url` 有一条**不落盘**的写入路径（`UpdateProfile` 接受任意字符串、不校验不落盘 —— 详见 `../PROGRESS.md` §「删除的完整清理 + 文件 GC」陷阱 3） |
| `videos` | 2 | 反范式列 `likes_count` / `popularity`；`transcode_status`（空串/skipped/pending/done/failed） |
| `tags` / `video_tags` | 2 / 扩展 | `video_tags` 必须是**一个两列复合唯一索引** `idx_video_tag (video_id, tag_id)` —— 写错一个字符就变成两个各自唯一的单列索引，含义变成"一个视频只能有一个标签"，**插入第二条时才炸** |
| `likes` | 4 | 同上，`idx_like_video_account (video_id, account_id)` 复合唯一 |
| `comments` | 5 | **没有唯一索引**，这是产品语义不是遗漏：同一个人可以对同一条视频发多条评论 |
| `socials` | 6 | `idx_social_follower_vlogger` 复合唯一 |
| `notifications` | 5 / 12 | `TargetID` 是**多态列**，含义由 `Type` 决定 —— 批量删除必须带 `WHERE type = ? AND target_id IN (...)` |
| `messages` | 12 | `from_id` / `to_id` **各要一个单列索引**，少一个会让会话查询的 `OR` 有一条腿退化成全表扫 |
| `outbox_msgs` | 2 | 与业务行**同事务**写，是"要么都在要么都不在"的落点 |
| `qoe_events` | 扩展 | **全项目唯一会无限增长的表** —— 由观看量驱动，天然比内容量大 1~2 个数量级。真上线要做按天分区 + drop |

## 4. 消息队列拓扑

`internal/middleware/rabbitmq/topology.go` 是**唯一权威清单**，API 进程和 worker 进程都从这里取。
它存在的理由：worker 进程一个 MQ 封装都不建（只消费不发布），如果让它自己手抄队列名，
多一份会漂移的副本 —— 哪天有人把 `like.events` 打成别的，**两边不报错、不崩溃，只是消息去了两个不同的队列。**

### 6 条业务链路

| 交换机 | 队列 | 绑定 key | 消费者 | 消费成本 |
|---|---|---|---|---|
| `like.events` | `like.events` | `like.*` | LikeWorker | 毫秒级 |
| `comment.events` | `comment.events` | `comment.*` | CommentWorker | 毫秒级 |
| `social.events` | `social.events` | `social.*` | SocialWorker | 毫秒级 |
| `video.popularity.events` | `video.popularity.events` | `video.popularity.*` | PopularityWorker | 毫秒级 |
| `video.timeline.events` | **`video.timeline.update.queue`** | `video.timeline.*` | TimelineConsumer（**在 API 进程**） | 毫秒级 |
| `video.transcode.events` | **`video.transcode.queue`** | `video.transcode.*` | TranscodeWorker | **分钟级（几十分钟 CPU）** |

> 时间线和转码两条的 **队列名与交换机名不同**，是六条里唯一的例外，取自常量而非手写字符串，
> 所以不会像手抄那样被"顺手改齐"。
>
> 转码那条与其余五条有**本质区别**：一条消息占住的不是 prefetch 槽，是几十分钟的 CPU。
> 消费端 `Qos(1)` 和"不做优雅等待"都是从这里推出来的。

### 3 条通知副本队列（只有 API 进程声明）

**同一个交换机上的不同队列 = 广播副本；同一个队列 = 竞争消费。**
通知要的是广播 —— 点赞事件既要被 LikeWorker 拿去落库，也要被 NotificationWorker 拿去发通知，
**两件事都得发生，不是二选一。**

| 交换机 | 队列 | 绑定 key |
|---|---|---|
| `like.events` | `notification.like` | `like.like` |
| `comment.events` | `notification.comment` | `comment.publish` |
| `social.events` | `notification.social` | `social.follow` |

三条的 binding key **都是精确匹配、没有通配符**，与业务队列的 `like.*` / `comment.*` / `social.*` 形成对照。
这个差别就是"取关 / 删评论要不要通知"：业务队列要（要落库、要删流水），
通知队列不要 —— **取消点赞不该给人发通知，那是骚扰。**
过滤在**交换机层**完成，不靠消费端判断。

### 消费进程分布

| 进程 | 跑什么 |
|---|---|
| `cmd/worker` | LikeWorker · CommentWorker · SocialWorker · PopularityWorker · TranscodeWorker |
| `cmd/main.go`（API） | TimelineConsumer · NotificationWorker（3 条队列）· **OutboxPoller（1 秒一轮）** · SSEHub |

> ⚠ **这个分布是测量方法的一部分**：因为有消费者跑在 API 进程里，
> 停掉 `worker.exe` 关不掉它们 —— 做 SQL 归因时**必须用 general log 逐条查**，不能总数相减。

### 降级

MQ 不可用时，写路径**降级为同步直写**（`publishMySQLDirect`），业务不挂。
这条降级路径也是压测拿 "before" 数据的手段：**停掉 RabbitMQ 容器**就跑在同步路径上。

## 5. 缓存与 Redis

### Key 清单（前缀 `v1:`，由 `rediscache.Key()` 统一生成）

| Key | 类型 | 用途 |
|---|---|---|
| `v1:account:%d` | string | 账号详情 |
| `v1:account:%d:refresh` | string | refresh token |
| `v1:video:entity:%d` | string | 视频实体（详情缓存的底层） |
| `v1:video:detail:id=%d` | string | `getDetail` 响应 |
| `v1:sf:entity:%d` | string | 单飞（singleflight）锁 |
| `v1:feed:global_timeline` | **ZSET** | 全局最新流（score = 时间戳），带 `ZRemRangeByRank` 裁剪 |
| `v1:sf:cold:listLatest:%d:%d` | string | 最新流冷区快照 |
| `v1:sf:fallback:global_timeline_rebuild` | string | 时间线重建防重锁 |
| `v1:feed:listByFollowing:*:accountID=%d:*` | string | 关注流缓存 |
| `v1:hot:video:1m:%s` / `v1:hot:video:merge:1m:%s` | — | 分钟桶热度 |
| `v1:ratelimit:%s:%s` | string | 限流桶 |
| `v1:refresh:%s` | string | 刷新单飞锁 |

### 最新流的三级缓存

```
L1 热区   ZSET 热区（水位线之上的部分）  ← ZRevRangeByScore
L2 冷区   快照键 sf:cold:listLatest      ← 水位线以下、已冻结的列表
L3 回源   MySQL                          ← 前两级都空才查，查完回填
```

关键设计：**热区与冷区之间有一条水位线**，热区只装最新的一批。
水位线之下的列表一旦冻结就不再变 —— 这正是"排序不可变时 offset 分页才是对的"这条规则的正确用法。

> **一次可量化的微优化**：把 `zrevrangebyscore` 与 `get` 的**顺序调换**，
> 砍掉 1 次 Redis 往返 → **QPS 4013.97 → 4391.36（+9.4%）**。
> 用 `INFO commandstats` 精确验到 `zrevrangebyscore=100 + get=100` = 恰好 2 次/请求。
> 见 [03-性能数据.md](03-性能数据.md) §2.2。

### 防击穿锁

`detailLockWaitRounds × detailLockWaitStep` 决定了一个**悬崖**：
DB 延迟超过 100ms 时锁完全失效，且比不加锁更慢。详见 [03](03-性能数据.md) §3。

## 6. 分片上传协议

后端协议（`internal/video/chunk_handler.go`）：

```
init      → 开一个会话，按 (accountID, file_hash) 索引；同哈希**复用**已有会话。
            同时把最终文件预分配到 file_size，半成品叫 xxx.mp4.part
upload×N  → 每片单独 MD5 校验，然后**直接写到 index*chunk_size 的偏移上**
complete  → 全部到齐 → 把 .part 改名成 .mp4 → 销毁会话 → 返回 play_url
```

**没有"服务端拼装"这一步。** 分片到达时就落在自己该在的位置上，`complete` 只是一次 `os.Rename`：

| | 老实现（每片落 tmp/ → complete 时按序 `io.Copy` 拼） | 现在 |
|---|---|---|
| complete 的 IO | 500MB 的文件读 500MB 再写 500MB | 一次 `os.Rename`（同目录内原子） |
| 乱序 / 并发到达 | 要等齐 | 无所谓 |
| 临时目录残留 | 有 | 没有 |
| "半个 mp4" | 可能 | 不存在 |

**代价**：这个方案**必须**有 `validateChunkPlan`。
分片一改成"按偏移直写"，`chunk_size × total_chunks ≠ file_size` 这个缺口就从
"合出来的文件短一截"升级成**"整个文件写歪"** —— 所以它不是可选项，是直写方案的前置条件。

```
validateChunkPlan 断言：total_chunks == ceil(file_size / chunk_size)
兜底：chunk_size ≥ 1MB、total_chunks ≤ 4096
      （否则 chunk_size=1 配 500MB 文件 = 一个 5 亿长度的 []bool = 一次 500MB 内存）
```

**前端分片大小自适应**：`<50MB → 5MB`、`<200MB → 10MB`、`≥200MB → 20MB`。
口径按文件大小分档：往返次数、位图大小、MD5 次数都随分片变大而变优，
代价是断点续传粒度变粗、单片重试更贵、在途内存 `chunk_size × 并发数` 变大。
单文件上限 **200MB → 500MB**（自主改动，原项目是 200MB）。

### 批量上传踩到的三个后端行为

| # | 后端行为 | 前端对策 |
|---|---|---|
| 1 | 断点续传按 `(accountID, file_hash)` 索引，**内容相同的两份文件会塌进同一个会话** | 开传**之前**全批算一份指纹，同哈希的只让第一个真传，其余标 `duplicate` 复用它的 `play_url` |
| 2 | 没有 TTL / 没有清理：放弃的会话留在内存，半成品 `.part` 留在磁盘 | 不提供"清理"按钮（后端没有对应接口），界面上如实写明 |
| 3 | 会话可能**永久无法完成**（位图说传过、磁盘文件却没了 → `upload` 幂等短路不写盘、`complete` 永远失败） | 逃生舱：`file_hash` 只是索引键、**从不校验内容**，`complete` 失败时用 `${hash}-r1` 重新 `init` 换一个全新会话，只加一次盐 |

## 7. 检索管线

```
query ──→ sanitize ──→ buildBoolean ──→ MySQL MATCH...AGAINST ──→ 冻结令牌游标 ──→ GetByIDs → 按序重排
```

### 三档降级

| 档 | 形式 | 语义 |
|---|---|---|
| 1 | `+tok1 +tok2`（AND） | 等价于"整串子串包含"，严格 |
| 2 | `tok1 tok2`（OR） | 第 1 档返回条数 < limit 时重试 |
| 3 | **LIKE 兜底** | 前两档**一条都没命中**时启用 —— 说明索引可疑，而 LIKE 不看索引，是唯一还能给出正确答案的手段。按 token AND 而不是整串 LIKE（`java 教程` 要能命中 `java-…教程`） |

跑的是哪一档**如实报给前端**（`mode` 字段）—— 这一页最有价值的可观测性就是
"搜索变差了能一眼看出是哪一步退化的"。

### 三个必须处理的边界

- **`ngram_token_size = 2`** → 单字查询（"日"）永远匹配不到，静默返回空。按 **rune** 数（不是 byte，中文一字 3 字节）< 2 → LIKE 降级。
- **BOOLEAN 模式下引号短语**（MySQL Bug #118238）：ngram + utf8mb4 + CJK 标点 → 返回空集，**不带引号反而能命中**。所以构造查询用**裸 token**。
- **sanitize 后 0 个 token → 400，不是空列表。** 只打标点 `+++` 时，空列表的语义是"没有这个视频"，用户会以为语料里真没有、然后一直换词试。

### 融合层

数据流里**仍有 `FuseRRF(k=60, lists...)` 这一步**，只是当前只喂给它一路。
看起来像白跑，但它在单路上是**恒等变换**（`score(d) = 1/(k+rank)` 对 rank 严格递减）。
留着它的理由是接线只差传参 —— 而不是"以后再补一层排序"（那会改掉排序语义，是另一回事）。

### 游标

**服务端签发的不透明令牌，令牌里冻着整轮 id 列表 + offset。**

RRF 的输出不是一个能按游标切片的有序序列，所以项目里用了四次的"镜像游标"在这**不适用**。
offset 分页在一般情况下不安全（新插入会让翻页重复/遗漏），**这里安全，因为底层顺序被冻住了** ——
同一轮翻页是一份**快照**（中途新发的视频不会插进来），和最新流的行为不同，是**有意的**。

> 令牌**不签名**：它是客户端持有的，改它只能换到另一个公开视频的切片，
> 不是安全边界 —— 加 HMAC 只会让人以为那里有什么可保护的。

### 唯一的手写 DDL

到检索这一轮为止，GORM 结构体 tag 是**唯一**的 schema 声明方式（仓库里 0 个 `.sql`）。
`WITH PARSER ngram` 没有对应的结构体 tag，所以 `internal/video/search_index.go` 里必然出现第一段裸 SQL：

```sql
ALTER TABLE videos ADD FULLTEXT INDEX ft_videos_title_desc (title, description)
  WITH PARSER ngram COMMENT 'myfeed-ft:ngram-n2-sw0';
```

幂等靠查 `information_schema.STATISTICS`（MySQL 没有 `ADD FULLTEXT INDEX IF NOT EXISTS`）。
`COMMENT` 是**索引的配方指纹** —— 启动时读回来和当前应有的配方比，不一致就重建。
为什么需要它：见 [04-疑难问题排查.md](04-疑难问题排查.md) §1。

## 8. 播放链路（扩展）

```
上传 ──▶ mp4probe 读 moov（门禁）──▶ 超阈值入队 ──▶ TranscodeWorker ──▶ ffmpeg 三档 HLS
                          │                                    │
                          ▼                                    ▼
                    直传 mp4 播放                     master.m3u8 + 分段 + runID 布局
                                                              │
                                                     hls.js（动态 import）+ ABR
                                                              │
                                                     useQoE 埋点 ──▶ qoe_events
```

| 段 | 内容 | 状态 |
|---|---|---|
| A | QoE 埋点（`internal/qoe/` + `useQoE.ts`） | 代码完成，**基线未采**（错过采集时机） |
| B | 上传质量门禁（`mp4probe.go` 读 moov） | ✅ 实测通过 |
| C | 转码 worker + 多档 HLS | ✅ 实测通过 |
| D | 播放端 hls.js + ABR | 🔶 请求链实测通过，未在真浏览器点过 |
| E | 过载降级（并发码率核算 + 动态 master + 503） | ⬜ **未开始** |

**关键的播放器决策**（都很容易写反）：

| 决定 | 理由 |
|---|---|
| 高亮跟 `pickedLevel`（用户意愿），不跟当前实际档位 | 自动模式下 ABR 一直切档，跟着实际档位会让「自动」那颗按钮一闪一闪 |
| 用 `nextLevel` 而不是 `currentLevel` | `currentLevel` 会 **flush 当前缓冲区**去尽快换档，每次造成一次真实重缓冲 —— 而 `useQoE` 把 `waiting` 记成 `stall_count`，**用户每点一次清晰度，看板上的卡顿率就自己涨一点** |
| 档位名优先用 `height` | master 是服务端现场生成的，`level.name` 可能为空或几档同名 |
| 渲染判据是 `levels.length >= 2`，不是 `> 0` | 降级时服务端把 master 缩成一档 —— 那时正确的表现是**整排按钮消失** |
| 不自动播放 | 同一个 URL 点进来会自己放、刷新进来停在浮层上 = **两种行为**，统一成"点了才放" |

### nginx 里三个必须写对的地方

```nginx
# 1) /api/ 前缀必须去掉：后端路由是 /feed/search 而不是 /api/feed/search
#    proxy_pass 末尾那个斜杠就是"剥掉 location 前缀"的开关，漏了就全部 404
location /api/ {
    proxy_pass http://api:8080/;          # ← 末尾斜杠，别删
    # buildAbsoluteURL 会读它拼绝对 URL（且**会落库**），不传就会存下一批 http://内网名/...
    proxy_set_header X-Forwarded-Proto $scheme;
    proxy_read_timeout 3600s;             # SSE 长连接
    client_max_body_size 600m;            # 依据 maxUploadSize = 500MB，留余量
}
location /api/video/chunk/upload {
    proxy_request_buffering off;          # 500MB 分片不再落一遍 nginx 临时文件
}

# 2) /static/ **不能**加末尾斜杠（保留完整 URI）
location /static/ {
    proxy_pass http://api:8080;
    proxy_buffering off;                  # 视频/分片不缓冲，Range 直接透传
}

# 3) SPA fallback —— Go 侧完全没有这个路由（无 go:embed、无 NoRoute），nginx 必须自己做
location / {
    root /usr/share/nginx/html;
    try_files $uri $uri/ /index.html;
}
```

### 容器化踩到的两个构建期问题

| 问题 | 根因 |
|---|---|
| `failed to solve: image "myfeed-app:latest": already exists` | `api` 和 `worker` **都声明了 `build:` 和同一个 `image:`** → Compose 并行构建两次同一个 Dockerfile 并竞争同一个 tag。**报错完全指不到"你有两个服务在构建同一个镜像"** |
| `sed: can't read /etc/apt/sources.list: No such file or directory` | **Debian 12+ 迁移到了 deb822**，源文件在 `/etc/apt/sources.list.d/debian.sources`，是 `key: value` 节格式。针对旧路径硬编码的 `sed` 必然失败 |

## 10. 已知缺口

| # | 缺口 | 影响 |
|---|---|---|
| 1 | **向量检索整套写在盘上但没接线**（`embed.go` / `vector_repo.go` 完整可用，`router.go` 给 `NewService` 传的都是 `nil`） | 需要 Redis 换 `redis-stack-server` 镜像、`ollama pull bge-m3`、一个幂等回填命令 |
| 2 | **标签在描述里是冗余的** | 因为 FULLTEXT 只索引 `title + description`，标签只进 `video_tags` 的话"只有标签、标题描述里没这个词"的视频会搜不到 |
| 3 | **删除视频不清磁盘文件** | 三个理由：① 一个文件可能被多条视频行共用（批量投稿的 duplicate 借 leader 的 `play_url`）② `play_url` 是**客户端给的**，服务端没有归属凭证 ③ MySQL 事务和文件系统之间没有原子性。正确的做法是异步 GC |
| 4 | **`.part` 残留无回收** | 未完成的分片上传每个最多占 500MB 且永不回收（`sessionTTL` 声明着但全项目零引用） |
| 5 | **`.part` 文件被 HTTP 暴露** | `r.Static("/static", "./.run/uploads")` 服务**整棵树**，未完成的分片可按 `/static/videos/<id>/<date>/<hex>.mp4.part` 直接下载 |
| 6 | **客户端声明的数字决定磁盘分配** | `init` 一进来就 `preallocate(req.FileSize)`，而它是客户端给的 —— **一个已认证请求就能占 500MB 的盘** |
| 7 | **检索索引没有 `*` 通配符** | ngram 已把词切成 bigram，`*` 与 ngram 的交互是版本相关的 |
| 8 | **`mode` 恒为 `lexical-only`** | 词法那一路自己的形态（`ngram` / `ngram-or` / `like` / `like-fallback`）到不了前端调试面板 |
| 9 | **`go test ./internal/video/...` 会动真库** | `like_concurrency_test.go` 读 `configs/config.yaml` 连**开发库**并跑 `AutoMigrate` → 会 `DROP`+`ADD` 全文索引、`OPTIMIZE` 整张 `videos` 表。**服务器上绝不能跑这条测试** |
| 10 | **阶段 E 过载降级未做** | 服务端在过载时不会主动缩 master，只能靠客户端 ABR 自己扛 |
