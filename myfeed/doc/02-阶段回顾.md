## 阶段 2 · 视频模块（09-12）

**产出**：直传 + 分片上传 + 发布事务 + outbox 伏笔；前端发布页可传可播。

### 两个大改造（09-13）

**① 去掉「合并」这一步：分片按偏移直写最终文件**

老实现是「每片落 `tmp/<upload_id>/<index>` → `complete` 时按序 `io.Copy` 拼成 mp4」，
`complete` 对 500MB 的文件要读 500MB 再写 500MB，用户得盯着进度条多等一整个磁盘往返。

新实现：

- `init` 就把输出路径定下来，并把 `.mp4.part` **预分配**到 `file_size`（`Truncate` 只移动 EOF，不写零，不费 IO）
- `upload` 用 `io.NewOffsetWriter(f, index*chunk_size)` 直接写到该片的位置上 →
  **分片乱序/并发到达都无所谓，也没有临时目录可残留**
- `complete` 只剩一次 `os.Rename(.part → .mp4)`：同目录内原子，**不存在"半个 mp4"**

配套防御：`session.chunkLen(index)` 校验每片实际字节数（400）；
写不满 `wantLen` 返回 5xx（可重试）；`complete` 前 `Stat` 确认文件还在
（错误信息里带 `missing`，前端才认得出来走逃生舱）。

**② 分片大小自适应（5 / 10 / 20 MB 分档）**

`chunkSizeFor(fileSize)`：`<50MB → 5MB`、`<200MB → 10MB`、`≥200MB → 20MB`。
它是**纯函数**，刻意不做参数透传 —— 只要所有分片运算都从 `chunkSizeFor(file.size)` 取尺子，
就不可能"指纹按 5MB 切、上传按 20MB 切"。

后端从"完全不校验 `chunk_size`"改成 `validateChunkPlan`，并给 `chunk_size ≥ 1MB`、
`total_chunks ≤ 4096` 兜底（否则 `chunk_size=1` 配 500MB 文件就是一个 5 亿长度的 `[]bool` = 一次 500MB 内存）。

续传时若分片几何变了，**丢掉旧会话重开**，而不是返回错误把文件钉死。

> ⚠ 补上的这个校验**不是可选项，是直写方案的前置条件** ——
> 分片一改成"按偏移直写"，"几何不自洽"的后果就从"合出来的文件短一截"升级成"整个文件写歪"。

**顺带**：`maxUploadSize = 500 << 20` 提到公共位置，直传和分片 init 共用同一个常量。
单文件上限从 200MB 提到 500MB（**原项目之外的自主改动**）。

**伏笔**：`publish` 事务里与视频行**同事务**写 `outbox_msgs` ——
"要么都在要么都不在"，这是阶段 9 异步化的地基。

## 阶段 3 · Feed 模块（09-13，`c57fa91`）

**产出**：最新流（时间游标）+ 点赞流（复合游标）+ 标签流 + 关注流，游客可刷。

- **四种游标，翻页不重不漏** —— 这是本阶段的核心验收。
- 前端发现页配 `DebugPanel`：游标原值 + **跨页重复探针**（重复出现即证明游标失效），默认收起。
- 这个"自证机制"在后面的检索页被复用了。

**修的真缺陷 —— 批量上传的流水线断点**：

`start()` 原来是 `await hashPass(); wake()`，而 `runHashPass()` 是顺序遍历、循环体里**没有** `wake()`。
后果：完全没有流水线 —— **第 1 个文件要等最后一个文件的指纹算完才开始传**
（20 个 500MB 的文件 = 先顺序读完 10GB），而且每个算完指纹的行都被置成 `queued` / `排队中` 然后干等。

改动：改成边算边往 `Map<fileHash, item>` 里登记，算出这一个的瞬间就能定它是不是重复，然后立刻 `wake()`。
**判重只要求"自己算完"，不要求"别人也算完"。**

配套加了一条**护城河**：`markDuplicates()` 遇到 `state === 'duplicate'` 直接 `continue`。
不加的话，一个已被增量判成 duplicate 的 item 会在收尾那趟里被登记成 leader，
于是它和它真正的 leader **互相指认 → 环形等待，两个都不传**。

## 阶段 4~6 · 点赞 / 评论 / 关注（09-13，`e960d69`）

**点赞**：唯一键拦重复（`idx_like_video_account` 复合唯一，撞 1062）；

**关注**：`socials` 表 + 关注流（软鉴权，游客可看）。

### 三件一起修的

**① 批量标签：`tag_names` 成为一等公民**

老实现是坏的，不是"不够好"：`BatchOptions.extraTags` 是一个裸 `<input>`，
它的内容**整个**变成每条视频的 `description`，后端再从 `title + " " + description` 里 `ExtractTags` 抽 `#xxx`。
三个问题：

- 打 `日常 vlog` 不带 `#` → **静默零标签**（最恶劣的那种失败：不报错、看起来生效了）
- 标签成了描述的一部分，白吃 `varchar(255)` 的额度
- 改 `extraTags` 只对**之后加入**的文件生效

现在服务端落库取 **`ExtractTags(文本) ∪ TagNames`**，因为是并集，**所有既有行为原样保留**。

> **顺手修掉的是一整类 bug，不是一个实例**：`titlePrefix` / 标签 / 统一描述三个批量选项
> 现在都在**发布那一刻**求值，每行还把该文件最终会带上的标题和标签显示出来 ——
> "它对已入队的文件也生效"变成**可见的**，而不是靠注释保证。

**② 批量删除：一次 `IN` + 清 `video_tags` + 401 → 403**

老 `DeleteVideo` = `db.Delete(&Video{}, id)`：没有事务、没有 `AND author_id = ?`、
**不清 `video_tags`**（孤儿关联一直在攒）。而且删别人的视频返回 **401** ——
而前端 `client.ts` 对**任何** 401 都 `clearTokens()`，**手滑点一下别人视频的删除键就被静默登出**。

- `SelectOwnedIDsTx` **先问"哪些 id 真是我的"**，再删那批 → `deleted_ids` / `skipped_ids`
  是先查出来的确定答案，不靠 `RowsAffected` 推断（GORM 的软删除语义会让它的含义随版本漂移）
- 单条 `Delete` 改成 `DeleteBatch` 的 **1 元素特例**，不再有两份删除逻辑
- handler 校验：空 → 400；`> 100` → 400；**去重后再进 service**（`[3,3,3]` 不算 3 条）

**③ 播放页 `/video/:id`**

后端零改动 —— 两个公开接口 + `feed/listByTag` 就够撑起这一页。

唯一的真坑：**`/video/*` 和 `/feed/*` 是两套字段形状**（作者是扁平字符串 vs 嵌套对象、
时间是 RFC3339 字符串 vs Unix 秒、有没有 `popularity`）。
解法是在 `api/video.ts` 里加 `normalizeVideo()` —— **归一放在 API 边界**，下游只认一种形状。

另外两处：

- **`/video/:id` 千万不能带 `requiresAuth`** —— 抄路由时特别容易连 `meta` 一起抄，
  抄了就把所有未登录用户从发现页一脚踢到登录页，而 `getDetail` 本来就是公开接口
- **路由参数是字符串，直接发给后端是 500 不是 404** —— 后端 `type GetDetailRequest struct { ID uint }`
  **没有 `binding:"required"`**，`{"id":"7"}` 会返回
  `json: cannot unmarshal string into Go struct field ... of type uint` 的 500，
  而那个 500 会被原样渲染到页面上。所以视图里先 `Number(route.params.id)` 校验再发请求

## 阶段 7 · Redis 缓存（09-14）★ 简历核心

**产出**：Redis 封装 + token / 详情 / Feed 缓存 + 防击穿锁 + 限流中间件。

**这是全项目性能数据最集中的阶段**，详见 [03-性能数据.md](03-性能数据.md) §2~§3：

| 缓存点 | SQL/req | QPS | p50 |
|---|---|---|---|
| `video/getDetail` | 1.00 → **0.00** | 4944 → **21648** | 15.9ms → **2.9ms** |
| `feed/listLatest`（三级） | 2.00 → 1.00 | 3563.96 → **4391.36** | 21.7ms → 17.7ms |
| `feed/listByFollowing` | 1.00 → 0.00 | 4054.84 → **5265.30** | 19.2ms → 14.3ms |

**基线（n=8000 c=80）**：health 0 SQL = 21454 QPS；auth 1 SQL = 5021；video 1 SQL = 4944；
profile 4 次聚合 = 1037 → **gin 天花板约 21000 QPS，每多一条 SQL 掉到 ~5000**。

### 最新流的三级缓存

```
L1 热区   ZSET 热区（水位线之上）        ← ZRevRangeByScore
L2 冷区   已冻结的快照键                ← 水位线以下
L3 回源   MySQL，查完回填
```

**热区与冷区之间有一条水位线**，热区只装最新的一批。
水位线之下的列表一旦冻结就不再变 —— 这正是"排序不可变时 offset 分页才是对的"的正确用法。

**微优化**：把 `zrevrangebyscore` 与 `get` 的**顺序调换**，砍掉 1 次 Redis 往返 → **+9.4% QPS**。
用 `INFO commandstats` 精确验到 2 次/请求。

### 防击穿锁 与 100ms 悬崖

| DB 延迟 | 无锁 SQL | 有锁 SQL | 无锁 avg | 有锁 avg |
|---|---|---|---|---|
| 0ms | 7 | **1** | 40.8ms | 38.8ms |
| 60ms | 44 | **1** | 98.6ms | 96.0ms |
| 150ms | 200 | **200（失效）** | 275.0ms | **302.8ms（更慢）** |

悬崖 = `detailLockWaitRounds × detailLockWaitStep = 5 × 20ms`。
修法：**20ms × 100 = 2s**。

### 只有本机才暴露的连接池坑

一次 **16 模式 × 8000 请求**的扫描把 `TIME_WAIT` 从 **1687 推到 15502**，
而 Windows 动态端口段只有 **16384** —— 超过后应用连 MySQL 都拨不出去开始 500。
修法：`SetMaxOpenConns(50)` + `SetMaxIdleConns(50)`。

## 阶段 9 · RabbitMQ 与 Worker（09-14）★ 简历核心

**产出**：6 条业务链路 + 3 条通知副本队列 + 独立 Worker 进程 + 降级直写。

### 一、六条链路与"广播 vs 竞争"

**同一个交换机上的不同队列 = 广播副本；同一个队列 = 竞争消费。**

通知要的是广播：点赞事件既要被 `LikeWorker` 拿去落库，也要被 `NotificationWorker` 拿去发通知，
**两件事都得发生，不是二选一**。所以不能共用 `like.events` 队列，必须另开一条绑到同一个交换机上。

三条通知队列的 binding key 是**精确匹配、没有通配符**的，与业务队列的 `like.*` 形成对照 ——
这个差别就是"取关/删评论要不要通知"。**取消点赞不该给人发通知，那是骚扰。**
过滤在交换机层完成，不靠消费端判断。

### 二、"异步不是优化，是重排" —— 本阶段最重要的结论

| | 写延迟 mean | p50 | p95 | p99 | **端到端** | **系统总 SQL** |
|---|---|---|---|---|---|---|
| 同步写事务 | 15.74ms | 15.66ms | 19.21ms | 23.47ms | 15.66ms | 11 |
| MQ 异步 | **4.35ms（−72%）** | 4.28（−73%） | 4.83（−75%） | 6.27（−73%） | **18.53ms（+18%）** | **11 = 11** |

**写延迟 −73%，端到端反而 +18%，总 SQL 一点没少。**

这三组数必须一起看。异步真正买到的是：
**请求路径变短（连接占用时间下降）+ 抗下游抖动**，而不是"更快"。

### 三、两条范式的对比（更值钱的部分）

| 链路 | 请求侧 SQL | 异步侧 | 总 SQL |
|---|---|---|---|
| 评论发布（范式 A） | 5 → **2（−60%）** | 3 + 1 | 5 → 6 |
| 评论删除（范式 A） | 3 → **1（−67%）** | 2 | 3 → 3 |
| 点赞（范式 A） | 5.50 → **2.00** | 3~4 | 11 → 11 |
| **关注（范式 B）** | 4 → **4（不变）** | 1 + 1 | 4 → **6** |
| **取关（范式 B）** | 4 → **4（不变）** | 1 | 4 → **5** |

**省不省 SQL 取决于写操作原来有没有跨表事务，不取决于"用没用 MQ"。**
范式 B 的异步侧反而多两条 —— 这不是 bug，是 MQ 的本职。

请求侧延迟降幅：点赞 15.7 → 4.2ms（−73%）；评论发布 17.95 → 5.76ms（−68%）；
评论删除 14.18 → 4.38ms（−69%）。

### 四、Outbox

`publish` 事务里与业务行**同事务**写 `outbox_msgs`，`OutboxPoller` 每秒一轮投递。
**首次端到端实测**：启动时 **245 条 pending**，轮询 **100 / 100 / 45** 投完，
`ZCARD v1:feed:global_timeline = 245` —— 账号/视频/时间线三条链路一次性补齐。

设计纪律（`video_service.go` 里写明）：**fire-and-forget 异步之所以敢做，
前提是"有一个幂等的兜底命令"**。

### 五、测量方法本身就是这个阶段的一半工作量

- **停掉 RabbitMQ 容器**触发降级直写 `publishMySQLDirect` → 拿到干净的 before
- **MySQL general log 逐条 SQL 归因**（不是总数相减）——
  因为 `NotificationWorker` / `TimelineConsumer` / `OutboxPoller` **都跑在 API 进程里**，
  停 `worker.exe` 根本关不掉它们
- 发现 `RabbitMQ 恢复 20 秒后仍降级`（所有"5 秒后重连"循环在空转）

> **顺带发现的一处已知问题（未修）**：`RabbitMQ 恢复 20 秒后仍降级`，
> 所有"5 秒后重连"的循环在空转，`amqp.Dial` 全包里只出现一次。

## 阶段 10 · Docker 部署（09-15）★ 上公网

**产出**：`deploy/` 五件套 + 腾讯云轻量应用服务器上单栈上线，IP + 80 端口。

### 安全项（按"静默程度"排序）

| 项 | 不改的后果 |
|---|---|
| 🔴 **生产必须设 `JWT_SECRET` 环境变量** | 该变量为空时回落到硬编码的 `"myfeed-dev-secret-change-me"`，**且不打印任何警告**。有公网 IP 后，任何人都能用这个公开密钥签发任意账号的 token |
| 🔴 三处 `127.0.0.1` → 服务名；mysql 端口 3307 → 3306 | 应用容器里的 `127.0.0.1` 是它自己；3307 是宿主机映射端口 |
| 🔴 换掉全部弱密码 | 虽然端口不发布，但弱密码 + 内网横向是同一个事故的两半 |
| 🟠 **三处容器设 `TZ=Asia/Shanghai` 且镜像装 `tzdata`** | 见下 |
| 🟠 MySQL 补 `--ngram_token_size=2` | 它现在是 InnoDB 默认值，等于"靠默认值碰巧对"。写进命令行参数才是**结构上保证** |

**时区这条会直接搞坏 feed 的排序**：DSN 是 `parseTime=True&loc=Local`，而全项目没有一处设置 `TZ`。
官方镜像默认 UTC。旧数据是 UTC+8 墙钟字面量，上云后新写入的是 UTC 墙钟 —— **比旧数据早 8 小时**。
feed 按 `create_time DESC` 排序，于是：

> **新上传的视频永远排在旧视频后面，翻到第一页看不见自己刚传的东西。**
> 不报错、零日志，旧数据全部"来自未来"。

### 优雅关闭

原来 `r.Run(addr)` = `http.ListenAndServe`：**SIGTERM 由 Go runtime 默认处理 = 立即退出**。后果：

- 三个 `defer`（`db.CloseDB` / `cache.Close` / `rmq.Close`）**全都不执行**
- API 进程里的后台消费者和 outbox 轮询器被腰斩 —— 正在投递的那一批可能投到一半
- SSE 连接全部硬断

改成 `http.Server` + `signal.NotifyContext` + `srv.Shutdown(15s)`。

> **认下的代价**：`Shutdown` 会等活跃连接结束，而 SSE 是长连接 ——
> 所以每次重启会等满 15 秒才强杀。想更干净得让 `ssehub` 订阅 `ctx.Done` 主动关连接。

### 上云当天发现的两个"本地永远测不出来"的 bug

| Bug | 根因 | 为什么本地测不出 |
|---|---|---|
| `crypto.randomUUID is not a function`（选完文件点上传，队列一个条目都不出现） | `crypto.randomUUID` **只在安全上下文存在**（https / localhost / 127.0.0.1 / file://）。`http://<公网IP>` 下 `crypto` 对象在、**方法没挂上去** | 本地跑在 localhost，**被浏览器特批为安全上下文**。这是"上云"这个动作本身带出来的 |
| `Cannot read properties of null (reading 'reduce')` | `UploadedChunks()` 里 `var indices []int` **零次 append 时返回 nil**，Go 的 nil slice 编成 `null` 而不是 `[]` | 触发路径很窄：**会话建好但一片都没落盘**，然后重试走断点续传分支 |

两条的修法都不是打补丁：

- 第一条**把兜底逻辑从调用点抽成 `utils/uuid.ts`** —— 因为"一个文件写了、另一个文件忘了，
  而忘掉的那个只在线上暴露"（`useQoE` 曾经写对过，上传队列忘了）。
  抽出来后可以随时跑 `grep -rn 'crypto\.randomUUID' frontend/src/`，应该只剩一处。
- 第二条修在**函数内部**而不是两个调用点 —— 理由是"**知道这件事**"和"**每个返回点都做对**"是两件事。
  同一个 handler 里"新建会话"那条路特意写了 `[]int{}`，说明这个坑当初是**知道**的，
  只是没落在函数内部。

### 状态保持（一个容易做错的取舍）

点卡片进播放页会卸载 `FeedView`，游标、已加载的每一页、调试面板的重复探针全部归零。
解法是**提到模块作用域单例** + 路由 `scrollBehavior`（`savedPosition ?? {top: 0}`）。

> ⚠ **别用 `<KeepAlive>` 解决这个问题** —— 被 deactivate 的组件不会触发 `onUnmounted`，
> 详情页播放器那三步释放（`pause()` + `removeAttribute('src')` + `load()`）就静默不跑了，
> 正好是 `utils/cover.ts` 记的那个解码器泄漏。

### 「缺少文件指纹」—— 一个状态有两个来源的经典 bug

现象：某一行直接落 `失败 / 缺少文件指纹`。

根因：`queued` 既是"指纹算完了可以传"，也是 `addPicked` 创建时的初始状态（**那时指纹还不存在**）。
`drain()` 只认 `state`，于是没算过指纹的 item 也会被捞进上传阶段。三条能造出来的路径：

| | 触发 |
|---|---|
| α | **算指纹/上传途中再补选文件** —— `hashPass()` 撞上"已有一轮在跑"时把**那一轮**的 promise 还了回来，而那一轮的 `for (const it of items.value)` 数组对象在循环开始就定死，`concat` 是**换新数组** → 新文件对它彻底隐形 |
| β | **暂停 → 继续** —— `pause()` 会 `hashAc.abort()`，每个 item 立刻抛 AbortError → 全部退回 `queued`（**一个指纹都没有**）；而 `resume()` 只 `wake()`，没重跑哈希 |
| γ | **对循环已越过的 item 点重试** —— 撞上同一轮陈旧 promise |

四处改动，核心是把两个问题分开：
**"算没算过"只有 `prints` 能回答（不是 `state`）**，以及 **`hashPass()` 从"有在跑就返回它"改成串成一条链**。

## 扩展 ★ · 视频播放体验（09-15）

`grep -rln "ffmpeg\|转码\|码率\|m3u8\|HLS\|画质" howto_feed-rebuild/*.md` **零命中**，

### 动因：一个被自己推翻的结论

`bench-notes-video-delivery.md` 先测出"**撑 33 人**"，然后自己发现那是**假的安全感**：

- 服务端单流 **9.38 Gbps**（需求的 780×），30 并发完整下载 **30/30 成功、聚合 11.53 Gbps（960×）**
- **瓶颈在 12 Mbps 家宽上行**（`WLAN LinkSpeed = 144.4 Mbps`，差 **12 倍**）
- 首帧公式 `RTT + 缓冲字节数 ÷ 每人分到的带宽` 预测与实测**吻合到 0.05 秒以内**
- **"撑 33 人"成立的唯一原因是上传者碰巧传了低码率** ——
  135 条素材里 **128 条是 1080p 却只有 0.16~1.16 Mbps**，**分辨率和码率脱钩**

### 于是做了 A~D 四段

| 段 | 内容 | 状态 |
|---|---|---|
| A | QoE 埋点（`internal/qoe/` + `useQoE.ts` + 看板 `/qoe`） | 🔶 代码完成，**基线未采**（错过采集时机，必须在 `r.Static` → `mountStatic` 替换**之前**采） |
| B | 上传质量门禁（`mp4probe.go` 读 moov，超阈值入队） | ✅ 实测通过 |

| D | 播放端 hls.js + ABR（动态 import，按播放才构造） | 🔶 请求链实测通过，**未在真浏览器点过** |

### 关键数据

- 转码：`#383` 45MB 无音轨 → **5.308s / 29.3MB / 19 文件**；`#384` 30.9MB AAC 192k → **3.255s / 20.6MB / 16 文件**
- 码率保真度 **93.8% ~ 106.7%**，峰值段不超过均值的 **103%**

### 两条反直觉的实测结论

1. **声明值 `BANDWIDTH` 偏乐观**：最坏一格（480p 带音轨）**峰值段是声明值的 110%**。

2. **存量素材 135 条里 0 条触发转码** —— 最低档 480p 阈值 1250 kbps，而全库最大只有 1156 kbps。
   "假的安全感"的精确形态是**分辨率与码率脱钩**：带宽开销只有 1080p 档位目标的 **1/12**。
